# immer-wiederholen

Telegram bot for practicing German with multiple choice questions (aiogram, Python). Exercises and topic relations are loaded at startup from the directory set by `COURSE_PATH` env var (default: `data`) — `{COURSE_PATH}/exercises.yaml` and `{COURSE_PATH}/topics.yaml`. Bot commands: `/start`, `/wiederholen` (show a exercise with answer options), `/progress` (today's remaining/new-today/answered-today counts plus a learning/mastered breakdown by word), `/language` (toggle ru/en), `/reset` (wipe the repetition schedule and today's answer stats after an inline confirm/cancel prompt).

`data/` is gitignored and populated locally with `exercises.yaml` (the exercise database) from outside this repo. Each `Exercise` has a `word` (the specific vocabulary item it drills, e.g. a verb like `sprechen`) and a `topic` (the grammar aspect being drilled, e.g. `partizip_ii`, `preteritum`, `government`) — `topic` is a free-form string (not a fixed enum), so new topics can be introduced without needing a code change in this repo.

## Key modules

Three top-level packages: `wiederholen.school` — everything about learning, transport-agnostic, shared by every frontend — and two delivery mechanisms that depend on `school` but never the other way around: `wiederholen.bot` (Telegram, aiogram) and `wiederholen.web` (a widget embeddable on a landing page, see `docs/web-frontend.md`).

- `wiederholen.school.curriculum` — `Exercise`/`Recall`/`Topic`, `Course` — the loaded exercises + `word_chained_topics`/`answer_chained_topics` (see below). The content model: what's being taught, not how it's scheduled or authored. Both `tutoring` and `authoring` depend on it as equal siblings, neither depends on the other through it.
- `wiederholen.school.tutoring` — the repetition-scheduling engine specifically (not the whole learning domain — that's `school`): `student_record` (`StudentRecord` — per-user persisted schedule state), `session` (`Mark`/`Progress`, `Tutor` — date-based repetition scheduling for one user's student_record, constructed as `Tutor(course, student_record)`; also owns the reminder decision, see "Reminders" below), `selection` (`SelectablePairs` — `next_exercise()`'s word/topic selection engine, factored out because its logic is entirely pairs-derived and needs no `Tutor`/`StudentRecord` state of its own), `events` (`RecallMode`, `ExerciseAnswered`/`TopicUnlocked`/`NoExerciseAvailable`/`TutoringEvent` — see "Tutoring events" below). The package's `__init__.py` re-exports all of these, so callers just do `from wiederholen.school.tutoring import ...`. Imports nothing beyond the standard library, `wiederholen.school.curriculum`, and its own sibling modules — no infra, no network — which is what keeps `Tutor`/`StudentRecord` testable without mocking anything external.
- `wiederholen.school.i18n` — supported languages (`Language` type, `LANGUAGES` set)
- `wiederholen.school.student_record_book` — `StudentRecordBook`/`RedisStudentRecordBook` (see "Persistence" below); transport-agnostic storage, a sibling of `tutoring`/`authoring`, not a dependency of either
- `wiederholen.school.authoring` — AI-generated "shadow" exercises (see "AI-generated exercises" below); the one module in the codebase that talks to an LLM, a flat module (not a package — there's only ever been the one file) deliberately a sibling of `tutoring`, not inside it, for the reason above; it depends on `wiederholen.school.curriculum` directly, not on `tutoring`, since all it actually needs is the content model
- `wiederholen.school.__init__` aggregates the public API of all of the above, mirroring `tutoring`'s own `__init__.py` one level up — `wiederholen.bot` imports everything it needs school-side with `from wiederholen.school import ...`
- `wiederholen.bot` — Telegram bot implementation (aiogram); each command lives in its own module under `wiederholen.bot.commands`. Every handler resolves the `StudentID` it addresses `StudentRecordBook` with via `wiederholen.school.student_identity_store.StudentIdentityStore` (see "Student identity" below), rather than deriving it directly from the chat itself.
- `wiederholen.web` — the embeddable-widget backend (Litestar); see `docs/web-frontend.md`.

## Repetition schedule

Spaced-repetition scheduling — `Tutor`/`StudentRecord`, `SelectablePairs` word/topic selection, repeat-avoidance, the daily new-word cap, chains/gates in `topics.yaml`, and `/progress`'s six numbers — is documented in full in `docs/repetition-schedule.md`. Read it before touching `wiederholen.school.tutoring.session`/`selection`/`student_record` or `wiederholen.school.curriculum.Course`'s chain/gate loading.

## Tutoring events

`check_answer()` returns just `Mark`, and `next_exercise()` returns just `Exercise | None` — neither threads an event list up to a caller. Instead, `wiederholen.school.tutoring.events.emit()` writes directly onto `trace.get_current_span()` — the span `wiederholen.bot.tracing.TracingMiddleware` already opened for the current Telegram update — the moment a meaningful thing happens, from inside `Tutor` itself. `wiederholen.school.tutoring` gaining a dependency on `opentelemetry-api` (not the SDK) for this is a deliberate, narrow exception to the package's own "no infra" rule: the API package is designed to be a safe no-op without a configured provider (`trace.get_current_span()` returns an inert span, and `.add_event()` on it does nothing), unlike a real infra dependency like `redis` or an HTTP client would be — so `Tutor`'s tests still need no mocking for this, and a test that doesn't care about tracing doesn't need to change at all. An earlier design collected `TutoringEvent` dataclasses into a list, returned it up through `check_answer()`/`next_exercise()`'s return signatures, and had the bot layer bridge each one to a span event at every call site (`wiederholen.bot.tracing.record_tutoring_events()`) — dropped once it became clear that bridge was the *only* consumer of that list anywhere in the codebase: nothing in `wiederholen.bot.commands.wiederholen` ever branched on event content (e.g. `NoExerciseAvailable.reason` was never read by the bot layer — the "study more" button shows on `exercise is None` alone), so routing observability through a public return value was pure ceremony for a fact only tracing cared about.

`ExerciseAnswered`, `TopicUnlocked`, `NoExerciseAvailable` (the `TutoringEvent` union) are still plain frozen dataclasses, living in `wiederholen.school.tutoring.events` alongside `emit()` and `RecallMode` — internal to the package now, not part of its public API (`wiederholen.school.tutoring.__init__.py`/`wiederholen.school.__init__.py` no longer export any of the three, or the union type; only `RecallMode` still does, since `Mark.recall`/the bot layer's recall-flow branching both need it). Keeping them as dataclasses rather than inlining `span.add_event()` calls with raw dict literals still matters: deciding *what counts as a meaningful event and when it fires* is domain knowledge (e.g. `ExerciseAnswered.is_new` mirrors the same `is_new` local `check_answer()` already gets back from `record_mark()`, `prev_repetition_interval: int | None` mirrors that same return value's other half — `None` for a pair's very first answer, see above — and `next_repetition_interval` mirrors what `_calc_next_repetition_interval()` already computes; `TopicUnlocked.via` — `"chain"` vs `"gate"`, based on whether `dependent_topic in course.gated_topics` — mirrors the gating rule from the previous section), so each event's shape stays declared once, next to the rule it's describing.

`ExerciseAnswered` is always emitted once per `check_answer()` call. `TopicUnlocked` is emitted once per dependent `_expedite_dependent()` actually creates an entry for (`Tutor._emit_topic_unlocked()` builds the event and emits it in one call — `_expedite_chained_topics()` itself returns nothing now, having no caller left to hand a list to). `NoExerciseAvailable` is emitted once whenever `next_exercise()` is about to return `None`, with a `reason: Literal["nothing_available", "daily_cap_reached"]` distinguishing empty pools from a cap-exhausted pick (see "Word selection" in `docs/repetition-schedule.md`). `request_recall()` still doesn't emit anything.

`emit()` builds the span attributes itself (`_attributes()`, the same logic the old bot-layer bridge used to own): starts from `dataclasses.asdict(event)` and adjusts two kinds of field that aren't valid span attribute values as-is — `Enum` fields (e.g. `ExerciseAnswered.recall_mode`) are unwrapped to their `.value` first, since an `Enum` instance isn't a valid span attribute type; `None` fields (e.g. `ExerciseAnswered.prev_repetition_interval` for a pair's very first answer, see above) are dropped from the attribute dict entirely rather than sent as-is — unlike an `Enum`, there's no single plain value to unwrap a missing interval to, and passing `None` through isn't a valid span attribute either. Testing this now means constructing a real, recording `TracerProvider`/`InMemorySpanExporter` and reading `span.events` back off it after calling `check_answer()`/`next_exercise()` under `tracer.start_as_current_span(...)` — `tests/school/tutoring/test_tutoring_events.py` does this via the shared `tracer`/`exporter` fixtures (`tests/plugins/tracing.py`, also used by `tests/bot/test_tracing.py`'s own span-content tests) rather than asserting on a returned list, the one real cost of this design (see "Tests" below) — the rest of `Tutor`'s test suite is unaffected, since `add_event()` on the default no-op span (no provider configured) is always safe and silently does nothing.

## Persistence

`wiederholen.school.student_record_book.StudentRecordBook` is an abstract, transport-agnostic store for exactly one thing: the student_record dict `Tutor`/`StudentRecord` operate on, addressed by a plain string `student_id` — resolved via `wiederholen.school.student_identity_store.StudentIdentityStore.resolve_or_create_student_id("telegram", str(chat_id))` for the Telegram bot's message handlers, `resolve_or_create_student_id("telegram", str(callback.from_user.id))` for its callback handlers (the same value in a private chat, which is all this bot has ever supported) — see "Student identity" below for why a resolution step exists at all rather than a bot-local encode/decode scheme. It has exactly two public members: `check_out(student_id)` and `__aiter__` — no public `close()`, see below. `_get(student_id) -> dict`/`_save(student_id, student_record)` are private abstract primitives — no caller outside the class needs them directly, since `check_out(student_id)` is a concrete `@asynccontextmanager` built on them alone (no subclass needs to override it) that fetches the student_record, yields it for in-place mutation via `Tutor`, and saves it back on exit **only if it actually changed** from a `copy.deepcopy` snapshot taken right after the fetch (plain `!=` on the two dicts — student records are already JSON-safe values, so structural equality is exactly what's wanted, no custom diffing needed). That one rule covers every caller uniformly, with no separate read-only or conditional-save path needed anywhere: a handler that unconditionally mutates (`check_answer()` recording an answer) gets saved; one that never mutates at all (`/progress`, `handle_recall`'s pure `check_recall()`) triggers no write; one that mutates only along a taken branch (the reminder worker, which only calls `record_reminder_sent()` once a reminder actually sends — see "Reminders") gets saved only then. The comparison runs in a `finally` block, so a mutation already applied before the body raises (e.g. `check_answer()` running before a later `message.answer()` fails) still gets saved rather than silently lost. Named `check_out`, not `open`: `store.open(id)` reads, grammatically, as "open the store" (a method applied to a receiver reads as an action *on* that receiver, unlike the free-function `open()` builtin), and `open_student_record` — tried in between — just repeated "student_record" for no reason once the receiver is already a `StudentRecordBook`. `check_out` sidesteps both: like a library checkout, the verb alone already implies "borrow one item from a store," and the borrow/mutate/return-on-exit lifecycle is a close match for what the method actually does. Every `wiederholen/bot/commands/*.py` handler that touches the student_record opens exactly one `async with student_record_book.check_out(student_id) as student_record:` per request and does its response-building and message-sending inside that block — there's nothing else to reach for. `RedisStudentRecordBook` is the concrete implementation, one JSON blob per student under the Redis key `f"student_record:{student_id}"`. `__aiter__` — iterating the store itself (`async for student_id in student_record_book`) — yields every `student_id` with a stored student_record, deliberately not the student_record alongside it: this mirrors `dict.__iter__`'s own key-only convention, and a caller that needs a given student's student_record reads it via `check_out()` like anywhere else, so there's no second way to fetch one.

Releasing a connection (`RedisStudentRecordBook`'s `_close()` plus its own `__aenter__`/`__aexit__` — `__aenter__` returns `self`, `__aexit__` calls `self._close()`) lives entirely on `RedisStudentRecordBook`, not on the abstract `StudentRecordBook` — whether there's a connection to release at all, and how, is specific to this one backend, not a guarantee every `StudentRecordBook` implementation carries; a hypothetical in-memory store for tests, say, would have nothing to close. There's no public `close()` to call directly either way. The only place a store's lifetime is actually scoped this way today is `tests/plugins/student_record_book.py`'s `student_record_book` fixture (`async with RedisStudentRecordBook.from_url(...) as store: yield store`) — production (`wiederholen.bot.__main__.main()`/`wiederholen.bot.reminder.main()`) never closes its store at all, since both processes just run until killed and let the OS reclaim the connection. Not exposing `close()` as an ordinary public method means a caller can't half-remember-to-call-it; the only door open is the same `async with` protocol Python already trains every reader to recognize for anything resource-owning.

Deliberately scoped to *only* the student_record, not the rest of a chat's per-session state (language, ai_mode, mid-conversation shown_exercise/shown_recall, last_buttoned_message_id, aiogram's own conversation-state name) — that's Telegram session/UI state, and stays in aiogram's own `RedisStorage` (see below) rather than this store: the student_record is the one piece of per-student state that's genuinely meant to be transport-independent (a future web frontend embedded on a landing page would need to read/write the same learning record a Telegram chat has, with its own notion of `student_id`), while a chat's language preference or which exercise is mid-flight isn't something a web client would share with the Telegram bot the way the actual learning record is. `wiederholen.school.tutoring` (`Tutor`/`StudentRecord`) still never touches `StudentRecordBook` or any other storage itself — it only ever receives a plain `dict` from whichever transport layer is calling it, keeping the "no I/O" invariant that package started with (see "Key modules" above) — `StudentRecordBook` is a layer *between* a transport and `Tutor`, not a dependency of `Tutor`'s.

Everything else per chat — language, ai_mode, shown_exercise/shown_recall, last_buttoned_message_id, and aiogram's own conversation-state name (the `UserState.answering`/`.recalling` a router filters on) — stays in a plain, unmodified `aiogram.fsm.storage.redis.RedisStorage`, exactly as aiogram ships it; there's no codebase-specific subclass wrapping it. `wiederholen.bot` builds `dispatcher` with aiogram's default in-memory FSM storage (needed so importing the package — e.g. from tests — never depends on an external service or env var). `wiederholen.bot.bootstrap.load_bot_course_and_storage() -> tuple[Bot, Course, RedisStorage, StudentRecordBook, StudentIdentityStore]` constructs the real `RedisStorage` (from `BOT_FSM_STORAGE_URL`), a `RedisStudentRecordBook` (from its own `STUDENT_RECORD_STORAGE_URL`, via the separate `load_student_record_book()`), and a `RedisStudentIdentityStore` (from `STUDENT_IDENTITY_STORAGE_URL`, via `load_student_identity_store()` — see "Student identity" below) — all required with no fallback, same as `BOT_TOKEN`. The three storage env vars point at the same physical Redis today, just different DB numbers (`STUDENT_RECORD_STORAGE_URL` on DB 0, `STUDENT_IDENTITY_STORAGE_URL` on DB 1, `BOT_FSM_STORAGE_URL` on DB 3 — deliberately keeping the two `wiederholen.school`-owned "student" stores adjacent, with `WEB_SESSION_STORAGE_URL` at DB 2 in between and transport-specific FSM state pushed to the end; not separate instances), and are deliberately separate names rather than one shared one: `wiederholen.school`'s own transport-independence (see above — a future web frontend would share the student record, not the Telegram session state) means the stores are conceptually independent even while they happen to be colocated, and a distinct env var per store is what would let a future deployment point any one of them at a separate Redis instance (or a wholly different backend) without touching the others. Both `wiederholen.bot.__main__.main()` (polling bot) and `wiederholen.bot.reminder.main()` (reminder worker) call this one function and get all five pieces back, even though the reminder worker has no aiogram routers of its own — it still needs `RedisStorage` for a small point lookup (see "Reminders" below), so splitting the loader in two wouldn't actually let it drop the dependency. `main()` assigns the `RedisStorage` to `dispatcher.fsm.storage`. Works with Valkey too (wire-compatible). `compose.yaml` (local dev, this repo) and the deployment compose file (outside this repo) both run a `valkey` service and set both `BOT_FSM_STORAGE_URL` and `STUDENT_RECORD_STORAGE_URL` for the `bot` and `reminder` services, backed by a named volume for durability across container recreation.

Tests run against a real Redis/Valkey too, not an in-memory fake — `tests/plugins/aiogram.py::pytest_configure` pins all four storage env vars (`BOT_FSM_STORAGE_URL`, `STUDENT_RECORD_STORAGE_URL`, `STUDENT_IDENTITY_STORAGE_URL`, `WEB_SESSION_STORAGE_URL`) to the same dedicated DB number for the whole test session, before any test code runs, so a local `docker compose run bot pytest` (which shares the `bot` service's real dev config) can never touch a DB a real dev/prod bot might be using regardless of what's set in the environment. The DB number comes from the `--redis-db-override` pytest option (named for what it now overrides — every one of those connection URLs, not just the FSM one — since the day it started covering more than just `BOT_FSM_STORAGE_URL`), defaulting to `15` (separate from any dev/prod DB — `0` for student records, `1` for student identity, `2` for web sessions, `3` for FSM, see "Persistence"/"Student identity" above) via `pyproject.toml`'s `addopts`; passing `--redis-db-override=""` disables the pin entirely, which the CI workflow does since its `valkey` service container is already ephemeral and tests-only, so there's no dev/prod DB to protect there — CI instead points them at their normal, *different* DB numbers on that same ephemeral container, deliberately: it's a cheap way to actually prove the stores are independent (a test accidentally reading/writing the wrong store's data would surface as a real failure there, not silently pass because both happened to share one DB). `tests/plugins/aiogram.py`'s `redis_storage` fixture builds a plain `RedisStorage` and flushes the DB before every test; the autouse `_reset_storage` fixture wires it into `dispatcher.fsm.storage`. `tests/plugins/student_record_book.py`'s `student_record_book` fixture builds a `RedisStudentRecordBook` from `STUDENT_RECORD_STORAGE_URL` and flushes *its own* DB directly, rather than assuming it coincides with `redis_storage`'s — the two DBs are different by default everywhere (compose.yaml, CI) and only coincide when the `--redis-db-override` pin forces both to the same overridden DB for a local pytest run, so relying on a same-DB assumption would silently stop cleaning this store the moment that assumption didn't hold (it still takes `redis_storage` as a parameter, but only for fixture ordering relative to `_reset_storage`, not for its flush) — and its own autouse `_set_student_record_book` fixture registers it as **permanent** aiogram workflow data (`dispatcher["student_record_book"] = student_record_book`, the same mechanism `main()` uses via `dispatcher.start_polling(..., student_record_book=...)`), not a per-call `feed_message(..., student_record_book=...)` kwarg the way `course` is — unlike `course` (different exercises in nearly every test), `student_record_book` is the same piece of infrastructure for every test in the session, so no test needs to pass it explicitly. This is deliberately fidelity-over-speed: it's still fast (no measurable slowdown at this suite's size) and catches real Redis behavior an in-memory double can't. Both fixtures are function-scoped, not session-scoped: pytest-asyncio gives each test its own event loop by default, and a Redis connection can't outlive the loop it was created in.

## Student identity

`wiederholen.school.student_identity_store.StudentIdentityStore` resolves a login (a `provider` — `AuthProvider = Literal["telegram", "browser"]` — plus that provider's own `identifier`, e.g. a Telegram `chat_id` as a string) to the `StudentID` that already-transport-agnostic `StudentRecordBook` is addressed by. Introduced because a bot-local `TelegramStudentID.encode(chat_id)` (the id scheme this replaced) baked "how do I address this student" and "which chat is this" into one inseparable, single-provider function — fine as long as Telegram was the only way in, but not once a second way of recognizing the same student (a future `/login_by_email`, or `wiederholen.web`'s own `"browser"` provider for a logged-in cookie — see "Telegram login" below) needs to resolve to the *same* student a Telegram chat already has, rather than minting an unrelated second one.

Two concepts, deliberately kept apart: an **account** (a student, and everything they've learned) is not the same thing as a **credential** (one way of proving you're that student). `StudentID` already *is* the account-level concept — a plain, transport-agnostic key `StudentRecordBook` doesn't interpret — so nothing new was invented for it; introducing a separate `AccountID` type would just have meant two names for the one value. What `StudentIdentityStore` adds is the missing piece: a place to look up *which* `StudentID` a given login belongs to, and to attach an additional login to an existing one later.

```python
class StudentIdentityStore(ABC):
    async def resolve_or_create_student_id(
        self, provider: AuthProvider, identifier: str
    ) -> StudentID: ...
    async def resolve_student_id(
        self, provider: AuthProvider, identifier: str
    ) -> StudentID | None: ...
    async def link_identity(
        self, student_id: StudentID, provider: AuthProvider, identifier: str
    ) -> None: ...
    def iter_identifiers(
        self, provider: AuthProvider
    ) -> AsyncIterator[tuple[str, StudentID]]: ...
```

`resolve_or_create_student_id()` is what every bot handler calls at the top of its own `check_out()` block: looks up `(provider, identifier)`; mints a fresh `StudentID` (`secrets.token_urlsafe(32)`, same shape `WebStudentID` already used for its own unrelated anonymous case) and records it if nothing was linked yet. `resolve_student_id(provider, identifier)` is the same lookup with the create half removed — `None` on a miss rather than minting one — for a caller where an unresolvable identifier means "fall back to something else" (e.g. `wiederholen.web`'s `"browser"` cookie, see "Telegram login" below) rather than "this is a legitimate first-time login." `link_identity(student_id, provider, identifier)` is the same write, aimed at a specific, already-known `student_id` instead of minting a new one — the primitive a future "attach an email to my existing Telegram-linked account" flow builds on; it raises `IdentityAlreadyLinkedError` if `(provider, identifier)` already resolves to a *different* student, rather than silently reassigning it. `RedisStudentIdentityStore` stores exactly one row per login, `identity:{provider}:{identifier} -> student_id`, written via `SET ... NX` so two concurrent first-time resolutions for the same brand-new `(provider, identifier)` still converge on one winner rather than minting two accounts. `iter_identifiers(provider)` — a `SCAN` over `identity:{provider}:*` — is what `wiederholen.bot.reminder.tick()` sweeps instead of `StudentRecordBook` itself (see "Reminders" below): scoped to one provider by construction, so a student reachable only through some other, non-Telegram provider is never even considered, no exception-catching needed to exclude it.

Naming went through several iterations worth recording since none of them were obviously right on the first pass: `identifier` (not `id`, which would shadow the builtin and, unlike every other `_id`-suffixed name in this codebase, appear with no noun in front of it; not `subject`, which borrows OIDC/JWT vocabulary for a protocol this doesn't actually implement — Telegram has no real OIDC endpoint, only its own bespoke per-surface signature schemes; not `provider_user_id`, needlessly long once `StudentIdentityStore` already supplies the missing context an isolated `identifier` used to lack). The store itself was `CredentialStore` before it was `StudentIdentityStore` — renamed once it became clear it holds no actual credential (a password, a token, a signature) at all, only the *result* of one having been checked elsewhere, once, transiently.

Deliberately excludes `wiederholen.web.web_student_id.WebStudentID`'s anonymous cookie path — an anonymous visitor isn't a login of any kind, has nothing to resolve, and folding it in here would make every drive-by page load count as a real identity the moment "how many students do we have" ever gets built on top of `StudentIdentityStore`'s own row count. `STUDENT_IDENTITY_STORAGE_URL` is its own env var/DB (1, deliberately adjacent to `STUDENT_RECORD_STORAGE_URL`'s DB 0 — the two `wiederholen.school`-owned "student" stores, as opposed to `BOT_FSM_STORAGE_URL`/`WEB_SESSION_STORAGE_URL`'s more transport-specific session state, which is what pushed `BOT_FSM_STORAGE_URL` off its original DB 1 to DB 3 rather than leave that adjacency implicit), following the same one-store-one-DB convention as the other three; `tests/plugins/aiogram.py::pytest_configure`'s `--redis-db-override` pin covers it the same way. No longer bot-only: `wiederholen.web` resolves through it too, both for its own Telegram Login Widget (`resolve_or_create_student_id("telegram", ...)`, the same call the bot makes) and for its `"browser"` cookie provider — see "Telegram login" below for both. `email` as a further `AuthProvider` still needs sending infrastructure (SMTP or a transactional API, code generation/expiry) this codebase doesn't have yet.

## Tracing

`wiederholen.tracing` (top-level, a sibling of `school`/`bot`/`web`) holds the generic OpenTelemetry setup every process that touches Redis needs — `default_tracer`, `configure_tracing()`, `instrument_redis()` — while `wiederholen.bot.tracing` keeps only what's genuinely aiogram-specific: `TracingMiddleware` and its `_describe()` helper for turning a Telegram `Update` into a span name/attributes. This split exists because `wiederholen.web.__main__` needs the same generic setup `wiederholen.bot.__main__`/`wiederholen.bot.reminder` already had — importing it from `wiederholen.bot.tracing` would have made `wiederholen.web` depend on `wiederholen.bot`, which "a sibling of `wiederholen.bot`, not a dependency of it or vice versa" (see `docs/web-frontend.md`) rules out. An earlier version of this fix tried exactly that import before catching the violation and extracting this module instead. `wiederholen.bot.tracing` imports `default_tracer` from here for `TracingMiddleware`'s own default argument, but re-exports nothing — `wiederholen.bot.__main__`/`wiederholen.bot.reminder`/`wiederholen.web.__main__` all import `configure_tracing`/`instrument_redis`/`default_tracer` directly from `wiederholen.tracing`, not proxied through the bot package.

`wiederholen.bot.tracing.TracingMiddleware` wraps every incoming Telegram update in one OpenTelemetry span — registered as `outer_middleware` on `dispatcher.update` (not `.message`/`.callback_query`) in `wiederholen/bot/__init__.py`, deliberately at the top-level "update" observer rather than the per-event-type ones. This matters because aiogram's own `Dispatcher.__init__` registers several of its own outer middlewares on `dispatcher.update` — `ErrorsMiddleware`, `UserContextMiddleware`, and `FSMContextMiddleware` (`dispatcher.fsm`) — and `FSMContextMiddleware` reads the current FSM state from storage (a Redis `GET` via `RedisStorage`, see "Persistence" below) *before* routing even resolves message vs callback_query vs anything else. Outer middlewares wrap in registration order (first-registered = outermost — verified via aiogram's `MiddlewareManager.wrap_middlewares`), so registering `TracingMiddleware` on `dispatcher.message`/`.callback_query` (an earlier version of this) meant that Redis `GET` always ran *before* our span existed, showing up as an orphan root span in the backend instead of a child of the update's span — caught by directly inspecting real trace data. The fix: construct `Dispatcher(disable_fsm=True)` (which still creates `dispatcher.fsm` but skips aiogram's own auto-registration of it as outer middleware) and register `TracingMiddleware` on `dispatcher.update` first, then `dispatcher.fsm` second — so our span now wraps the FSM state lookup too. Confirmed empirically both ways: pointed a live dispatcher at real Redis with an in-memory span exporter and checked parent/child span IDs directly, rather than trusting the theory. `dispatcher.fsm.storage = storage` (set later in `main()`, see "Persistence") still works exactly as before — `disable_fsm` only skips the auto-registration, not the middleware's existence.

The module-level `_describe()` function unwraps `update.event` (aiogram's own property for "whichever event type is actually set on this Update") and builds the span name/attributes from it: `"telegram.message"` with `telegram.chat_id` and, only if the text is a bot command (starts with `/`), `telegram.command` — deliberately never the raw free-text an exercise answer might contain; `"telegram.callback_query"` with `telegram.chat_id` (from `event.message`, guarded by `isinstance(..., Message)` since Telegram can hand back an `InaccessibleMessage` for an old message) and `telegram.callback_data` (always one of this codebase's own fixed constants — `NEXT_EXERCISE`/`RECALL`/`STUDY_MORE`/etc. — never free text, so safe to record outright). Any other update type (this bot doesn't handle any, but Telegram can still deliver e.g. `poll_answer`/`my_chat_member`) falls back to a generic `"telegram.update"` span with no attributes, rather than the middleware raising for a type it doesn't special-case.

The SDK wiring is separate from the middleware itself: `TracingMiddleware` takes an injectable `tracer` (defaulting to `wiederholen.tracing.default_tracer`, a module-level `trace.get_tracer(__name__)` obtained *before* any provider is configured) — this is the standard OTel pattern, since `get_tracer()` returns a proxy that starts delegating to a real provider the moment one is registered, so it's safe to grab at import time. `configure_tracing()` (which builds the real `TracerProvider` + `BatchSpanProcessor(OTLPSpanExporter())` and calls `trace.set_tracer_provider()`) is called only from `wiederholen.bot.__main__.main()`, `wiederholen.bot.reminder.main()`, and `wiederholen.web.__main__.main()`, never at import time — so importing `wiederholen.bot`/`wiederholen.web` (e.g. from tests) still has no external dependency (same reasoning as the in-memory FSM storage default, see "Persistence" above): without a configured provider, spans are inert no-ops. `configure_tracing()` itself is a no-op (`_otlp_endpoint_configured()` returns `False`, checked before touching anything else) unless `OTEL_EXPORTER_OTLP_ENDPOINT` or `OTEL_EXPORTER_OTLP_TRACES_ENDPOINT` is actually set — deliberately: `OTLPSpanExporter()` on its own defaults to `http://localhost:4318` (the standard convention for a local collector sidecar), which this project's plain docker-compose deployment never has, so without an explicit endpoint that default is never valid; without this check, `configure_tracing()` would still build a real `TracerProvider`/`BatchSpanProcessor` that spends its life retrying a doomed export in the background (confirmed: `BatchSpanProcessor` logs `Transient error ... Connection refused` repeatedly and `Failed to export span batch` on shutdown) purely as log noise, never actually breaking anything since it fails closed rather than raising. `configure_tracing()` passes `Resource.create()` no explicit attributes at all — deliberately: every other piece of this config (endpoint, headers, protocol) is 100% env-var-driven with no code-level default, so `service.name`/`service.namespace`/etc. follow the same rule via `OTEL_SERVICE_NAME`/`OTEL_RESOURCE_ATTRIBUTES`, falling back to the OTel SDK's own generic `"unknown_service"` if genuinely unset. A hardcoded fallback name was tried and dropped: it actively hid a real misconfiguration (the `reminder` service briefly missing its `OTEL_*` env vars in `compose.override.yaml` — see below) by making its spans look identically labeled to the bot's instead of standing out as unconfigured. Tests exercise `TracingMiddleware` by constructing it directly with a throwaway `TracerProvider`/`InMemorySpanExporter` (`tests/bot/test_tracing.py`) rather than touching the process-global provider, since `trace.set_tracer_provider()` can only ever succeed once per process — a second call is a silent no-op, which would make per-test isolation impossible if tests relied on the global registration instead; `configure_tracing()`/`_otlp_endpoint_configured()`/`instrument_redis()` themselves (owned by `wiederholen.tracing`, not aiogram-specific) get their own direct tests in `tests/test_tracing.py` instead, split out from `tests/bot/test_tracing.py` (which now holds only `TracingMiddleware`'s own span-content tests) when the module itself split.

`tests/plugins/tracing.py::pytest_configure` forces `OTEL_SDK_DISABLED=true` for the whole test session, before any test code runs — same rationale and shape as `tests/plugins/aiogram.py::pytest_configure` pinning `BOT_FSM_STORAGE_URL`/`STUDENT_RECORD_STORAGE_URL` to a dedicated DB (see "Persistence" above): `docker compose run bot pytest` shares the `bot` service's config with the real bot, so without this, a real `OTEL_EXPORTER_OTLP_ENDPOINT`/`HEADERS` set for local dev (e.g. real Honeycomb credentials via `compose.override.yaml`, see below) would mean every test run actually exports real spans to that backend — confirmed by temporarily pointing the endpoint at an unreachable address and watching `BatchSpanProcessor` retry and fail to export at process exit (`TracerProvider` registers an `atexit` handler that flushes on shutdown by default). `OTEL_SDK_DISABLED` is read by `TracerProvider.__init__` itself — regardless of whether it's the global provider or a one-off instance a test constructs directly — so it also disables the throwaway `TracerProvider`/`InMemorySpanExporter` the shared `tracer`/`exporter` fixtures (`tests/plugins/tracing.py`, same file as the `pytest_configure` above) build to verify span content; `tracer` explicitly opts back in with `monkeypatch.delenv("OTEL_SDK_DISABLED", raising=False)` before constructing its own provider, scoped to just the tests that request it via `monkeypatch`'s automatic teardown. `tests/bot/test_tracing.py` (`TracingMiddleware`'s own span content) and `tests/school/tutoring/test_tutoring_events.py` (`emit()`'s span events, see "Tutoring events" above) share these two fixtures rather than each defining their own copy.

`compose.override.yaml` (gitignored, local-only, also used to bind-mount the private content repo's `data/`) sets `OTEL_SERVICE_NAME`/`OTEL_RESOURCE_ATTRIBUTES`/`OTEL_EXPORTER_OTLP_*` per service (`bot`/`reminder` each get their own `OTEL_SERVICE_NAME` so their spans are distinguishable in the backend) — this needs its own `environment:` block under *each* service key, since Compose merges `environment` per-service, not globally; a service with no block simply gets none of these vars and `OTLPSpanExporter()` silently falls back to `http://localhost:4318`, which just fails every export in a container with no local collector. A stray `=` inside a YAML mapping *key* (e.g. `OTEL_RESOURCE_ATTRIBUTES=:` instead of `OTEL_RESOURCE_ATTRIBUTES:`) is a related trap worth knowing about: Compose doesn't error on it, it silently becomes part of the *value* instead (`docker compose config` is the way to check what actually gets resolved) — which for `OTEL_RESOURCE_ATTRIBUTES` manifests as a leading `=` that makes the first `key=value` pair parse with an empty key, logged by `opentelemetry/attributes` as `invalid key `` `.

`instrument_redis()` wraps `opentelemetry.instrumentation.redis.RedisInstrumentor().instrument()` — third-party auto-instrumentation that monkeypatches `redis`'s command execution (both the sync client and the `redis.asyncio.Redis` both `RedisStorage` and `RedisStudentRecordBook`/`WebSessionStore` use, see "Persistence" above) to emit a span per Redis call, with no code changes needed at any call site — it patches the client class globally, so it covers all of them regardless of which process reaches them. It's idempotent (a repeat call just logs a warning and no-ops) like `set_tracer_provider()`, which matters because both it and `configure_tracing()` get called on every `main()` invocation, including the repeated ones in `tests/bot/test_main.py`/`tests/bot/test_reminder.py`/`tests/web/test_main.py` within a single test session. `wiederholen.bot.__main__.main()`, `wiederholen.bot.reminder.main()`, and `wiederholen.web.__main__.main()` all call `configure_tracing()` and `instrument_redis()`, since all three processes talk to Redis one way or another. The `TracingMiddleware`-per-update span coverage above is bot-only (the reminder worker has no aiogram routers to wrap, and `wiederholen.web` is a Litestar app with no aiogram involved at all) — but `wiederholen.bot.reminder` gets its own hand-rolled equivalent instead of going without: `tick()` wraps its whole sweep in a `"reminder.tick"` span (via the same `tracing.default_tracer` `TracingMiddleware` uses) and `_remind_chat()` wraps each chat's check in a nested `"reminder.check_chat"` span (`telegram.chat_id` attribute, plus `reminder.sent` — `False` by default, flipped to `True` only once `bot.send_message()` actually succeeds) — without this, every Redis call iterating `student_record_book`/`_remind_chat()` makes would otherwise show up as an orphan root span per call, one per sweep-chat, with no way to see which chat or sweep it belonged to. A chat whose processing raises still gets its exception recorded on `reminder.check_chat` automatically (the exception propagates out through the `with` block before `tick()`'s own `except Exception` catches it and logs), same mechanism as `TracingMiddleware`.

## Reminders

A separate worker process (`python -m wiederholen.bot.reminder`, its own `reminder` service in this repo's `compose.yaml` and in the deployment compose file) nudges users who've gone quiet with material due — not an in-process `asyncio` task in the polling bot, specifically to avoid leaking an uncancelled background task across `tests/bot/test_main.py`'s repeated `main()` calls.

`Tutor` owns the decision, student_record-backed like the rest of its scheduling state: `check_answer()` records `student_record["last_exercise"]["answered_at"]` (a timestamp, part of the same `last_exercise` record as `question`) — "activity" means answering the main exercise specifically, not any interaction with the bot (recall answers don't count). `Tutor.should_remind()` is a pure query — no side effects — returning `True` only if there's anything due at all (`self._get_due_pairs()`, unfiltered — introduced status doesn't matter here the way it does for `next_exercise()`'s own selection, so a due-but-not-yet-introduced pair, e.g. one expedited via a chain, counts too) or a fresh-and-ungated pair available (`self._get_available_not_scheduled_pairs()`, deliberately not also unioning in `_get_due_pairs(is_introduced=False)` the way `next_exercise()` does — see above for why that's redundant here) — checked inline rather than through a named helper (a `_due_topics_count()`-style method was tried and dropped: its name suggested only genuinely-*due* reviews, which was misleading once it also counted available-but-not-yet-due new pairs), deliberately not filtered through the word cap, since a reminder should fire even if the cap is what's currently blocking new material — `last_answered_at` is ≥`Tutor.REMIND_AFTER` (24h) old, and there hasn't already been a reminder since that last answer (`last_reminded_at is None or last_reminded_at < last_answered_at`) — this last condition means exactly one reminder per period of inactivity, not a repeating nag. Checking only an available-new check here, without the due-pairs check alongside it (a since-fixed regression, caught by `test_should_remind_is_true_for_an_overdue_review_with_no_new_pairs_available`), would miss a learner who has genuine overdue reviews but is at today's new-word cap, silently never reminding them. `Tutor.record_reminder_sent()` is a separate method, called by the bot layer only *after* a Telegram send actually succeeds — `should_remind()` itself never mutates the student_record, so a failed send never gets wrongly marked as delivered.

The worker has no separate registry of known chats — it sweeps `StudentIdentityStore.iter_identifiers("telegram")` (see "Student identity" below), which yields exactly the `(identifier, student_id)` pairs linked under the `telegram` provider via a real Redis `SCAN` over its own `identity:telegram:*` keys, never touching `StudentRecordBook` to enumerate anything (a student linked only via some future non-Telegram provider is structurally never surfaced here — there's no exception to catch, the sweep simply never reaches it). `wiederholen.bot.reminder.tick()` does this once per sweep, converts each `identifier` back to an `int` chat_id, and delegates to `_remind_chat()`, which opens `student_record_book.check_out(student_id)` (the `student_id` already in hand from the sweep, no re-resolution needed) and builds a `Tutor` from the student_record to decide `should_remind()` — but sending the reminder needs the chat's **language**, which isn't part of the student_record (see "Persistence" above): `_remind_chat()` builds one `FSMContext(storage=fsm_storage, key=StorageKey(bot_id=bot.id, chat_id=chat_id, user_id=chat_id))` for that lookup (`await state.get_data()`), the one place `reminder.py` still touches aiogram directly, since nothing about it depends on iterating anything — it just needs one already-known chat_id's data. That same `FSMContext` also backs `clear_stale_buttons()`/`remember_buttoned_message()` (see "Pending inline buttons" below): the reminder message itself now carries a `make_next_button(locale)` button, and sending it first clears whichever earlier message's button group (e.g. an unanswered "Следующее задание" prompt) was still pending — without this, that old button used to stay attached forever, the same problem `clear_stale_buttons()` already solves for every command entry point, just reached here from a background sweep instead of an incoming `Message`. Both that clear and the send itself can raise `TelegramForbiddenError` for the same reason (the chat blocked the bot), so one `try`/`except` wraps both rather than duplicating the same catch. There's no explicit save call anywhere in `_remind_chat()`: `check_out()`'s own change-detection (see "Persistence" above) already does exactly the right thing — the two early returns (`should_remind()` false, or the try block raising `TelegramForbiddenError`) leave the student_record untouched, so nothing gets written; only the fall-through path, where `record_reminder_sent()` actually runs, changes anything, and that's exactly when `check_out()` saves. One chat raising (e.g. malformed student_record data) is caught and logged, not fatal to the sweep. `run()` loops `tick()` every `POLL_INTERVAL_SECONDS` (15 min).

## Feature flags

`wiederholen.bot.feature_flags` gates a feature by chat_id without persistence or admin commands — built for testing a single premium feature (AI-personalized exercises, not yet implemented) on one test user before any billing exists. `BOT_FEATURE_FLAGS` env var format: `flag_name:chat_id1,chat_id2;other_flag:chat_id3`, parsed once at startup by `wiederholen.bot.bootstrap.load_feature_flags()` (a separate function from `load_bot_course_and_storage()`, not merged into its return tuple — `reminder.py` doesn't call it, since gating a not-yet-built feature isn't a reminder-worker concern) into `dict[str, frozenset[int]]`. `parse_feature_flags(raw)` tolerates surrounding whitespace and a trailing `;` (a flag with no chat ids after `:` parses to an empty `frozenset`, matching no one). `has_feature(flags, flag, chat_id) -> bool` does the actual lookup — `chat_id in flags.get(flag, frozenset())`.

No persistence, no runtime toggling: enabling a flag for a chat means editing `BOT_FEATURE_FLAGS` and restarting, same as `BOT_TOKEN`/`OTEL_*` already work — a genuine limitation for anything beyond a handful of test users, deliberately deferred until there are paying subscribers instead of one.

Deliberately bot-layer-only, mirroring `wiederholen.bot.tracing`'s own precedent for keeping infra/config concerns out of the learning domain: `wiederholen.school` never sees a chat_id or a flag name, and `Tutor`/`StudentRecord` gain no new parameter for this. `__main__.main()` calls `load_feature_flags()` alongside `load_bot_course_and_storage()` and passes the result to `dispatcher.start_polling(bot, course=course, feature_flags=feature_flags)` — aiogram's dependency injection then hands it to any handler that declares a `feature_flags` parameter by name, the same mechanism `course` already relies on. `command_wiederholen` is the one example check point this issue scoped in: `feature_flags: dict[str, frozenset[int]] | None = None` (defaulting to `None`, not `{}`, so the many existing `/wiederholen` tests that don't pass `feature_flags=` don't need touching — production always passes a real, possibly-empty dict) — if `has_feature(feature_flags or {}, "ai_exercises", message.chat.id)`, it sets a `feature.ai_exercises` attribute on the current span and otherwise does nothing. No behavior changes yet for any chat; the actual AI-exercise feature is separate, larger work this unblocks.

## Pending inline buttons

Tapping "Следующее задание"/"Закрепить"/"Study more"/etc. clears its own button — the callback handler gets `callback.message` for free and calls `edit_reply_markup(reply_markup=None)` on it directly. Typing a command instead (`/wiederholen`, `/progress`, `/reset`, `/language`) bypasses that entirely: Telegram never tells a bot which earlier message a command "replaces", so without deliberate tracking the button stays visibly attached to the old message forever, even though the bot has already moved on.

`wiederholen.bot.pending_buttons` fixes this with one piece of FSM state, `last_buttoned_message_id: int | None`, alongside `student_record`/`shown_exercise`/etc.: `remember_buttoned_message(state, message)` stores the id of a message that was just sent with an inline keyboard; `forget_buttoned_message(state)` clears it once the button's markup is gone some other way; `clear_stale_buttons(bot, chat_id, state)` reads the stored id and, if one is pending, strips it via `bot.edit_message_reply_markup(chat_id=chat_id, message_id=..., reply_markup=None)` (swallowing `TelegramBadRequest` — the message may already be edited, deleted, or too old to touch) before forgetting it either way. Only one id is ever tracked at a time: a chat has at most one live set of buttons pending a tap, since sending a new buttoned message (or a command clearing the old one) always supersedes whatever was there before. Takes `bot`/`chat_id` as plain values, not a `Message` (an earlier version did take `message: Message` directly, reading `message.bot`/`message.chat.id` off it) — every command handler has a real incoming `Message` to pull those from, but `wiederholen.bot.reminder`'s background sweep (see "Reminders" above) has neither an incoming update nor a `Message` of its own, only the `Bot` and `chat_id` it already looked up, so the primitive values are what the function actually needs either way.

Every message sent with an inline keyboard calls `remember_buttoned_message()` right after: `command_wiederholen`'s and `_respond_with_next_exercise()`'s `nothing_due_text`+study-more-button replies, `handle_answer()`'s explanation (only when it actually attaches a recall/next button — the required-recall path attaches none), `handle_recall()`'s correct/wrong replies, `command_reset`'s confirm/cancel prompt, `handle_reset_confirm()`'s done message, `command_progress`'s reply (see below), and `_remind_chat()`'s reminder message (see "Reminders" above). Every one of the four command entry points (`command_wiederholen`, `command_progress`, `command_reset`, `command_language`) calls `clear_stale_buttons(message.bot, message.chat.id, state)` as its very first action, before anything else; `_remind_chat()` calls the same function (via its own `FSMContext`, not a `Message`) right before sending, since unlike a command it's a conditional background action, not something to do unconditionally on every sweep. The callback handlers that clear their own button directly and attach nothing new (`_respond_with_next_exercise()`'s exercise-found branch, `handle_recall_request()`, `handle_reset_cancel()`) call `forget_buttoned_message()` right after, so the tracked id doesn't linger stale once its message no longer has a keyboard — `_respond_with_next_exercise()`'s exercise-*not*-found branch and `handle_reset_confirm()` instead call `remember_buttoned_message()`, since each attaches a fresh button of its own (a study-more button, a next-exercise button — see below) that supersedes rather than clears. `handle_reset_confirm()`/`handle_reset_cancel()` also pass `reply_markup=` explicitly to their `edit_text()` calls (`make_next_button(locale)`/`None` respectively) rather than omitting it, since editing a message's text alone doesn't implicitly drop its existing inline keyboard.

`command_progress`'s reply and `handle_reset_confirm()`'s "Прогресс сброшен" reply both carry their own `NEXT_EXERCISE` button (`make_next_button(locale)`, promoted from `wiederholen.py`'s private `_make_next_button` to a plain module-level function once other command modules needed to import it too) — since both already strip or replace whatever button was there before, showing a fresh one lets a learner jump straight back into practicing without a separate `/wiederholen`. `handle_next_exercise()`'s callback handler needs no change to support either: it isn't state- or origin-aware, so a tap works identically regardless of which command's message the button was attached to, and the tap-cleanup/re-remember machinery above already covers it like any other buttoned message.

`message.bot` is typed `Bot | None` by aiogram (bound lazily when a real update is dispatched) — `clear_stale_buttons(bot: Bot | None, ...)` asserts it's set rather than threading an optional through, same as the codebase's other `assert x is not None` narrowing (e.g. `Tutor.request_recall()`'s `last_exercise` check); `_remind_chat()` passes its own always-real `bot: Bot` straight through, so the assert is a no-op there. Tests need a realistic `SendMessage` response to exercise any of this: `tests/plugins/aiogram.py`'s `feed_raw_update` fixture used to mock `session.make_request` to always return bare `True`, which is fine for every method whose result nothing reads, but a message-id-tracking feature needs the actual assigned id — it now returns a synthetic `Message` (an incrementing `message_id` starting at 1000, plus `date`/`chat`) specifically for `SendMessage` calls, and keeps returning `True` for everything else. `tests/bot/test_reminder.py` needs the same treatment for the same reason, but can't reuse `feed_raw_update` (there's no incoming update to feed — `tick()` is called directly): its own `mock_request` side effect builds an equivalent synthetic `Message` for `SendMessage` calls and `True` for everything else (`edit_message_reply_markup` included), mirroring `feed_raw_update`'s fixture rather than importing it.

## AI-generated exercises

MVP preview step for a possible AI-personalized-exercises freemium feature (GitHub issue #122): an `/ai` toggle, gated behind the `ai_exercises` feature flag (see "Feature flags" above) and invisible to everyone else, switches a chat between the normal exercise flow and one where `question`/`explanation` are generated on the fly by an LLM instead of coming from `exercises.yaml`.

`wiederholen.school.authoring.generate_shadow_exercise(client, exercise, course, *, authoring_guide=None) -> Exercise` takes a real `Exercise` already selected by `Tutor.next_exercise()` and returns a "shadow" copy — same `word`/`topic`/`answer`/`distractors`/`recalls`, AI-written `question`/`explanation` — via `dataclasses.replace(exercise, question=..., explanation=..., ...)` (`Exercise` is a frozen dataclass, so this is the natural way to get a modified copy, and `__post_init__` validates the result for free — e.g. that `explanation` has both `ru`/`en` keys). Keeping everything except the wording untouched means correctness (does the answer fit, are the distractors actually wrong) is guaranteed by construction, not by trusting the model's German grammar. This module is the only place in the codebase that calls out to an LLM, and lives as a flat module, a sibling of `tutoring` under `wiederholen.school` rather than inside `tutoring` specifically so `Tutor`/`StudentRecord` never gain a network dependency (see "Key modules" above) — `session.py`/`student_record.py` don't import it, and nothing about scheduling changes: `check_answer()` only ever reads `word`/`topic`/`answer` off whatever `Exercise` it's given, never `question`, so a shadow exercise flows through `check_answer()`/`request_recall()` identically to a real one once it's in `shown_exercise` state.

`description` (the `preposition_meaning`-style disambiguating translation of the target sentence, shown before answering — see the content repo's own authoring guide) is regenerated too, but only conditionally: it's carried over into `dataclasses.replace()` only when `exercise.description is not None`, and the prompt only asks for a replacement (and the tool schema only requires one) in that case. This isn't optional polish — it was a real bug caught from a live test: `question`/`explanation` used to be the only fields replaced, so a `preposition_meaning` exercise's `description` kept describing the *original* sentence's meaning after the model wrote a brand-new one (observed in production: a new question about apples coming from the garden, paired with a leftover description translating "the table is made of wood") — exactly the mismatch a description exists to prevent in the first place. A topic whose exercises never carry a `description` (the vast majority) is unaffected either way, since `exercise.description is None` for them and the field is never mentioned to the model at all.

The prompt sent to the model (Anthropic Messages API, `AsyncAnthropic`, model pinned to `claude-haiku-4-5-20251001` via the `MODEL` constant) has two parts: an optional cached system block — the full "Exercises" section of the content repo's own `CLAUDE.md` authoring guide, if `authoring_guide` is provided, marked `cache_control: {"type": "ephemeral"}` so repeated calls within a testing session mostly hit Anthropic's prompt cache instead of reprocessing the whole guide each time — and a user message with up to three few-shot examples of real `question`s sharing the target exercise's `topic` (`course.exercises` filtered by topic, excluding the target itself), plus the target's own `word`/`topic`/`answer`/`distractors`. The model is forced to respond via tool use (`tool_choice={"type": "tool", "name": "submit_shadow_exercise"}`) with a `{question: str, explanation: {ru: str, en: str}}` schema, rather than parsing free text — `generate_shadow_exercise()` pulls the `ToolUseBlock` out of the response, validates its `input` shape, and raises `AIGenerationError` (defined alongside it) for anything that goes wrong: the API call itself failing, no tool-use block in the response, missing/wrong-typed fields, or an `explanation` that fails `Exercise.__post_init__`'s own validation. There's no fallback to the real exercise on failure anywhere — `AIGenerationError` always surfaces as `locale.ai_generation_failed` to the learner, deliberately: this is a testing tool for one person, so a silent fallback would risk masking a broken integration behind human-authored questions that look perfectly normal; a visible failure is what lets a tester actually notice and either retry or turn `/ai` back off.

Both the Anthropic client and the guide text are optional, loaded once at startup by `wiederholen.bot.bootstrap.load_anthropic_client()`/`load_authoring_guide()` and threaded through `dispatcher.start_polling()` as `anthropic_client`/`authoring_guide` workflow data, the same mechanism `course`/`feature_flags` already use. Neither is required the way `BOT_TOKEN` is: `ANTHROPIC_API_KEY` unset means `load_anthropic_client()` returns `None` rather than failing startup (only the one flag-gated test chat ever needs it), and `AUTHORING_GUIDE_PATH` unset means `load_authoring_guide()` returns `None` and generation just runs on few-shot examples alone (same "absence means the feature is off" pattern as `topics.yaml`).

`command_ai` (`wiederholen.bot.commands.ai`) is a bare toggle, no arguments, mirroring `/language`'s own shape: reads `ai_mode` out of FSM state as a plain top-level key (like `language`, not nested in `student_record`, so it survives `/reset`), flips it, and replies with `locale.ai_mode_on`/`ai_mode_off`. It no-ops entirely — no reply, no state change — for any chat `has_feature(feature_flags or {}, "ai_exercises", ...)` doesn't cover, the same invisible-unless-flagged shape `command_wiederholen`'s own flag check point uses; like the other four command entry points, it calls `clear_stale_buttons()` first.

`ai_mode` is meant to stay on for a whole session, not just the one exercise it was toggled before — but `handle_answer()`/`handle_recall()` both read `state_data` and immediately call `state.clear()` (wiping the entire FSM data dict, `ai_mode` included) before selectively restoring the handful of keys they still need, and `_start_recall()` does its own separate `state.update_data()` call for the required-recall path. Each of these four `update_data()` call sites (`handle_answer()`'s non-required branch, `handle_recall()`, and both of `_start_recall()`'s callers — `handle_answer()`'s required-recall branch and `handle_recall_request()`) now explicitly re-adds `ai_mode` — read from `state_data` *before* the `clear()` in the first two cases — alongside the keys they already restored; `_start_recall()` itself takes `ai_mode` as a keyword-only parameter for this rather than reaching into `self`/state on its own, matching how it already receives `language`/`student_record` as plain parameters instead of re-reading state. Missing this (caught from a real user report) meant AI mode silently reverted to off after exactly one exercise — since nothing surfaced the flag flipping back, a tester would just see human-authored questions again and have no idea why.

Generation is further scoped **per topic**, not just per chat: `Course.ai_generatable_topics: frozenset[str]` (parsed from `topics.yaml`'s new per-source `ai_generation: true` key, alongside `chains`/`gates`/`chains_by_answer`/`instruction` — same opt-in-by-absence shape, a topic with no entry or `ai_generation` unset/false is simply not eligible) exists because the "swap `question`/`explanation`, leave everything else untouched" correctness argument only holds for topics whose `answer` is grammatically independent of the exact sentence wording. It breaks down for topics where the question's *exact form* encodes part of the answer: `partizip_ii`/`praeteritum`'s `question` is a fixed `"verb → form"` template, not a sentence, so there's nothing meaningful to rewrite; `konjunktion_wortstellung`/`nebensatzkonjunktion_wortstellung` has an `Exercise.word_bank` that `answer` is a specific reordering of (see below) — a rewritten sentence with different words would leave the old `word_bank`/`answer` matching nothing; `praesens_vokalwechsel`'s `answer` depends on which subject (`du`/`er`-`sie`-`es`) the sentence uses — a model free to pick a different subject while rewriting could produce a sentence whose grammatically correct answer no longer matches the untouched `answer` it's paired with. Both `command_wiederholen` and `_respond_with_next_exercise()` compute this per-exercise, after `next_exercise()` has actually picked one (topic isn't known any earlier): `ai_mode = ai_mode and exercise.topic in course.ai_generatable_topics` — reusing the `ai_mode` name for the narrowed, per-exercise value rather than introducing a second variable, since nothing downstream in either function needs the raw chat-level toggle separately. A topic outside the allowlist behaves exactly as if `ai_mode` were off for that one exercise: the real `question`/`explanation` show through, no `🤖` marker, no API call — not an error, since this is a known, static scope limit rather than a runtime failure.

`_apply_ai_mode()` (`wiederholen.bot.commands.wiederholen`) is the shared decision point both `command_wiederholen` and `_respond_with_next_exercise()` (so both `handle_next_exercise` and `handle_study_more`, which share it) call right after `tutor.next_exercise()` finds a real exercise: if `ai_mode` is off, the exercise passes through untouched; if it's on, it calls `generate_shadow_exercise()` and returns the shadow — or `None`, both when `anthropic_client` is `None` (flag on but not configured) and when generation raises `AIGenerationError`, collapsing both failure modes into one signal the caller reacts to identically (show `locale.ai_generation_failed`, leave FSM state untouched, same as the existing "nothing due" early-return shape). `next_exercise()` itself does no student_record writes (confirmed: no `schedule_pair()`/`_get_or_create_schedule_entry()` calls anywhere in it), so picking an exercise and then bailing out for an AI failure has nothing to roll back.

`_format_question()` takes an `is_ai_generated` keyword-only flag (default `False`) that prefixes the rendered text with `🤖 ` ahead of the `❓` question line — both call sites already have the `ai_mode` boolean in hand (the one `_apply_ai_mode()` was just called with) and pass it straight through, so a shadow exercise is visually distinguishable from a real one at a glance, since nothing else about the message (buttons, reply keyboard, `💭`/`ℹ️` lines) differs between the two.

`Exercise.word_bank: list[str] | None` (`wiederholen.school.curriculum`) is the structured word-order data for `konjunktion_wortstellung`/`nebensatzkonjunktion_wortstellung` exercises: `answer`'s own words, grouped into meaningful phrase chunks (e.g. `"in Hamburg"` stays one chunk, not two — confirmed against the real content data, true for the large majority of these exercises) in the *correct*, unscrambled order. `__post_init__` validates `" ".join(word_bank) == answer` when set, the same kind of authoring-drift check `answer`-in-`distractors`/`explanation`/`description` keys already get. This replaced an earlier design (issue #191) where the scrambled hint was hand-authored prose baked directly into `question` (`'...sondern ___. (in Hamburg / wohnt / sie)'`) — no single source of truth, kept in sync with `answer` by hand, with nothing to validate it. `question` no longer carries this parenthetical at all once an exercise has `word_bank`; both frontends reconstruct it fresh instead: `curriculum.shuffle_word_bank(word_bank) -> list[str]` is one shared shuffle-with-reshuffle-if-unchanged implementation (reshuffles if `shuffle()` happens to land back on the original order — real for a short sentence, and the learner should never be handed an already-solved bank; a single-chunk `word_bank` has no other permutation to land on, so it's returned as-is instead of looping forever) that both `wiederholen.bot` (re-inserts the shuffled chunks as a `" (a / b / c)"` parenthetical after the question, in `_format_question()` — reproducing exactly the old visual shape, just computed fresh on every render instead of frozen at authoring time) and `wiederholen.web` (renders them as tap-to-arrange tiles, see below) call rather than each keeping its own copy. `word_bank` truthiness is the only signal either frontend needs — no separate `topics.yaml` flag exists for this (an earlier draft had one, `Course.word_order_topics`; dropped once `word_bank` itself became the self-describing signal, the same convention `choices: null` already uses for a typed-input exercise). `Tutor` never touches this field — deciding *how to render* an exercise stays a frontend concern, not a scheduling one.

## Grammar-class hints

`Exercise.grammar_classes: list[str] | None` (`wiederholen.school.curriculum`) tags a word with an opaque grammatical-behavior class for its topic — an Ablaut vowel-pattern like `e-a-o` for `partizip_ii`/`praeteritum`, or a preposition+case combo like `an+Akk` for `verb_preposition_case` — same treatment as `word`/`topic`: pure string equality, no meaning baked in here, content authors choose the values (immer-wiederholen#195). An exercise can carry more than one class at once (a narrow one and a broad one), hence a list, not a single value. `__post_init__` rejects an empty list the same way `Recall.answer` rejects one — `None` (the field's default) is the "no classes" case, not `[]`.

Named `grammar_classes`, not the field's original `hint_groups`, or the intermediate `similarity_groups`/`pattern_groups`/`pattern_tags` tried along the way: "hint" collided with the already-existing `Recall.hint` (a different field, a per-recall textual clue, not this one); "similarity"/"pattern" were both too vague or, worse, actively misleading for one of the two planned uses — a shared preposition+case government requirement isn't a repeating *pattern* the way an Ablaut vowel shift is, it's a categorical fact every member of the class shares verbatim, nothing to reapply. "Class" is the one noun that reads naturally for both without implying a specific kind of regularity — and it's also the word the content side reached for unprompted when describing its own data (immer-wiederholen-de#28's "Ablaut-классы"/"Ablaut classes").

`Tutor.get_hint(exercise) -> str | None` (`wiederholen.school.tutoring.session`) is the one method reading this field: finds other exercises of the same `topic` whose `grammar_classes` overlaps `exercise`'s own, excluding `exercise.word` itself, then narrows to candidates this learner has a *durable* hold on — `StudentRecord.get_repetition_interval(candidate_word, exercise.topic) > 1`, not "ever answered correctly": `repetition_interval` resets to `0` both on a wrong answer and on a pair's own first-ever answer regardless of correctness (see `docs/repetition-schedule.md`), so `0` alone can't tell those two apart, and `> 1` requires at least one confirmed doubling past the first answer — a better anchor-quality bar anyway than "got it right once" would be. Among qualifying candidates it returns the one with the highest `repetition_interval` (the most durably remembered, the best possible anchor), ties broken at random — free to compute once the filter above already needs every candidate's interval, so there's no reason to settle for a random pick instead. Read-only, like `progress()` — no student_record writes. Returns just the bare candidate word, not a dataclass or the candidate `Exercise` itself: a candidate `Exercise` would be type-identical to whatever `next_exercise()` returns and risk being mistaken for one (fed into `check_answer()`, stored as `shown_exercise`), and once the render decision below dropped showing the candidate's own `answer`, there was nothing left needing a second field to justify a wrapper type — a bare `tuple[str, str]` would have been the alternative for that case, but two same-typed fields with no type-level way to tell them apart is exactly what a wrapper type earns its keep against.

Deliberately doesn't render the candidate's own `answer` (`"Похоже на: {word} ({answer})"`, an earlier draft) — the two phases this powers aren't symmetric here: showing an Ablaut anchor's exact forms doesn't hand over much, since the target word's own stem consonants differ (knowing `singen → sang` doesn't give you `finden → fand`) and the learner still has to reapply the vowel shift themselves; but for a government class, the anchor's value *is* the answer verbatim — every member of an `an+Akk` class takes exactly `an+Akk` — so showing it outright would just hand over the answer instead of prompting recall. Naming the anchor alone (`Locale.grammar_class_hint`, `"Так же, как и у {word}"`/`"Same as for {word}"`) is the one phrasing that works for both without spoiling the government case, and doubles as retrieval practice for the anchor itself.

Rendered in `_format_question()` behind a `<tg-spoiler>` tag (`🔍 <tg-spoiler>{hint text}</tg-spoiler>`) — opt-in, tap-to-reveal, rather than a separate button or a hint gated to after a wrong answer (both considered; the latter was dropped since a wrong answer already reveals the correct answer directly, so a same-turn "similar to" hint would add nothing there). This is the first message `_format_question()` sends with `parse_mode="HTML"` — every other piece it interpolates (`question`, the `word_bank` parenthetical, `description`, the topic instruction) now goes through `html.escape()` too, not just the hint text, since authored content containing `<`/`>`/`&` would otherwise break the markup instead of rendering as plain text the way it used to before this field existed. Both `command_wiederholen` and `_respond_with_next_exercise()` call `tutor.get_hint(exercise)` right after `_apply_ai_mode()` resolves the exercise actually being shown — `grammar_classes` isn't one of the fields `generate_shadow_exercise()` rewrites, so it survives onto a shadow exercise unchanged and the hint computes the same way regardless of AI mode.

Bot-only for now, no per-topic allowlist the way `ai_generatable_topics` needs one: `grammar_classes` being unset is already the per-exercise opt-in, and nothing here rewrites `question`/`answer` the way AI generation does, so there's no analogous correctness risk to scope around. `wiederholen.web` doesn't read this field yet — a follow-up, mirroring how `/ai` shipped bot-only first (see above).

## Telegram login

`wiederholen.web`'s one shared cookie slot (`_student_id_from_request()`/`_remember_student_id()`/`_remember_browser_login()` in `app.py`) carries two different kinds of value, disambiguated by a prefix check: an anonymous `WebStudentID`'s own `web:` token (see above), or a `browser:{token}` value minted by `telegram_login_callback()` below. Deliberately not `student:{student_id}` (an earlier version of this): a logged-in cookie never carries the real `student_id` at all, only an opaque per-browser credential resolved through `StudentIdentityStore` the same way a Telegram `chat_id` is — `"browser"` is a second `AuthProvider` alongside `"telegram"`, added for exactly this, and `StudentIdentityStore.resolve_student_id(provider, identifier) -> StudentID | None` is a resolve-*only* sibling to `resolve_or_create_student_id()` (same `_get()` primitive underneath, just never falling through to `_create_if_absent()`) added alongside it — a `browser:` token existing at all already implies a real login happened somewhere to link it, so minting a fresh student on a miss would be wrong the way it isn't for `"telegram"`. This is the same account/credential split "Student identity" draws for every other provider: the cookie in the browser is a credential, never the account id itself, so a compromised or leaked cookie value doesn't hand over the permanent `student_id` directly, and a future "log out this browser" flow would just be `link_identity`'s row for `("browser", token)` going away, no `student_id` rotation needed. `telegram_login_callback()`/`_remember_browser_login()` always mints a brand-new `secrets.token_urlsafe(32)` and `link_identity()`s it to the resolved `student_id` — never reuses whatever `browser:` token the incoming request already carried, since that token might already be linked to a *different* student (a previous login, on a shared or reused browser) and `link_identity()` raises `IdentityAlreadyLinkedError` rather than silently reassigning it. `_student_id_from_request()` checks for the `browser:` prefix *before* falling through to `WebStudentID.validate()`, and resolves the token via `resolve_student_id()` — a miss (stale store, tampered value) falls through to a fresh anonymous `WebStudentID` exactly like a foreign/garbage `web:`-shaped cookie already does, rather than either trusting it as a literal id or, worse, minting a phantom new account for it. This tagging is deliberately not "anything that isn't `web:`-prefixed is a real login" — that was tried first and reverted (`test_next_exercise_treats_a_foreign_cookie_as_a_new_visitor` catches exactly this): it would blindly trust *any* foreign or garbage cookie value as a legitimate `StudentID`, not just genuine ones this module minted itself.

`GET /api/auth/telegram/callback` is a sixth endpoint, the target of a [Telegram Login Widget](https://core.telegram.org/widgets/login) button (see `widget.js` below) — deliberately not OIDC/OAuth: Telegram has no real standards-based identity provider, just this one bespoke, redirect-based HMAC scheme (`wiederholen/web/telegram_login.py`'s `validate_telegram_login()`), itself a different scheme again from a Mini App's own `initData`, which this codebase doesn't implement. `hash = HMAC-SHA256(data_check_string, SHA256(BOT_TOKEN))`, `data_check_string` being every other field sorted and joined `key=value` with `\n` — `validate_telegram_login()` raises `InvalidTelegramLoginError` for a bad signature *or* an `auth_date` older than a day (stale/replayed callback URLs, e.g. one saved in browser history). `BOT_TOKEN` is why `wiederholen.web` needs it at all now (`load_bot_token()`, required, no fallback, same as `wiederholen.bot`'s own) — not to call the Bot API, just to check this one signature.

On success, `telegram_login_callback()` calls the exact same `StudentIdentityStore.resolve_or_create_student_id("telegram", str(telegram_user_id))` `wiederholen.bot` calls for every message — this is the entire point: a learner who's chatted with the bot and then logs into the web app with the same Telegram account lands on the same `student_id`, same progress, no separate account. `return_to` (a query param the widget adds itself, *not* one of Telegram's own signed fields — popped off the payload before `validate_telegram_login()` ever sees it, or its mere presence would change the `data_check_string` Telegram itself never signed over) lets the redirect land back on whichever page the login button was actually clicked from, not always the API's own root — `_safe_redirect_target()` only honors it if it's a same-origin relative path (`/...`, explicitly rejecting the `//host/...` protocol-relative form, a real open-redirect vector that passes a naive `startswith("/")` check) or an absolute URL whose origin is already in `WEB_ALLOWED_ORIGINS`; anything else falls back to `/` rather than sending a visitor to an attacker-chosen destination reflected straight off their own request.

`wiederholen/web/static/widget.js`'s `<german-exercise-widget>` gains two attributes for this, off by default like `recall`: a bare `login`, plus `telegram-bot="BotUsername"` naming which bot (the component has no single bot baked in). `_renderLoginButton()` constructs Telegram's own `<script data-telegram-login=... data-auth-url=...>` via `createElement()`/`setAttribute()`, not an HTML string — a `<script>` tag inserted via `innerHTML`/`insertAdjacentHTML` never executes, by design, in every browser. This is also why `_render()` — previously the single "wipe the whole shadow root and rebuild" entry point — now only replaces `.deck`'s own contents: `_render()` runs on *every* exercise (a fresh question, a result, an error), and re-running `_renderLoginButton()` that often would re-fetch Telegram's widget script and flicker the button on every single interaction. `connectedCallback()` now builds a small persistent shell once (`<style>` + an empty `[data-login-container]`) before ever calling `_render()`, and `_renderLoginButton()` renders into that container exactly once per connection — `_render()` only ever touches its own `.deck` sibling from then on. No client-side "am I already logged in" check gates the button itself: clicking it while already logged in just re-resolves the same `student_id`, which is harmless, so simplicity won over hiding a button that's still safe to click.

The standalone app (`index.html`) is the one place actually setting `login`+`telegram-bot="ImmerWiederholenBot"` today, same bot-parity reasoning as its own `recall` attribute — a landing page's embedded widget could opt in too, but only on a domain actually registered for this bot via BotFather's `/setdomain` (Telegram ties the whole widget to one specific domain; there's no way to register several).

`create_app()` also registers `litestar.plugins.opentelemetry.OpenTelemetryPlugin(OpenTelemetryConfig())` — real auto-instrumentation (`opentelemetry-instrumentation-asgi` underneath, the same kind of third-party package `instrument_redis()`'s `RedisInstrumentor` is, not a hand-rolled equivalent of `wiederholen.bot.tracing.TracingMiddleware`) that wraps every request in a server span. Without it, every Redis call `next_exercise()`/`check_answer()` makes via `student_record_book`/`session_store` would show up as its own orphan root span instead of grouped under the request that made it — the same problem `TracingMiddleware`/`reminder.py`'s hand-rolled spans solve for their own processes (see "Tracing" above). No explicit `tracer_provider` passed to `OpenTelemetryConfig()`: like `default_tracer` elsewhere, it resolves whatever the current global provider is lazily, so this is a safe no-op until `wiederholen.web.__main__.main()`'s own `configure_tracing()` call actually installs one.

Testing `wiederholen.web` needs `litestar.testing.AsyncTestClient`, not the sync `TestClient`: the sync client serves the ASGI app through an `anyio` portal running in its own thread with its own event loop, and a Redis client whose connection pool already made contact from the outer test's loop can't be reused from a different one (`RuntimeError: ... attached to a different loop`). `tests/web/test_app.py`'s `web_app_factory` fixture depends on the `student_record_book`/`web_session_store`/`student_identity_store` fixtures purely to get their DBs flushed before the test, but deliberately builds *fresh* `RedisStudentRecordBook`/`WebSessionStore`/`RedisStudentIdentityStore` instances pointed at the same URLs for the app's own state, so the app's first real Redis command happens from whichever loop actually serves it, not the outer test's. `AsyncTestClient` also needs `base_url="https://..."` (not the default `http://`): a `Secure` cookie is never attached to a plain-`http` request by httpx's cookie jar, which would otherwise make every cookie silently vanish between requests in a test — same as a real browser would refuse to send it back over plain HTTP.
