# immer-wiederholen

Telegram bot for practicing German with multiple choice questions (aiogram, Python). Exercises and topic relations are loaded at startup from the directory set by `COURSE_PATH` env var (default: `data`) — `{COURSE_PATH}/exercises.yaml` and `{COURSE_PATH}/topics.yaml`. Bot commands: `/start`, `/wiederholen` (show a exercise with answer options), `/progress` (today's remaining/new-today/answered-today counts plus a learning/mastered breakdown by word), `/language` (toggle ru/en), `/reset` (wipe the repetition schedule and today's answer stats after an inline confirm/cancel prompt).

`data/` is gitignored and populated locally with `exercises.yaml` (the exercise database) from outside this repo. Each `Exercise` has a `word` (the specific vocabulary item it drills, e.g. a verb like `sprechen`) and a `topic` (the grammar aspect being drilled, e.g. `partizip_ii`, `preteritum`, `government`) — `topic` is a free-form string (not a fixed enum), so new topics can be introduced without needing a code change in this repo.

## Key modules

Three top-level packages: `wiederholen.school` — everything about learning, transport-agnostic, shared by every frontend — and two delivery mechanisms that depend on `school` but never the other way around: `wiederholen.bot` (Telegram, aiogram) and `wiederholen.web` (a widget embeddable on a landing page, see "Web frontend" below).

- `wiederholen.school.curriculum` — `Exercise`/`Recall`/`Topic`, `Course` — the loaded exercises + `word_chained_topics`/`answer_chained_topics` (see below). The content model: what's being taught, not how it's scheduled or authored. Both `tutoring` and `authoring` depend on it as equal siblings, neither depends on the other through it.
- `wiederholen.school.tutoring` — the repetition-scheduling engine specifically (not the whole learning domain — that's `school`): `student_record` (`StudentRecord` — per-user persisted schedule state), `session` (`Mark`/`Progress`, `Tutor` — date-based repetition scheduling for one user's student_record, constructed as `Tutor(course, student_record)`; also owns the reminder decision, see "Reminders" below), `selection` (`SelectablePairs` — `next_exercise()`'s word/topic selection engine, factored out because its logic is entirely pairs-derived and needs no `Tutor`/`StudentRecord` state of its own), `events` (`RecallMode`, `ExerciseAnswered`/`TopicUnlocked`/`NoExerciseAvailable`/`TutoringEvent` — see "Tutoring events" below). The package's `__init__.py` re-exports all of these, so callers just do `from wiederholen.school.tutoring import ...`. Imports nothing beyond the standard library, `wiederholen.school.curriculum`, and its own sibling modules — no infra, no network — which is what keeps `Tutor`/`StudentRecord` testable without mocking anything external.
- `wiederholen.school.i18n` — supported languages (`Language` type, `LANGUAGES` set)
- `wiederholen.school.student_record_book` — `StudentRecordBook`/`RedisStudentRecordBook` (see "Persistence" below); transport-agnostic storage, a sibling of `tutoring`/`authoring`, not a dependency of either
- `wiederholen.school.authoring` — AI-generated "shadow" exercises (see "AI-generated exercises" below); the one module in the codebase that talks to an LLM, a flat module (not a package — there's only ever been the one file) deliberately a sibling of `tutoring`, not inside it, for the reason above; it depends on `wiederholen.school.curriculum` directly, not on `tutoring`, since all it actually needs is the content model
- `wiederholen.school.__init__` aggregates the public API of all of the above, mirroring `tutoring`'s own `__init__.py` one level up — `wiederholen.bot` imports everything it needs school-side with `from wiederholen.school import ...`
- `wiederholen.bot` — Telegram bot implementation (aiogram); each command lives in its own module under `wiederholen.bot.commands`. `wiederholen.bot.telegram_student_id.TelegramStudentID` encodes/decodes the `StudentID` this bot addresses `StudentRecordBook` with (see "Persistence" below) — deciding the id *scheme* for one particular frontend is transport-specific, so it lives here, not in `wiederholen.school`.
- `wiederholen.web` — the embeddable-widget backend (Litestar); see "Web frontend" below.

## Repetition schedule

`Tutor` (in `wiederholen.school.tutoring.session`) tracks review scheduling in `student_record["word_schedule"]` — `{"{word}": {"{topic}": {"repetition_interval": int, "due_date": "YYYY-MM-DD"}}}`. A schedule entry is addressed by `word` *and* `topic` (`StudentRecord.get_repetition_interval(word, topic)`), not `word` alone — so e.g. `sprechen`'s government topic (different prepositions) and its `partizip_ii` topic are scheduled independently, while exercises that intentionally share a `word` within the same topic (different prepositions of the same verb) still share one schedule entry.

`next_exercise()` selects in three steps — a **word**, then a **topic** of that word, then a random `Exercise` among the (possibly several) YAML entries sharing that `(word, topic)` pair — so a pair backed by many entries isn't shown more often than one with a single entry, and a word with several simultaneously-due topics isn't over-represented relative to a word with only one. It computes its source pair-sets once and bundles them into a `SelectablePairs` dataclass, whose own `select_word()`/`select_topic()` methods `next_exercise()` calls directly rather than re-deriving anything at separate call sites. `SelectablePairs` is a genuine three-way partition — `due_introduced`, `due_not_introduced`, and `not_scheduled` — split first by whether a pair is due today, then, for due pairs, by introduced status; a not-yet-scheduled pair is always not-introduced too (introducing a pair requires answering it, which requires a schedule entry), so there's no fourth "not scheduled and introduced" cell, and all three fields are mutually exclusive with no overlap. `due_introduced`/`due_not_introduced` deliberately keep "due" in both names — together they're exactly `_get_due_pairs()`'s unfiltered result, so no due pair's identity is hidden behind a differently-scoped word the way an earlier, two-field version's plain `due_pairs` field once hid not-yet-introduced due pairs behind an unrelated `new_pairs` name instead. Call sites that need "everything not introduced" (`select_topic()`'s new-topic fallback) or "everything selectable" (`next_exercise()`'s empty-pool check, `_get_word_tiers()`'s relevant-words set below) go through the `not_introduced`/`all_pairs` properties — computed fresh on each access from `due_introduced`/`due_not_introduced`/`not_scheduled` rather than inline unions repeated at each call site (no leading underscore, unlike `_get_word_tiers()` below, since both are genuinely useful outside the class too: `all_pairs` in particular is `next_exercise()`'s own emptiness check by way of `__bool__`). `SelectablePairs.__bool__` (`bool(self.all_pairs)`) backs `next_exercise()`'s "nothing due or available" check (`if not selectable_pairs: ...`) — a container of pairs being falsy when it holds none follows the same convention as any other empty Python collection, so no separate `is_empty()` method is needed. Neither property is a stored field — each is computed fresh from the three canonical fields on every access, so there's no risk of a cached union going stale relative to them; they're cheap in-memory set unions either way, not student_record re-fetches. `SelectablePairs._get_word_tiers(introduced_words)`, `.select_word(introduced_words, budget, last_pair)`, and `.select_topic(word, last_pair)` (see "Word selection" below) all live on the class for the same reason as the two properties: each one's logic is entirely pairs-derived, needing only a handful of externally-supplied primitives (`introduced_words: set[str]`, `budget: int`, `last_pair: tuple[str, str] | None`) rather than any other `Tutor`/`StudentRecord` state — so `next_exercise()` gathers those few values once (`self._student_record.get_words_already_introduced()`, the budget expression, `self._get_last_pair()`) and passes them in, rather than any of the three methods reaching into `self._student_record` themselves. `_get_word_tiers()` keeps its leading underscore, unlike `select_word()`/`select_topic()`: nothing outside `SelectablePairs` calls it directly, `select_word()` being its only caller. This keeps `SelectablePairs` student_record-agnostic like the rest of it, and leaves `next_exercise()` as a thin orchestrator: construct the partition, bail out early if it's empty, gather the few external inputs, delegate the actual word/topic decisions to the object that holds the data. Deliberately named `SelectablePairs`, not `SelectionPools`: an earlier version had a `_word_selection_pools()` `Tutor` method using "pools" for a different concept (the free/queued/fresh word tiers below) than the pair-set bundle also named "Pools" at the time — reusing the word for both made it ambiguous in the very method that computed both; moving that method onto `SelectablePairs` itself (and renaming it in the process), and later moving `_select_word()`/`_select_topic()` alongside it for the same reason, resolved this for good, since the class name no longer contains "Pools" at all and `Tutor` no longer has its own word/topic-selection methods to potentially collide with it.

**Word selection** (`SelectablePairs.select_word()`) draws from three tiers, computed by `_get_word_tiers(introduced_words)` from the words with something due or available today (`_get_due_pairs(is_introduced=True)`, and `next_exercise()`'s own `_get_available_not_scheduled_pairs() | _get_due_pairs(is_introduced=False)`, collapsed to their words):
- **free** — the word has been actually introduced via *some* topic (`StudentRecord.get_words_already_introduced()`: a word is in the set if any of its topics has `introduced_at` set, regardless of whether that's the same topic that's due/available today — one student_record scan for every word at once, not a per-word lookup) — always in the running, no budget cost. This is what makes a word like `warten` free even when its only progressing topic (`government`, say) isn't due for another week: if it also has a completely untouched topic (`verb_case`), that topic has no schedule entry at all, so it's unconditionally in `_get_available_not_scheduled_pairs()`'s result (see below) — and the word already counts as introduced via `government` regardless, so there's no reason to gate it behind the new-word budget just because one specific topic hasn't been touched yet.
- **queued** — not yet introduced (no topic has `introduced_at`), but already has *some* schedule entry — e.g. a topic expedited via `_expedite_dependent()` (chains/gates, see below) that the learner hasn't actually answered yet. These get first claim on the day's remaining new-word budget, ahead of...
- **fresh** — no schedule entry anywhere: a word never touched or triggered in any way.

`next_exercise()` computes today's remaining budget (see the word cap below) and passes it into `select_word(introduced_words, budget, last_pair)`, which takes as many **queued** words as fit (a random sample if there are more than the budget), then fills any leftover budget with a random sample of **fresh** words. The pick happens uniformly at random over `free ∪ taken_queued ∪ taken_fresh`, minus the last answer's word (repeat-avoidance below). Deliberately not a fixed weight between "due" and "new" (an earlier design, `Tutor.REVIEW_WEIGHT`, worked that way and has been removed): the *fresh* pool is sampled down to the remaining budget *before* the pick, not weighted down after including everything, so a course with hundreds of untouched words never dilutes a handful of free/queued words' chances the way a fixed-ratio weight could be swamped by sheer pool size.

**Topic selection** (`SelectablePairs.select_topic(word, last_pair)`), once a word is chosen: if the word has any topic due today, pick uniformly among *those* (ignoring its new/available topics entirely this round) — a due topic always wins over a new one for the same word, since it has a real deadline and the new one doesn't. Otherwise, pick uniformly among its available-new topics.

Returns `(None, [NoExerciseAvailable(reason="nothing_available")])` if nothing is due or available at all today (e.g. a brand-new gated-only course) — see "Tutoring events" below. A fallback that borrowed an early review here was tried twice (PR #108/#109, and again later) and dropped both times as overcomplicated; reporting the state honestly is simpler.

**Repeat-avoidance.** `check_answer()` records `student_record["last_exercise"]["question"]`, `word`, and `topic` (`record_mark()` replaces the whole `last_exercise` record in one go, see `StudentRecord` docstring-equivalent below; `word`/`topic` are `NotRequired` on `LastExercise` so a record from before they existed stays valid — the exclusions below just no-op until the next answer refreshes it). Three layered exclusions, each falling back to the *unfiltered* candidates if excluding would leave nothing — repeating is then unavoidable, not a bug:
1. `select_word()` excludes the last answer's word from its combined candidate set.
2. `select_topic()` excludes the last answer's topic from its candidate topics, if the chosen word (via tier 1's fallback) happens to be the same word as last time.
3. `next_exercise()` excludes candidates with a matching `question` text, once a `(word, topic)` pair is finally settled on.

This exists because a pair's first answer becomes due again the *same day* (see below) — without word/topic-level exclusion, a freshly-answered word could be picked again as literally the next exercise, and if it has only one YAML entry, the question-level filter alone has nothing to fall back to, so the exact same question could appear twice in a row (observed in production).

On a correct answer the interval doubles (capped at `Tutor.MAX_REPETITION_INTERVAL_DAYS`, currently 60 days); on a wrong answer it resets to `0` (due again immediately). A pair's very first answer is an exception to the "correct → interval days out" half of that rule: `check_answer()` passes `due_interval=0` to `StudentRecord.schedule_pair()` whenever `is_new or not is_correct` — regardless of correctness for the "new" half — so a same-day correct first answer doesn't get pushed a full day out; real interval-based spacing only starts from the second answer onward. `_calc_next_repetition_interval()` sets `repetition_interval` to `0` rather than the doubling formula's own `1` (`max(0 * 2, 1)`) both for this first answer and for any wrong answer (even one that resets an established pair) — in both cases there's no real previous interval to double from, so landing on `1` here would let the *next* correct answer double straight to `2` without the pair ever having been tested at a real 1-day gap, silently emptying the next day's schedule for a learner who works through material steadily (caught from a real user report — see `_calc_next_repetition_interval()` below). Starting at `0` means the following correct answer is the one that doubles cleanly to a real `1`. This due-again-today exception exists specifically so a brand-new learner (or one right after `/reset`) doesn't run out of due material partway through their first day just because everything they answered correctly that day — the earlier fix for the same problem (PR #109/#110's borrow-from-future fallback) was reverted for being overcomplicated; this is the simpler replacement, and it composes for free with the rest of the scheduling machinery since a same-day-due pair is `is_new=False` (`introduced_at` now set) the moment it's set, so it's picked up by the ordinary `_get_due_pairs(is_introduced=True)` path like anything else. The student_record's durability depends on the FSM storage backing it — see below.

`Tutor.__init__` resolves "today" once — `self._today = datetime.now(UTC).date()` — and passes it to `StudentRecord(student_record, today=self._today)`, which it constructs internally; every calendar-day comparison or stamp in either class reads `self._today`/`StudentRecord._today` instead of independently recomputing `datetime.now(UTC).date()`. This isn't about testability — tests already build dates as `datetime.now(UTC).date() + timedelta(...)` in fixtures rather than mocking the clock, and that didn't change. It's a single seam to update if/when "today" ever needs to be resolved per-student (e.g. by timezone) instead of blindly in UTC. Beyond constructing `StudentRecord`, `Tutor` itself no longer touches `self._today` at all — every date computation that used to live on `Tutor` (`_calc_next_repetition_interval()`'s due-date branch, `_expedite_dependent()`, `request_recall()`) now goes through `StudentRecord.schedule_pair()`'s `due_interval` offset instead (see below), so `Tutor` only ever hands `StudentRecord` a relative number of days, never resolves an absolute date itself. A handful of student_record fields are genuinely about *elapsed wall-clock time* rather than *which calendar day it is*, and deliberately keep calling `datetime.now(UTC)` directly rather than going through `self._today` (a `date`, not a `datetime`, has no time-of-day component to compare against): `record_mark()`'s `answered_at` timestamp and `should_remind()`'s 24h inactivity window (see "Reminders" below) — a future per-student timezone wouldn't need to touch either.

Each `_ScheduleEntry` also carries an optional `introduced_at` (`"YYYY-MM-DD"`, `NotRequired` so pre-existing entries created before this field existed stay valid rather than being treated as malformed) — set once, the first time the pair is actually answered via `check_answer()`, and never overwritten after that. It's tracked independently of `due_date`/`repetition_interval` so it can double as a per-pair "when did I start learning this" timestamp for future stats (e.g. which words have been in progress longest), not merely as bookkeeping for the cap below.

To keep review frequency from being diluted as the course grows, word selection also caps how many distinct never-before-answered **words** it surfaces per calendar day — deliberately per word, not per `(word, topic)` pair: a learner who answers `sprechen`'s `government` and then its `partizip_ii` on the same day has only started one new word, not two, so `StudentRecord.get_words_introduced_today()` collapses pairs down to their distinct words before comparing against `Tutor.NEW_WORDS_PER_DAY` (currently 7) — `Tutor._get_words_introduced_today()` intersects its result with `{word for word, _ in self._course_pairs}`, since `StudentRecord` itself is course-agnostic. A word counts only if it's actually been introduced — at least one topic with `introduced_at` set — *and every one of those dates is today*, not merely "any topic introduced today" (a simpler earlier definition): a word introduced days ago whose *other* topic gets its first answer today (e.g. unlocked via chain, itself now `is_new`) doesn't count as newly started today, since the word itself already started earlier — worst/oldest-topic-wins, the same instinct behind `progress()`'s `learning`/`mastered` buckets below. A queued-but-never-answered topic (a real schedule entry from `_expedite_dependent()`, but no `introduced_at` yet) doesn't make a word count either, which needs its own explicit guard: `all()` over an empty "this word's introduced dates" collection is vacuously `True`, so a word with no introduced topics at all would otherwise pass a naive "no date other than today" check — `get_words_introduced_today()` requires that collection to be non-empty first (caught and fixed from a real bug in an earlier version). `next_exercise()`'s budget (`_get_effective_cap() − len(_get_words_introduced_today())`, floored at 0 — `_get_effective_cap()` is `NEW_WORDS_PER_DAY + extra grants`, shared with `grant_new_word_budget()`'s own cap check below) is exactly this cap's remaining headroom for today, and it only ever constrains the **queued**/**fresh** tiers (see above) — a **free** word (already introduced via some topic) never spends budget again, which is what lets the rest of an already-started word's topics, including one just unlocked by a chain, keep flowing even once the word cap is otherwise exhausted.

`StudentRecord.iter_scheduled_pairs(*, only_due_today: bool = False, is_introduced: bool | None = None)` is the single student_record-native iterator most of the above builds on — every `(word, topic)` with a real, *valid* entry, narrowed independently by its two keyword-only filters: `only_due_today` restricts to entries whose `due_date` is today or earlier (default off — no restriction); `introduced` restricts to only introduced (`True`) or only not-yet-introduced (`False`) pairs, `None` (the default) meaning no restriction. It shares its malformed-data handling with `get_words_introduced_today()` and `get_words_already_introduced()` (the **free**-tier check above — every word with *some* topic ever introduced, any day, not just today) via two small private generators, `_iter_valid_scheduled_pairs()` (words) and `_iter_valid_topics()` (topics within one word) — both skip a non-`str` key at their level in addition to `_is_valid_schedule_entry()`'s own pydantic-backed validation, so a malformed word- or topic-level container, or a non-string key at either level, is treated as unscheduled rather than silently kept "scheduled" by mistake. It iterates `word_schedule` (typically much smaller than the whole course) rather than every `(word, topic)` the course defines, since a real entry is required by every use of it either way — callers still have to filter the result against their own known `(word, topic)` pairs, since `word_schedule` can outlive a course change (a word/topic removed from `topics.yaml` stays in a learner's student_record). `Tutor._get_due_pairs(is_introduced: bool | None = None)` is the course-filtered wrapper (`only_due_today=True`, plus the `self._course_pairs` filter): `next_exercise()` and `progress()` call it with `is_introduced=True` for genuinely due, already-introduced reviews; `next_exercise()` also calls it with `is_introduced=False` for the "queued" half of new material (an entry exists, due today, not yet introduced). `iter_scheduled_pairs()` used to also support `is_introduced="today"`, for `_get_words_introduced_today()`'s own use — once that moved to the student_record-native `get_words_introduced_today()` (see above), nothing called it that way anymore, and the option was removed once coverage confirmed it was dead.

`_get_available_not_scheduled_pairs()` computes the **fresh-and-ungated** half — `self._course_pairs.difference(set(self._student_record.iter_scheduled_pairs()))` (every course pair with *no* entry at all) filtered to exclude `topic in self._course.gated_topics`. This can't be a student_record-native call the way `_get_due_pairs()` is: pairs with no entry at all aren't in `word_schedule` for `StudentRecord` to iterate, and whether an entry-less pair is available at all depends on `gated_topics` — a `Course`-level concept `StudentRecord` deliberately doesn't know about (it stays course-agnostic) — so the gating check happens directly here rather than through a course-aware fallback inside `StudentRecord`. A gated topic with no entry at all is locked, not available — it only becomes reachable once `_expedite_dependent()` creates a real entry for it, at which point it shows up via `_get_due_pairs(is_introduced=False)` instead, no longer "untouched." `next_exercise()` unions the two directly (`self._get_available_not_scheduled_pairs() | self._get_due_pairs(is_introduced=False)`) inline, to get the full "new material available today" set its word/topic selection needs — there's no separate named method for that union, since `next_exercise()` is its only caller (an earlier `_get_available_not_introduced_pairs()` wrapper was inlined once that became clear). `check_answer()`'s `is_new` local comes from `record_mark()`'s return value (see below), not a separate lookup — `record_mark()` already has to check the same fact internally to decide whether to stamp `introduced_at`, so handing that answer back avoids computing it twice and, more importantly, avoids an ordering hazard: `record_mark()` stamps `introduced_at` partway through `check_answer()`, so a separate lookup made *after* it runs would silently see the *post*-answer state instead of the pre-answer one `check_answer()`'s `due_interval` decision and the `ExerciseAnswered` event actually need. `SelectablePairs._get_word_tiers()` (which distinguishes the **free**/**queued**/**fresh** tiers, see above) builds `free_words` as `today_relevant_words & introduced_words` (the caller-supplied `StudentRecord.get_words_already_introduced()` result — see "Selectable pairs" above for why it's a parameter rather than a `self._student_record` call) and `queued_words` as `{word for word, _ in self.due_not_introduced} - introduced_words` (a not-yet-introduced entry is always due today, per `_expedite_dependent()`'s own invariant — see below — so "has any entry" and "has a due entry" coincide for these words; this is also why `due_not_introduced` can just be `_get_due_pairs(is_introduced=False)`, computed once in `next_exercise()` rather than re-derived here); `fresh_words` is whatever's left. This replaced an earlier version with two per-word helper methods (`_has_introduced_topic()`/`_has_any_schedule_entry()`, each scanning one word's topics via `get_schedule_entry()` in a loop) once `StudentRecord.get_words_already_introduced()` made a single whole-student_record scan cheaper than a lookup per candidate word. An even earlier version of the introduced-check looked at `repetition_interval == 0` instead, as an indirect proxy for "never actually answered," specifically to tolerate a schedule entry that predates the `introduced_at` field entirely (real `repetition_interval` but no `introduced_at`) without misclassifying it as new. That tolerance was deliberately dropped once there was no such legacy data left to protect against: a pair in that shape is now treated as new, and gets `introduced_at` stamped on its next answer like any other new pair. `_expedite_dependent()` (see chaining below) still creates a schedule entry with `repetition_interval=0` and no `introduced_at` to unlock or advance a chained/gated topic before the learner has ever actually seen it — such a pair must still count as new (its word merely **queued**, not **free**) until it's actually answered, or unlocking it would let its word silently bypass the daily cap. `should_remind()`'s own inline "anything due at all" check (see "Reminders" — deliberately not filtered through the word cap, since it only asks whether *anything* is due, not how much of it the cap would currently let through) builds on `_get_due_pairs()`/`_get_available_not_scheduled_pairs()` — deliberately *not* also unioning in `_get_due_pairs(is_introduced=False)` the way `next_exercise()` does, since that's already a subset of the unfiltered `_get_due_pairs()` the check calls first; checking it again would be redundant, not wrong. If the cap excludes every otherwise-eligible word and nothing else is due, `select_word()` returns `None` and so does `next_exercise()` (paired with `NoExerciseAvailable(reason="daily_cap_reached")` — see "Tutoring events" below, distinct from the `"nothing_available"` reason above); the bot layer (`command_wiederholen`/`handle_next_exercise` in `wiederholen.bot.commands.wiederholen`) shows `locale.nothing_due_text` in that case and leaves the FSM state untouched, rather than setting `UserState.answering`. `StudentRecord.reset_progress(data)` (a `classmethod` — takes the raw student_record dict directly rather than needing an instance, since wiping student_record state this way touches nothing that needs an instance to reach; called directly as `StudentRecord.reset_progress(student_record)` from `/reset`'s handler, not routed through `Tutor`) wipes `word_schedule` (the key lives in `StudentRecord._WORD_SCHEDULE_KEY`) and needs no special-casing to clear `introduced_at` along with it, since it's nested inside each `_ScheduleEntry`. It also clears `today_answers` (`StudentRecord._TODAY_ANSWERS_KEY`) explicitly, a separate top-level key the `word_schedule` wipe doesn't reach on its own: without this, `/progress` would still show the pre-reset `answered_today`/`correct_today` for the rest of the day, silently contradicting what a learner just asked `/reset` to do (caught as a real bug — the schedule wipe alone wasn't enough, and the method was renamed from `reset_schedule` once it started doing more than that).

`check_answer()` calls `StudentRecord.record_mark()` exactly once, right before computing the next repetition — the one place that records "an answer just happened," covering three independent pieces of student_record state in a single call: it replaces the whole `last_exercise` record (question/word/topic/`answered_at`/`is_recall_optional`, see "Repeat-avoidance" above); it updates the self-expiring `today_answers` counter (`AnswerStats` — `{"date": ..., "answered": int, "correct": int}`, read back via `get_answer_stats_today()`, same self-expiring pattern as `new_word_budget` above); and it stamps `introduced_at` on the pair's `_ScheduleEntry` (fetched/created via the private `_get_or_create_schedule_entry(word, topic)`) if it isn't set yet. `record_mark()` derives whether the pair is new by checking that entry's `introduced_at` directly, rather than trusting a caller-supplied flag — it's the one point in `check_answer()`'s call chain where that self-check is still safe, since nothing has touched `introduced_at` yet at that point — and returns `tuple[bool, int | None]`: the `is_new` verdict *and* `prev_repetition_interval`, which `check_answer()` unpacks straight into its own locals (`is_new, prev_repetition_interval = self._student_record.record_mark(...)`). `prev_repetition_interval` is read via `get_repetition_interval(word, topic)` *before* `_get_or_create_schedule_entry(word, topic)` runs — not off the entry `_get_or_create_schedule_entry()` returns — specifically so a genuinely never-scheduled pair reads as `None`, not `0`: reading it off the post-creation entry (an earlier version did this) would return `0` for a brand-new pair — the same `0` a pair that already has an entry (e.g. queued via a chain, `_expedite_dependent()`'s `repetition_interval=0`) but was never answered would report — collapsing "never scheduled at all" and "scheduled but stuck at 0" into one value `_calc_next_repetition_interval()` (see below) needs to tell apart. This is also why `check_answer()` doesn't derive `is_new` itself (see above) — `record_mark()`'s return value already *is* that answer, computed at the one moment it's safe to ask — and why `check_answer()` never needs its own `get_repetition_interval()` call to read `prev_repetition_interval` (for the `ExerciseAnswered` event) either. `progress()`'s `answered_today`/`correct_today` (see below) read `get_answer_stats_today()` directly.

`_calc_next_repetition_interval(*, prev_repetition_interval: int | None, is_answer_correct: bool) -> int` (both keyword-only, matching `record_mark()`/`schedule_pair()`'s own quantity/flag parameters) is a pure function on `Tutor` — no `StudentRecord` access, no mutation, no `self._today` — taking exactly the inputs the interval math needs and returning just the new `repetition_interval`. A wrong answer or a missing `prev_repetition_interval` (`None` — no schedule entry existed before this answer at all) both return `0`: neither has a real previous interval to double from, so there's nothing to distinguish between them. Otherwise it's the normal doubling formula, `min(max(prev_repetition_interval * 2, 1), MAX_REPETITION_INTERVAL_DAYS)` — which also covers `prev_repetition_interval == 0` (an entry existed but was never really spaced, e.g. this pair's own first answer, or one queued-but-unanswered via a chain), landing on `max(0 * 2, 1) == 1`. So a pair's interval sequence across successive correct answers reads `None → 0 → 1 → 2 → 4 → ...`, not `None → 1 → 2 → 4 → ...`; and a wrong answer on an established pair (say, at `30`) resets it to `0`, not `1`, for the same reason — either way, the *next* correct answer is what reaches a real `1`. The extra `0` step means the pair is only ever doubled from an interval it was actually scheduled at, never from a value that was itself just a same-day placeholder (see the due-again-today exception above — the mixup this fixes is a real one: doubling straight from a placeholder `1` on the very next correct answer, if that answer happened the following day, would skip past a real 1-day gap and land the pair 2 days out, leaving nothing due that day for a learner who was working through material one day at a time). It no longer decides *when* the pair is next due (that used to be baked into its `is_new` parameter and a returned `due_date`); `check_answer()` now makes that call itself right at the `schedule_pair()` call site, passing `due_interval=0 if (is_new or not is_correct) else None` alongside `repetition_interval=next_repetition_interval` — collapsing what used to be two return values threaded through an intermediate tuple into one `int` plus one inline expression at the point that actually needs the exception. This replaces an earlier `_schedule_next_repetition()` that fetched the entry itself, read from it, *and* wrote back to it in one method on `Tutor` — `Tutor` never touches a raw `_ScheduleEntry` at all; it only ever passes plain `int`s across the `StudentRecord` boundary (`get_repetition_interval(word, topic) -> int | None` is the read side of that boundary — see below).

`StudentRecord._get_schedule_entry(word, topic) -> _ScheduleEntry | None` is read-only, with no `create_if_missing` — every write goes through a dedicated method instead: `schedule_pair(word, topic, *, repetition_interval, due_interval: int | None = None)` (the private `_get_or_create_schedule_entry(word, topic) -> _ScheduleEntry` fetches-or-creates, then `schedule_pair` overwrites just the two fields it was given, in place — deliberately not replacing the whole entry wholesale, since that would blow away `introduced_at` if `record_mark()` just set it moments earlier in the same `check_answer()` call). `due_interval` is a relative offset — days from `self._today`, resolved to an absolute `due_date` entirely inside `StudentRecord` — not an absolute date, so no caller needs to know or compute "today" itself just to schedule a pair; it defaults to `repetition_interval` when omitted, since that's the ordinary spaced-repetition case (next due date = today + the newly-computed interval), and callers only pass it explicitly to override that default for the "due again today regardless" exceptions (`check_answer()`'s `is_new`/wrong-answer case above; `_expedite_dependent()`'s `repetition_interval=0` call also relies on this default rather than passing `due_interval=0` itself, since `0` is what the default resolves to anyway). `record_mark()` uses the same private helper for its own `introduced_at` stamping. An earlier version instead put an overloaded `create_if_missing: bool` parameter directly on the public `get_schedule_entry()`, `@overload`-typed to `-> ScheduleEntry` when `create_if_missing=True` — every caller that only ever reads now doesn't need to know that parameter exists at all. `_is_valid_schedule_entry()` (used by both the read-only and fetch-or-create paths to validate a raw dict against `_ScheduleEntry`'s shape via pydantic) is typed `-> TypeIs[_ScheduleEntry]`, not plain `bool` — needed once `_get_or_create_schedule_entry()`'s return type tightened to `_ScheduleEntry` (no `| None`): a plain `bool` return gives a type checker nothing to narrow on, so without `TypeIs` the type checker can't see that the entry is guaranteed valid after that check passes (or after the fallback default is substituted in the branch where it doesn't).

`_ScheduleEntry`/`get_schedule_entry()` were both public until every caller turned out to only ever need `repetition_interval`, never `due_date` or `introduced_at` directly — `Tutor.progress()`'s mastered/learning check, `_expedite_dependent()`'s existence check, and `request_recall()`'s halving logic all read `repetition_interval` (or just checked for `None`) and nothing else. Rather than keep exposing the whole entry for that, `get_schedule_entry()` was renamed `_get_schedule_entry()` (private) and `StudentRecord.get_repetition_interval(word, topic) -> int | None` became the sole public read accessor, built on top of it. `ScheduleEntry` itself became `_ScheduleEntry` (private-by-convention) at the same time, since nothing outside `StudentRecord` constructs or destructures one directly anymore. Named to echo `_calc_next_repetition_interval()` (the sibling method that computes this same value on a correct/wrong answer), not `interval` alone (too generic on its own) or `get_interval_days` (redundant once `_ScheduleEntry.repetition_interval`, the field it mirrors, is itself private and no longer a naming anchor external callers need to match).

The word cap can be lifted for the rest of the day on request: when `next_exercise()` returns `None` because the cap (not a genuine lack of due material) excluded everything, the bot shows a "study more" button (`STUDY_MORE` callback data, `wiederholen.bot.commands.wiederholen.handle_study_more`) alongside `locale.nothing_due_text`, both from `command_wiederholen`/`handle_next_exercise` and, once granted, from the shared `_respond_with_next_exercise()` helper if the raised cap still isn't enough. Clicking it calls `Tutor.grant_new_word_budget()`, which reads `StudentRecord.get_new_word_budget()`, checks the cap, and — if still binding — calls `StudentRecord.bump_new_word_budget(Tutor.NEW_WORD_BUDGET_GRANT)` (currently grants 3). That method itself reads the current count, adds the amount, stores the result back as `student_record["new_word_budget"]` (`NewWordBudget` — `{"date": ..., "count": ...}`; named for what it stores — a *count*, not actual word entities, unlike the earlier `ExtraNewWords`/`extra_new_words` this was renamed from), and returns the new total (not currently used by the caller, but there for whoever needs it next). The self-expiring behavior — a grant only counts if its `date` is today, so yesterday's grant, if any, never carries over, no explicit cleanup needed, same pattern as `introduced_at` — lives entirely in `StudentRecord` now: `Tutor` works with plain ints and does no date comparison of its own for this (mirrors `record_mark()`'s `today_answers` handling above — same shape, same reasoning). `Tutor._get_effective_cap()` (`NEW_WORDS_PER_DAY + StudentRecord.get_new_word_budget()`) is this shared expression, factored out once both `grant_new_word_budget()`'s cap check and `next_exercise()`'s budget calculation needed it verbatim. Grants stack with no limit on how many times a learner can click in one day — deliberately: this is an opt-in escape hatch for a learner who explicitly wants more, not something that needs its own throttle. It's stored outside `word_schedule`, and unlike `today_answers` (see above), `StudentRecord.reset_progress()` deliberately leaves it alone — a leftover same-day grant surviving a same-day `/reset` is harmless (the learner already asked for more today, and it doesn't contradict anything `/reset` claims to have done) and it still expires naturally the next day regardless. Telegram keeps a message's inline button clickable indefinitely, so a "study more" button can still be tapped after its message is no longer current — e.g. the next day, once the cap has already reset — and unlike `NEXT_EXERCISE`/`RECALL` (whose handlers have no state that a stale tap could corrupt, they just act on whatever's true *now*), a grant is a stacking mutation, so a stale tap honored blindly would silently raise a day's cap the learner never actually asked to raise that day. `grant_new_word_budget()` guards against this at the source rather than by invalidating the button: it first checks whether today's word count has actually reached `_get_effective_cap()` and does nothing at all — no student_record write — if it hasn't, since that means the cap isn't the thing standing between the learner and more material right now (most likely because a new day reset it). A tap that arrives while the cap is genuinely still binding always goes through, whether that's the button's first day or a later same-day re-tap after actually working through the previous grant.

`request_recall()` follows the same pattern for recall variants: it records `student_record["last_exercise"]["recall_question"]` and reads it back next time to exclude a matching candidate, unless that would leave no candidates. Because `record_mark()` replaces the entire `last_exercise` record on every answer, `recall_question` from a prior episode is simply absent from the new one — no explicit reset needed. This too lives entirely inside `Tutor`/`student_record` — the bot layer (`_start_recall` in `wiederholen.bot.commands.wiederholen`) just calls `tutor.request_recall(exercise)` and doesn't track which variant was shown last.

`progress()` (shown by `/progress`) reports six numbers, none of them a raw `(word, topic)` pair count — the earlier design exposed `total`/`new`/`due` pair counts directly, but `due` conflated genuine overdue reviews with every never-started pair (always "due" by construction, so the number was dominated by backlog size rather than actual today's-workload) and `total`/`new` meant little to a learner who thinks in words, not word+topic pairs:
- `remaining_today` — `len(_get_due_pairs())`, every pair with a real schedule entry that's due today, regardless of introduced status (a due-but-never-introduced pair — e.g. one just expedited via a chain — counts too, same reasoning as `should_remind()`'s check below). Deliberately *not* the same as `next_exercise()`'s full selection pool (`SelectablePairs.all_pairs`): an earlier version of this number also estimated never-touched new material (`_new_remaining_today()`, since removed), but that number was always a bounded *estimate*, never an exact count (a not-yet-started word might cascade into more than one pair once actually answered, via chains, with no way to predict that in advance) — before that, an even earlier version reused the raw eligibility check as a blanket list of every never-touched, non-gated pair in the whole course (issue #119: a learner with ~40 words in progress once saw "290 упражнений" this way). Both were dropped in favor of `remaining_today` meaning exactly one thing — genuinely due reviews, a number a learner can act on and trust — with new-material progress tracked separately by `new_today` below instead of folded into the same figure.
- `new_today` — `len(_get_words_introduced_today())`, how many distinct **words** were actually introduced today (see above — worst/oldest-topic-wins, not merely "any topic introduced today") — matching the word cap it mirrors, not a raw pair count; a "progress so far" counter, complementary to `remaining_today` rather than derived from it.
- `answered_today`/`correct_today` — read straight from `StudentRecord.get_answer_stats_today()`, the self-expiring `today_answers` counter `record_mark()` maintains (see above) — how many times the learner has answered the main exercise today, and how many of those were correct. Counts attempts, not distinct pairs, so it's a different unit from `new_today`: answering the same pair three times today (e.g. wrong, wrong, right) is 3 toward `answered_today` but at most 1 toward `new_today`. Recall answers don't count — same "activity" definition `should_remind()` uses (see "Reminders" below).
- `learning`/`mastered` — bucketed by distinct **word**, not `(word, topic)` pair, since a learner thinks "I'm learning `sprechen`," not "I'm learning `sprechen`'s `government` and separately its `partizip_ii`." A word needs a rule for combining the states of its (possibly several independently-scheduled) topics: `mastered` only if *every* one of the word's topics has `repetition_interval >= MAX_REPETITION_INTERVAL_DAYS`; `learning` if the word has any schedule progress at all but isn't fully mastered yet (worst-topic-wins, not best-topic-wins — knowing a verb's `partizip_ii` well doesn't make the word "mastered" while its `government` is still barely started); a word with no schedule entries for any of its topics is counted in neither bucket (it's not being worked on yet, and unlike the old `new` bucket this is no longer surfaced as its own number).

There's no `total` anymore — it wasn't a number a learner could act on. Read-only: `progress()` never creates or mutates schedule entries, unlike `next_exercise()`/`check_answer()`.

`Course` (in `wiederholen.school.curriculum`) bundles `exercises` with `word_chained_topics: dict[str, list[str]]`, `gated_topics: frozenset[str]`, `answer_chained_topics: dict[str, list[str]]`, and `topic_instructions: dict[str, dict[Language, str]]`, all derived from one gitignored file, `topics.yaml` — its absence means all four are empty, the feature is simply off. `Course.load(path)` is the usual construction path: `Course._load_exercises()`/`Course._load_topics()` are both private staticmethods, `Course.load()` is the intended public entry point. `wiederholen.bot.bootstrap.load_bot_course_and_storage()` calls `Course.load()` with the directory from the `COURSE_PATH` env var (see intro). `Tutor(course, student_record)` reads the first three (`exercises`, `word_chained_topics`, `gated_topics`, `answer_chained_topics`) off the `Course` it's given — `topic_instructions` is a display-only concern the bot layer reads directly, `Tutor` never touches it (see below).

`Course.restricted_to(topics)` returns a narrower `Course` — same `exercises`, filtered down to the given topics — used by `wiederholen.web` to scope a widget to whatever grammar topics its landing page is about (see "Web frontend" below), and available to `wiederholen.bot` too if a similar need ever comes up there, since it's a `wiederholen.school.curriculum` concern, not a web-specific one. `word_chained_topics`/`answer_chained_topics`/`gated_topics`/`topic_instructions`/`ai_generatable_topics` are deliberately left untouched rather than filtered down too: a chain/gate pointing at a topic excluded from this view simply never finds an exercise to expedite — `_expedite_dependent()` already treats "dependent topic has no exercises" as a no-op, the same case a topic with genuinely no exercises in the unrestricted course hits — and the rest are just inert, unused data for a topic that can never appear in this view's `exercises` anyway. The same `student_record` works against either view interchangeably, since schedule entries are keyed by `(word, topic)`, not by which `Course` object selected them — a learner's progress on a topic doesn't disappear just because today's widget doesn't surface it.

`topics.yaml` configures, per **source** topic, four independent things: `chains` (topics whose due date this source expedites once answered, keyed by the source exercise's `word`), `gates` (topics that are *also* gated — locked until this source is answered — as well as expedited via `chains`; `gates` is not a subset you repeat in `chains`, `Course._load_topics()` folds it in automatically), `chains_by_answer` (same expediting effect as `chains`, but the dependent's schedule entry is addressed by the source exercise's `answer` instead of its `word` — for a dependent topic that's about *what the source's answer represents*, not about the source's own word; e.g. `government`'s answer is a preposition like `auf`, and that preposition — not the verb being drilled — is what `preposition_meaning`/`preposition_case` are about), and `instruction` (a `{ru: ..., en: ...}` pair shown to the learner alongside exercises of this topic — see below). `Tutor` sees two separate merged results: `Course.word_chained_topics[source]` is `chains + gates` (deduplicated, order preserved, word-keyed), and `Course.answer_chained_topics[source]` is `chains_by_answer` (answer-keyed) — there's no `gates_by_answer`; an answer-chained dependent topic can still be gated, just via a `gates` entry declared under some other (word-keyed) source, since gating only checks the dependent's *topic name*, never how it was reached. `Course.gated_topics` is the flattened set of every topic that appeared in any source's `gates` list. Keeping `chains`/`gates` independent (rather than deriving "gated" from "appears as a dependent," as an earlier design did) matters for pairs like `partizip_ii`/`preteritum`, where either answered first should expedite the other but neither should be locked from the start — making both mutually gated would deadlock them (neither could ever unlock, since each is waiting on the other). The topic names themselves stay opaque to the code — `topics.yaml` is just data, so the content repo can declare new chains/gates/instructions without a code-repo change, same reasoning as `topic` itself being a free-form string (see intro).

`_format_question()` (`wiederholen.bot.commands.wiederholen`) renders two independent optional lines below the question, neither one a fallback for the other: `exercise.description[language]` (per-exercise context, e.g. a sentence the answer is drawn from) prefixed `💭`, and `course.topic_instructions.get(exercise.topic, {}).get(language)` (per-topic guidance on *how* to answer — e.g. `konjunktion_wortstellung`'s answer requires reordering several given words, not just filling in one, so it needs different guidance than a plain fill-in-the-blank topic) prefixed `ℹ️`. Deliberately no hardcoded default instruction text: a topic with nothing in `topics.yaml` simply shows no instruction line, rather than a generic one that could be wrong for its exercise format — this used to be a single locale-templated string (`Locale.description_prompt`, one fixed "enter the missing word" for every topic with a `description`) which broke down once a topic needing different guidance appeared, so it moved to `topics.yaml` for the same free-form-content reason as `chains`/`gates`.

`check_answer()` calls `_expedite_chained_topics()`, which loops `word_chained_topics.get(exercise.topic, [])` (addressing each dependent entry as `exercise.word`, `dependent_topic`) and `answer_chained_topics.get(exercise.topic, [])` (addressing each dependent entry as `exercise.answer`, `dependent_topic`), both routed through the shared `_expedite_dependent(word, topic)`: if that pair has no schedule entry yet, creates one due *today* (`repetition_interval=0`) — this is what makes a **gated** dependent topic (see below) reachable for the first time, and what gives either side of a *mutual* chain (see below) its one-time initial nudge. If the pair already has an entry, `_expedite_dependent()` now leaves it alone entirely, regardless of its `due_date` or a `(word, topic)` pair with no exercises at all — deliberately: once a dependent has actually been answered (`repetition_interval >= 1`), its own earned schedule is not something an unrelated chain trigger should override. An earlier version *did* pull an existing future `due_date` forward to today unconditionally; for a one-way chain that just made a dependent show up sooner than its own interval called for, but for a **mutual** chain (two topics each chaining to the other, e.g. `partizip_ii`↔`praeteritum`) it meant every correct answer to either topic immediately erased the other's just-earned interval through this same mechanism — trapping both in a permanent due-today loop, since `repetition_interval` kept growing but `due_date` never got the chance to hold (caught from a real user report: stuck re-answering the same word's `partizip_ii`/`praeteritum` pair indefinitely). This runs regardless of whether the answer was correct, and only ever affects *when* a never-yet-answered dependent first becomes eligible — once picked, it goes through the exact same `next_exercise()`/`check_answer()` path as anything else, no separate state.

A topic in `gated_topics` (e.g. `partizip_ii_meaning`, gated behind `partizip_ii`) is locked behind its source, not just expedited: for a `(word, topic)` pair with **no** schedule entry, `_get_available_not_scheduled_pairs()`'s gating filter (`topic not in self._course.gated_topics`, see above) excludes it outright until `_expedite_chained_topics()` actually creates its entry, which only happens once its source has been answered at least once (for that same word) — at which point it has a real entry and shows up via the ordinary due/queued paths like anything else. A fully-gated, never-unlocked course (or a still-locked topic within an otherwise-active one) simply never contributes to any of `SelectablePairs`' three fields, so `next_exercise()` returns `NoExerciseAvailable(reason="nothing_available")` for it exactly like any other empty-pool state — no separate due-date fallback is needed to handle gating as a special case (an earlier `_get_due_date()`-based earliest-due tie-break did exist for this, see "Word selection" above; it's gone now). `progress()`'s `learning`/`mastered` buckets are unaffected by lock state (they only look at whether a word's topics have a schedule entry and their `repetition_interval`, not at due dates); `remaining_today` (via `_get_due_pairs()`, which requires a real entry to begin with) is unaffected too, since a locked pair never has one until unlocked.

## Tutoring events

`check_answer()` returns just `Mark`, and `next_exercise()` returns just `Exercise | None` — neither threads an event list up to a caller. Instead, `wiederholen.school.tutoring.events.emit()` writes directly onto `trace.get_current_span()` — the span `wiederholen.bot.tracing.TracingMiddleware` already opened for the current Telegram update — the moment a meaningful thing happens, from inside `Tutor` itself. `wiederholen.school.tutoring` gaining a dependency on `opentelemetry-api` (not the SDK) for this is a deliberate, narrow exception to the package's own "no infra" rule: the API package is designed to be a safe no-op without a configured provider (`trace.get_current_span()` returns an inert span, and `.add_event()` on it does nothing), unlike a real infra dependency like `redis` or an HTTP client would be — so `Tutor`'s tests still need no mocking for this, and a test that doesn't care about tracing doesn't need to change at all. An earlier design collected `TutoringEvent` dataclasses into a list, returned it up through `check_answer()`/`next_exercise()`'s return signatures, and had the bot layer bridge each one to a span event at every call site (`wiederholen.bot.tracing.record_tutoring_events()`) — dropped once it became clear that bridge was the *only* consumer of that list anywhere in the codebase: nothing in `wiederholen.bot.commands.wiederholen` ever branched on event content (e.g. `NoExerciseAvailable.reason` was never read by the bot layer — the "study more" button shows on `exercise is None` alone), so routing observability through a public return value was pure ceremony for a fact only tracing cared about.

`ExerciseAnswered`, `TopicUnlocked`, `NoExerciseAvailable` (the `TutoringEvent` union) are still plain frozen dataclasses, living in `wiederholen.school.tutoring.events` alongside `emit()` and `RecallMode` — internal to the package now, not part of its public API (`wiederholen.school.tutoring.__init__.py`/`wiederholen.school.__init__.py` no longer export any of the three, or the union type; only `RecallMode` still does, since `Mark.recall`/the bot layer's recall-flow branching both need it). Keeping them as dataclasses rather than inlining `span.add_event()` calls with raw dict literals still matters: deciding *what counts as a meaningful event and when it fires* is domain knowledge (e.g. `ExerciseAnswered.is_new` mirrors the same `is_new` local `check_answer()` already gets back from `record_mark()`, `prev_repetition_interval: int | None` mirrors that same return value's other half — `None` for a pair's very first answer, see above — and `next_repetition_interval` mirrors what `_calc_next_repetition_interval()` already computes; `TopicUnlocked.via` — `"chain"` vs `"gate"`, based on whether `dependent_topic in course.gated_topics` — mirrors the gating rule from the previous section), so each event's shape stays declared once, next to the rule it's describing.

`ExerciseAnswered` is always emitted once per `check_answer()` call. `TopicUnlocked` is emitted once per dependent `_expedite_dependent()` actually creates an entry for (`Tutor._emit_topic_unlocked()` builds the event and emits it in one call — `_expedite_chained_topics()` itself returns nothing now, having no caller left to hand a list to). `NoExerciseAvailable` is emitted once whenever `next_exercise()` is about to return `None`, with a `reason: Literal["nothing_available", "daily_cap_reached"]` distinguishing empty pools from a cap-exhausted pick (see "Word selection" above). `request_recall()` still doesn't emit anything.

`emit()` builds the span attributes itself (`_attributes()`, the same logic the old bot-layer bridge used to own): starts from `dataclasses.asdict(event)` and adjusts two kinds of field that aren't valid span attribute values as-is — `Enum` fields (e.g. `ExerciseAnswered.recall_mode`) are unwrapped to their `.value` first, since an `Enum` instance isn't a valid span attribute type; `None` fields (e.g. `ExerciseAnswered.prev_repetition_interval` for a pair's very first answer, see above) are dropped from the attribute dict entirely rather than sent as-is — unlike an `Enum`, there's no single plain value to unwrap a missing interval to, and passing `None` through isn't a valid span attribute either. Testing this now means constructing a real, recording `TracerProvider`/`InMemorySpanExporter` and reading `span.events` back off it after calling `check_answer()`/`next_exercise()` under `tracer.start_as_current_span(...)` — `tests/school/tutoring/test_tutoring_events.py` does this via the shared `tracer`/`exporter` fixtures (`tests/plugins/tracing.py`, also used by `tests/bot/test_tracing.py`'s own span-content tests) rather than asserting on a returned list, the one real cost of this design (see "Tests" below) — the rest of `Tutor`'s test suite is unaffected, since `add_event()` on the default no-op span (no provider configured) is always safe and silently does nothing.

## Persistence

`wiederholen.school.student_record_book.StudentRecordBook` is an abstract, transport-agnostic store for exactly one thing: the student_record dict `Tutor`/`StudentRecord` operate on, addressed by a plain string `student_id` — `wiederholen.bot.telegram_student_id.TelegramStudentID.encode(chat_id)` for the Telegram bot's message handlers, `TelegramStudentID.encode(callback.from_user.id)` for its callback handlers (the same value in a private chat, which is all this bot has ever supported). A bare `str(chat_id)` would have no way to tell a Telegram-originated id apart from an id another frontend (a future web chat, say) might use for the same shared store — `TelegramStudentID.encode()` tags every Telegram id with a `telegram:` prefix so the two can never collide, and `.decode(student_id)` recovers the `chat_id`, raising `NotATelegramStudentIdError` for a `student_id` that isn't Telegram-shaped at all (see "Reminders" below for the one place that matters: sweeping every student in the store, not just Telegram's own). It has exactly two public members: `check_out(student_id)` and `__aiter__` — no public `close()`, see below. `_get(student_id) -> dict`/`_save(student_id, student_record)` are private abstract primitives — no caller outside the class needs them directly, since `check_out(student_id)` is a concrete `@asynccontextmanager` built on them alone (no subclass needs to override it) that fetches the student_record, yields it for in-place mutation via `Tutor`, and saves it back on exit **only if it actually changed** from a `copy.deepcopy` snapshot taken right after the fetch (plain `!=` on the two dicts — student records are already JSON-safe values, so structural equality is exactly what's wanted, no custom diffing needed). That one rule covers every caller uniformly, with no separate read-only or conditional-save path needed anywhere: a handler that unconditionally mutates (`check_answer()` recording an answer) gets saved; one that never mutates at all (`/progress`, `handle_recall`'s pure `check_recall()`) triggers no write; one that mutates only along a taken branch (the reminder worker, which only calls `record_reminder_sent()` once a reminder actually sends — see "Reminders") gets saved only then. The comparison runs in a `finally` block, so a mutation already applied before the body raises (e.g. `check_answer()` running before a later `message.answer()` fails) still gets saved rather than silently lost. Named `check_out`, not `open`: `store.open(id)` reads, grammatically, as "open the store" (a method applied to a receiver reads as an action *on* that receiver, unlike the free-function `open()` builtin), and `open_student_record` — tried in between — just repeated "student_record" for no reason once the receiver is already a `StudentRecordBook`. `check_out` sidesteps both: like a library checkout, the verb alone already implies "borrow one item from a store," and the borrow/mutate/return-on-exit lifecycle is a close match for what the method actually does. Every `wiederholen/bot/commands/*.py` handler that touches the student_record opens exactly one `async with student_record_book.check_out(student_id) as student_record:` per request and does its response-building and message-sending inside that block — there's nothing else to reach for. `RedisStudentRecordBook` is the concrete implementation, one JSON blob per student under the Redis key `f"student_record:{student_id}"`. `__aiter__` — iterating the store itself (`async for student_id in student_record_book`) — yields every `student_id` with a stored student_record, deliberately not the student_record alongside it: this mirrors `dict.__iter__`'s own key-only convention, and a caller that needs a given student's student_record reads it via `check_out()` like anywhere else, so there's no second way to fetch one.

Releasing a connection (`RedisStudentRecordBook`'s `_close()` plus its own `__aenter__`/`__aexit__` — `__aenter__` returns `self`, `__aexit__` calls `self._close()`) lives entirely on `RedisStudentRecordBook`, not on the abstract `StudentRecordBook` — whether there's a connection to release at all, and how, is specific to this one backend, not a guarantee every `StudentRecordBook` implementation carries; a hypothetical in-memory store for tests, say, would have nothing to close. There's no public `close()` to call directly either way. The only place a store's lifetime is actually scoped this way today is `tests/plugins/student_record_book.py`'s `student_record_book` fixture (`async with RedisStudentRecordBook.from_url(...) as store: yield store`) — production (`wiederholen.bot.__main__.main()`/`wiederholen.bot.reminder.main()`) never closes its store at all, since both processes just run until killed and let the OS reclaim the connection. Not exposing `close()` as an ordinary public method means a caller can't half-remember-to-call-it; the only door open is the same `async with` protocol Python already trains every reader to recognize for anything resource-owning.

Deliberately scoped to *only* the student_record, not the rest of a chat's per-session state (language, ai_mode, mid-conversation shown_exercise/shown_recall, last_buttoned_message_id, aiogram's own conversation-state name) — that's Telegram session/UI state, and stays in aiogram's own `RedisStorage` (see below) rather than this store: the student_record is the one piece of per-student state that's genuinely meant to be transport-independent (a future web frontend embedded on a landing page would need to read/write the same learning record a Telegram chat has, with its own notion of `student_id`), while a chat's language preference or which exercise is mid-flight isn't something a web client would share with the Telegram bot the way the actual learning record is. `wiederholen.school.tutoring` (`Tutor`/`StudentRecord`) still never touches `StudentRecordBook` or any other storage itself — it only ever receives a plain `dict` from whichever transport layer is calling it, keeping the "no I/O" invariant that package started with (see "Key modules" above) — `StudentRecordBook` is a layer *between* a transport and `Tutor`, not a dependency of `Tutor`'s.

Everything else per chat — language, ai_mode, shown_exercise/shown_recall, last_buttoned_message_id, and aiogram's own conversation-state name (the `UserState.answering`/`.recalling` a router filters on) — stays in a plain, unmodified `aiogram.fsm.storage.redis.RedisStorage`, exactly as aiogram ships it; there's no codebase-specific subclass wrapping it. `wiederholen.bot` builds `dispatcher` with aiogram's default in-memory FSM storage (needed so importing the package — e.g. from tests — never depends on an external service or env var). `wiederholen.bot.bootstrap.load_bot_course_and_storage() -> tuple[Bot, Course, RedisStorage, StudentRecordBook]` constructs both the real `RedisStorage` (from `BOT_FSM_STORAGE_URL`) and a `RedisStudentRecordBook` (from its own `STUDENT_RECORD_STORAGE_URL`, via the separate `load_student_record_book()`) — both required with no fallback, same as `BOT_TOKEN`. The two env vars point at the same physical Redis today, just different DB numbers (`STUDENT_RECORD_STORAGE_URL` on DB 0, `BOT_FSM_STORAGE_URL` on DB 1 — not two separate instances), and are deliberately two separate names rather than one shared one: `wiederholen.school`'s own transport-independence (see above — a future web frontend would share the student record, not the Telegram session state) means the two stores are conceptually independent even while they happen to be colocated, and a distinct env var is what would let a future deployment point them at separate Redis instances (or a wholly different backend for student records) without touching the other. Both `wiederholen.bot.__main__.main()` (polling bot) and `wiederholen.bot.reminder.main()` (reminder worker) call this one function and get all four pieces back, even though the reminder worker has no aiogram routers of its own — it still needs `RedisStorage` for a small point lookup (see "Reminders" below), so splitting the loader in two wouldn't actually let it drop the dependency. `main()` assigns the `RedisStorage` to `dispatcher.fsm.storage`. Works with Valkey too (wire-compatible). `compose.yaml` (local dev, this repo) and the deployment compose file (outside this repo) both run a `valkey` service and set both `BOT_FSM_STORAGE_URL` and `STUDENT_RECORD_STORAGE_URL` for the `bot` and `reminder` services, backed by a named volume for durability across container recreation.

Tests run against a real Redis/Valkey too, not an in-memory fake — `tests/plugins/aiogram.py::pytest_configure` pins both `BOT_FSM_STORAGE_URL` and `STUDENT_RECORD_STORAGE_URL` to the same dedicated DB number for the whole test session, before any test code runs, so a local `docker compose run bot pytest` (which shares the `bot` service's real dev config) can never touch a DB a real dev/prod bot might be using regardless of what's set in the environment. The DB number comes from the `--redis-db-override` pytest option (named for what it now overrides — both connection URLs, not just the FSM one — since the day it started covering `STUDENT_RECORD_STORAGE_URL` too), defaulting to `15` (separate from either dev/prod DB — `0` for student records, `1` for FSM, see "Persistence" above) via `pyproject.toml`'s `addopts`; passing `--redis-db-override=""` disables the pin entirely, which the CI workflow does since its `valkey` service container is already ephemeral and tests-only, so there's no dev/prod DB to protect there — CI instead points `BOT_FSM_STORAGE_URL` and `STUDENT_RECORD_STORAGE_URL` at their normal two *different* DB numbers on that same ephemeral container, deliberately: it's a cheap way to actually prove the two stores are independent (a test accidentally reading/writing the wrong store's data would surface as a real failure there, not silently pass because both happened to share one DB). `tests/plugins/aiogram.py`'s `redis_storage` fixture builds a plain `RedisStorage` and flushes the DB before every test; the autouse `_reset_storage` fixture wires it into `dispatcher.fsm.storage`. `tests/plugins/student_record_book.py`'s `student_record_book` fixture builds a `RedisStudentRecordBook` from `STUDENT_RECORD_STORAGE_URL` and flushes *its own* DB directly, rather than assuming it coincides with `redis_storage`'s — the two DBs are different by default everywhere (compose.yaml, CI) and only coincide when the `--redis-db-override` pin forces both to the same overridden DB for a local pytest run, so relying on a same-DB assumption would silently stop cleaning this store the moment that assumption didn't hold (it still takes `redis_storage` as a parameter, but only for fixture ordering relative to `_reset_storage`, not for its flush) — and its own autouse `_set_student_record_book` fixture registers it as **permanent** aiogram workflow data (`dispatcher["student_record_book"] = student_record_book`, the same mechanism `main()` uses via `dispatcher.start_polling(..., student_record_book=...)`), not a per-call `feed_message(..., student_record_book=...)` kwarg the way `course` is — unlike `course` (different exercises in nearly every test), `student_record_book` is the same piece of infrastructure for every test in the session, so no test needs to pass it explicitly. This is deliberately fidelity-over-speed: it's still fast (no measurable slowdown at this suite's size) and catches real Redis behavior an in-memory double can't. Both fixtures are function-scoped, not session-scoped: pytest-asyncio gives each test its own event loop by default, and a Redis connection can't outlive the loop it was created in.

## Tracing

`wiederholen.tracing` (top-level, a sibling of `school`/`bot`/`web`) holds the generic OpenTelemetry setup every process that touches Redis needs — `default_tracer`, `configure_tracing()`, `instrument_redis()` — while `wiederholen.bot.tracing` keeps only what's genuinely aiogram-specific: `TracingMiddleware` and its `_describe()` helper for turning a Telegram `Update` into a span name/attributes. This split exists because `wiederholen.web.__main__` needs the same generic setup `wiederholen.bot.__main__`/`wiederholen.bot.reminder` already had — importing it from `wiederholen.bot.tracing` would have made `wiederholen.web` depend on `wiederholen.bot`, which "a sibling of `wiederholen.bot`, not a dependency of it or vice versa" (see "Web frontend" below) rules out. An earlier version of this fix tried exactly that import before catching the violation and extracting this module instead. `wiederholen.bot.tracing` imports `default_tracer` from here for `TracingMiddleware`'s own default argument, but re-exports nothing — `wiederholen.bot.__main__`/`wiederholen.bot.reminder`/`wiederholen.web.__main__` all import `configure_tracing`/`instrument_redis`/`default_tracer` directly from `wiederholen.tracing`, not proxied through the bot package.

`wiederholen.bot.tracing.TracingMiddleware` wraps every incoming Telegram update in one OpenTelemetry span — registered as `outer_middleware` on `dispatcher.update` (not `.message`/`.callback_query`) in `wiederholen/bot/__init__.py`, deliberately at the top-level "update" observer rather than the per-event-type ones. This matters because aiogram's own `Dispatcher.__init__` registers several of its own outer middlewares on `dispatcher.update` — `ErrorsMiddleware`, `UserContextMiddleware`, and `FSMContextMiddleware` (`dispatcher.fsm`) — and `FSMContextMiddleware` reads the current FSM state from storage (a Redis `GET` via `RedisStorage`, see "Persistence" below) *before* routing even resolves message vs callback_query vs anything else. Outer middlewares wrap in registration order (first-registered = outermost — verified via aiogram's `MiddlewareManager.wrap_middlewares`), so registering `TracingMiddleware` on `dispatcher.message`/`.callback_query` (an earlier version of this) meant that Redis `GET` always ran *before* our span existed, showing up as an orphan root span in the backend instead of a child of the update's span — caught by directly inspecting real trace data. The fix: construct `Dispatcher(disable_fsm=True)` (which still creates `dispatcher.fsm` but skips aiogram's own auto-registration of it as outer middleware) and register `TracingMiddleware` on `dispatcher.update` first, then `dispatcher.fsm` second — so our span now wraps the FSM state lookup too. Confirmed empirically both ways: pointed a live dispatcher at real Redis with an in-memory span exporter and checked parent/child span IDs directly, rather than trusting the theory. `dispatcher.fsm.storage = storage` (set later in `main()`, see "Persistence") still works exactly as before — `disable_fsm` only skips the auto-registration, not the middleware's existence.

The module-level `_describe()` function unwraps `update.event` (aiogram's own property for "whichever event type is actually set on this Update") and builds the span name/attributes from it: `"telegram.message"` with `telegram.chat_id` and, only if the text is a bot command (starts with `/`), `telegram.command` — deliberately never the raw free-text an exercise answer might contain; `"telegram.callback_query"` with `telegram.chat_id` (from `event.message`, guarded by `isinstance(..., Message)` since Telegram can hand back an `InaccessibleMessage` for an old message) and `telegram.callback_data` (always one of this codebase's own fixed constants — `NEXT_EXERCISE`/`RECALL`/`STUDY_MORE`/etc. — never free text, so safe to record outright). Any other update type (this bot doesn't handle any, but Telegram can still deliver e.g. `poll_answer`/`my_chat_member`) falls back to a generic `"telegram.update"` span with no attributes, rather than the middleware raising for a type it doesn't special-case.

The SDK wiring is separate from the middleware itself: `TracingMiddleware` takes an injectable `tracer` (defaulting to `wiederholen.tracing.default_tracer`, a module-level `trace.get_tracer(__name__)` obtained *before* any provider is configured) — this is the standard OTel pattern, since `get_tracer()` returns a proxy that starts delegating to a real provider the moment one is registered, so it's safe to grab at import time. `configure_tracing()` (which builds the real `TracerProvider` + `BatchSpanProcessor(OTLPSpanExporter())` and calls `trace.set_tracer_provider()`) is called only from `wiederholen.bot.__main__.main()`, `wiederholen.bot.reminder.main()`, and `wiederholen.web.__main__.main()`, never at import time — so importing `wiederholen.bot`/`wiederholen.web` (e.g. from tests) still has no external dependency (same reasoning as the in-memory FSM storage default, see "Persistence" above): without a configured provider, spans are inert no-ops. `configure_tracing()` itself is a no-op (`_otlp_endpoint_configured()` returns `False`, checked before touching anything else) unless `OTEL_EXPORTER_OTLP_ENDPOINT` or `OTEL_EXPORTER_OTLP_TRACES_ENDPOINT` is actually set — deliberately: `OTLPSpanExporter()` on its own defaults to `http://localhost:4318` (the standard convention for a local collector sidecar), which this project's plain docker-compose deployment never has, so without an explicit endpoint that default is never valid; without this check, `configure_tracing()` would still build a real `TracerProvider`/`BatchSpanProcessor` that spends its life retrying a doomed export in the background (confirmed: `BatchSpanProcessor` logs `Transient error ... Connection refused` repeatedly and `Failed to export span batch` on shutdown) purely as log noise, never actually breaking anything since it fails closed rather than raising. `configure_tracing()` passes `Resource.create()` no explicit attributes at all — deliberately: every other piece of this config (endpoint, headers, protocol) is 100% env-var-driven with no code-level default, so `service.name`/`service.namespace`/etc. follow the same rule via `OTEL_SERVICE_NAME`/`OTEL_RESOURCE_ATTRIBUTES`, falling back to the OTel SDK's own generic `"unknown_service"` if genuinely unset. A hardcoded fallback name was tried and dropped: it actively hid a real misconfiguration (the `reminder` service briefly missing its `OTEL_*` env vars in `compose.override.yaml` — see below) by making its spans look identically labeled to the bot's instead of standing out as unconfigured. Tests exercise `TracingMiddleware` by constructing it directly with a throwaway `TracerProvider`/`InMemorySpanExporter` (`tests/bot/test_tracing.py`) rather than touching the process-global provider, since `trace.set_tracer_provider()` can only ever succeed once per process — a second call is a silent no-op, which would make per-test isolation impossible if tests relied on the global registration instead; `configure_tracing()`/`_otlp_endpoint_configured()`/`instrument_redis()` themselves (owned by `wiederholen.tracing`, not aiogram-specific) get their own direct tests in `tests/test_tracing.py` instead, split out from `tests/bot/test_tracing.py` (which now holds only `TracingMiddleware`'s own span-content tests) when the module itself split.

`tests/plugins/tracing.py::pytest_configure` forces `OTEL_SDK_DISABLED=true` for the whole test session, before any test code runs — same rationale and shape as `tests/plugins/aiogram.py::pytest_configure` pinning `BOT_FSM_STORAGE_URL`/`STUDENT_RECORD_STORAGE_URL` to a dedicated DB (see "Persistence" above): `docker compose run bot pytest` shares the `bot` service's config with the real bot, so without this, a real `OTEL_EXPORTER_OTLP_ENDPOINT`/`HEADERS` set for local dev (e.g. real Honeycomb credentials via `compose.override.yaml`, see below) would mean every test run actually exports real spans to that backend — confirmed by temporarily pointing the endpoint at an unreachable address and watching `BatchSpanProcessor` retry and fail to export at process exit (`TracerProvider` registers an `atexit` handler that flushes on shutdown by default). `OTEL_SDK_DISABLED` is read by `TracerProvider.__init__` itself — regardless of whether it's the global provider or a one-off instance a test constructs directly — so it also disables the throwaway `TracerProvider`/`InMemorySpanExporter` the shared `tracer`/`exporter` fixtures (`tests/plugins/tracing.py`, same file as the `pytest_configure` above) build to verify span content; `tracer` explicitly opts back in with `monkeypatch.delenv("OTEL_SDK_DISABLED", raising=False)` before constructing its own provider, scoped to just the tests that request it via `monkeypatch`'s automatic teardown. `tests/bot/test_tracing.py` (`TracingMiddleware`'s own span content) and `tests/school/tutoring/test_tutoring_events.py` (`emit()`'s span events, see "Tutoring events" above) share these two fixtures rather than each defining their own copy.

`compose.override.yaml` (gitignored, local-only, also used to bind-mount the private content repo's `data/`) sets `OTEL_SERVICE_NAME`/`OTEL_RESOURCE_ATTRIBUTES`/`OTEL_EXPORTER_OTLP_*` per service (`bot`/`reminder` each get their own `OTEL_SERVICE_NAME` so their spans are distinguishable in the backend) — this needs its own `environment:` block under *each* service key, since Compose merges `environment` per-service, not globally; a service with no block simply gets none of these vars and `OTLPSpanExporter()` silently falls back to `http://localhost:4318`, which just fails every export in a container with no local collector. A stray `=` inside a YAML mapping *key* (e.g. `OTEL_RESOURCE_ATTRIBUTES=:` instead of `OTEL_RESOURCE_ATTRIBUTES:`) is a related trap worth knowing about: Compose doesn't error on it, it silently becomes part of the *value* instead (`docker compose config` is the way to check what actually gets resolved) — which for `OTEL_RESOURCE_ATTRIBUTES` manifests as a leading `=` that makes the first `key=value` pair parse with an empty key, logged by `opentelemetry/attributes` as `invalid key `` `.

`instrument_redis()` wraps `opentelemetry.instrumentation.redis.RedisInstrumentor().instrument()` — third-party auto-instrumentation that monkeypatches `redis`'s command execution (both the sync client and the `redis.asyncio.Redis` both `RedisStorage` and `RedisStudentRecordBook`/`WebSessionStore` use, see "Persistence" above) to emit a span per Redis call, with no code changes needed at any call site — it patches the client class globally, so it covers all of them regardless of which process reaches them. It's idempotent (a repeat call just logs a warning and no-ops) like `set_tracer_provider()`, which matters because both it and `configure_tracing()` get called on every `main()` invocation, including the repeated ones in `tests/bot/test_main.py`/`tests/bot/test_reminder.py`/`tests/web/test_main.py` within a single test session. `wiederholen.bot.__main__.main()`, `wiederholen.bot.reminder.main()`, and `wiederholen.web.__main__.main()` all call `configure_tracing()` and `instrument_redis()`, since all three processes talk to Redis one way or another. The `TracingMiddleware`-per-update span coverage above is bot-only (the reminder worker has no aiogram routers to wrap, and `wiederholen.web` is a Litestar app with no aiogram involved at all) — but `wiederholen.bot.reminder` gets its own hand-rolled equivalent instead of going without: `tick()` wraps its whole sweep in a `"reminder.tick"` span (via the same `tracing.default_tracer` `TracingMiddleware` uses) and `_remind_chat()` wraps each chat's check in a nested `"reminder.check_chat"` span (`telegram.chat_id` attribute, plus `reminder.sent` — `False` by default, flipped to `True` only once `bot.send_message()` actually succeeds) — without this, every Redis call iterating `student_record_book`/`_remind_chat()` makes would otherwise show up as an orphan root span per call, one per sweep-chat, with no way to see which chat or sweep it belonged to. A chat whose processing raises still gets its exception recorded on `reminder.check_chat` automatically (the exception propagates out through the `with` block before `tick()`'s own `except Exception` catches it and logs), same mechanism as `TracingMiddleware`.

## Reminders

A separate worker process (`python -m wiederholen.bot.reminder`, its own `reminder` service in this repo's `compose.yaml` and in the deployment compose file) nudges users who've gone quiet with material due — not an in-process `asyncio` task in the polling bot, specifically to avoid leaking an uncancelled background task across `tests/bot/test_main.py`'s repeated `main()` calls.

`Tutor` owns the decision, student_record-backed like the rest of its scheduling state: `check_answer()` records `student_record["last_exercise"]["answered_at"]` (a timestamp, part of the same `last_exercise` record as `question`) — "activity" means answering the main exercise specifically, not any interaction with the bot (recall answers don't count). `Tutor.should_remind()` is a pure query — no side effects — returning `True` only if there's anything due at all (`self._get_due_pairs()`, unfiltered — introduced status doesn't matter here the way it does for `next_exercise()`'s own selection, so a due-but-not-yet-introduced pair, e.g. one expedited via a chain, counts too) or a fresh-and-ungated pair available (`self._get_available_not_scheduled_pairs()`, deliberately not also unioning in `_get_due_pairs(is_introduced=False)` the way `next_exercise()` does — see above for why that's redundant here) — checked inline rather than through a named helper (a `_due_topics_count()`-style method was tried and dropped: its name suggested only genuinely-*due* reviews, which was misleading once it also counted available-but-not-yet-due new pairs), deliberately not filtered through the word cap, since a reminder should fire even if the cap is what's currently blocking new material — `last_answered_at` is ≥`Tutor.REMIND_AFTER` (24h) old, and there hasn't already been a reminder since that last answer (`last_reminded_at is None or last_reminded_at < last_answered_at`) — this last condition means exactly one reminder per period of inactivity, not a repeating nag. Checking only an available-new check here, without the due-pairs check alongside it (a since-fixed regression, caught by `test_should_remind_is_true_for_an_overdue_review_with_no_new_pairs_available`), would miss a learner who has genuine overdue reviews but is at today's new-word cap, silently never reminding them. `Tutor.record_reminder_sent()` is a separate method, called by the bot layer only *after* a Telegram send actually succeeds — `should_remind()` itself never mutates the student_record, so a failed send never gets wrongly marked as delivered.

The worker has no separate registry of known chats — iterating `StudentRecordBook` itself (`async for student_id in student_record_book`, via `RedisStudentRecordBook.__aiter__`) enumerates every student with a stored student_record via a real Redis `SCAN` over its own `student_record:*` keys, regardless of which frontend wrote it. `wiederholen.bot.reminder.tick()` does this once per sweep and tries to decode each `student_id` back into an `int` chat_id via `TelegramStudentID.decode()` — a `student_id` from a different frontend sharing this same store (see "Persistence" above) raises `NotATelegramStudentIdError`, which `tick()` catches and skips outright: reminding isn't this worker's job for a student it can't even address as a chat. For each id that does decode, `tick()` delegates to `_remind_chat()`, which opens `student_record_book.check_out(TelegramStudentID.encode(chat_id))` and builds a `Tutor` from the student_record to decide `should_remind()` — but sending the reminder needs the chat's **language**, which isn't part of the student_record (see "Persistence" above): `_remind_chat()` does one point `RedisStorage.get_data(StorageKey(bot_id=bot.id, chat_id=chat_id, user_id=chat_id))` lookup for that, the one place `reminder.py` still touches aiogram directly, since nothing about that lookup depends on iterating anything — it just needs one already-known chat_id's data. There's no explicit save call anywhere in `_remind_chat()`: `check_out()`'s own change-detection (see "Persistence" above) already does exactly the right thing — the two early returns (`should_remind()` false, or the send raising `TelegramForbiddenError`) leave the student_record untouched, so nothing gets written; only the fall-through path, where `record_reminder_sent()` actually runs, changes anything, and that's exactly when `check_out()` saves. One chat raising (e.g. malformed student_record data) is caught and logged, not fatal to the sweep. `run()` loops `tick()` every `POLL_INTERVAL_SECONDS` (15 min).

## Feature flags

`wiederholen.bot.feature_flags` gates a feature by chat_id without persistence or admin commands — built for testing a single premium feature (AI-personalized exercises, not yet implemented) on one test user before any billing exists. `BOT_FEATURE_FLAGS` env var format: `flag_name:chat_id1,chat_id2;other_flag:chat_id3`, parsed once at startup by `wiederholen.bot.bootstrap.load_feature_flags()` (a separate function from `load_bot_course_and_storage()`, not merged into its return tuple — `reminder.py` doesn't call it, since gating a not-yet-built feature isn't a reminder-worker concern) into `dict[str, frozenset[int]]`. `parse_feature_flags(raw)` tolerates surrounding whitespace and a trailing `;` (a flag with no chat ids after `:` parses to an empty `frozenset`, matching no one). `has_feature(flags, flag, chat_id) -> bool` does the actual lookup — `chat_id in flags.get(flag, frozenset())`.

No persistence, no runtime toggling: enabling a flag for a chat means editing `BOT_FEATURE_FLAGS` and restarting, same as `BOT_TOKEN`/`OTEL_*` already work — a genuine limitation for anything beyond a handful of test users, deliberately deferred until there are paying subscribers instead of one.

Deliberately bot-layer-only, mirroring `wiederholen.bot.tracing`'s own precedent for keeping infra/config concerns out of the learning domain: `wiederholen.school` never sees a chat_id or a flag name, and `Tutor`/`StudentRecord` gain no new parameter for this. `__main__.main()` calls `load_feature_flags()` alongside `load_bot_course_and_storage()` and passes the result to `dispatcher.start_polling(bot, course=course, feature_flags=feature_flags)` — aiogram's dependency injection then hands it to any handler that declares a `feature_flags` parameter by name, the same mechanism `course` already relies on. `command_wiederholen` is the one example check point this issue scoped in: `feature_flags: dict[str, frozenset[int]] | None = None` (defaulting to `None`, not `{}`, so the many existing `/wiederholen` tests that don't pass `feature_flags=` don't need touching — production always passes a real, possibly-empty dict) — if `has_feature(feature_flags or {}, "ai_exercises", message.chat.id)`, it sets a `feature.ai_exercises` attribute on the current span and otherwise does nothing. No behavior changes yet for any chat; the actual AI-exercise feature is separate, larger work this unblocks.

## Pending inline buttons

Tapping "Следующее задание"/"Закрепить"/"Study more"/etc. clears its own button — the callback handler gets `callback.message` for free and calls `edit_reply_markup(reply_markup=None)` on it directly. Typing a command instead (`/wiederholen`, `/progress`, `/reset`, `/language`) bypasses that entirely: Telegram never tells a bot which earlier message a command "replaces", so without deliberate tracking the button stays visibly attached to the old message forever, even though the bot has already moved on.

`wiederholen.bot.pending_buttons` fixes this with one piece of FSM state, `last_buttoned_message_id: int | None`, alongside `student_record`/`shown_exercise`/etc.: `remember_buttoned_message(state, message)` stores the id of a message that was just sent with an inline keyboard; `forget_buttoned_message(state)` clears it once the button's markup is gone some other way; `clear_stale_buttons(message, state)` reads the stored id and, if one is pending, strips it via `message.bot.edit_message_reply_markup(chat_id=message.chat.id, message_id=..., reply_markup=None)` (swallowing `TelegramBadRequest` — the message may already be edited, deleted, or too old to touch) before forgetting it either way. Only one id is ever tracked at a time: a chat has at most one live set of buttons pending a tap, since sending a new buttoned message (or a command clearing the old one) always supersedes whatever was there before.

Every message sent with an inline keyboard calls `remember_buttoned_message()` right after: `command_wiederholen`'s and `_respond_with_next_exercise()`'s `nothing_due_text`+study-more-button replies, `handle_answer()`'s explanation (only when it actually attaches a recall/next button — the required-recall path attaches none), `handle_recall()`'s correct/wrong replies, `command_reset`'s confirm/cancel prompt, `handle_reset_confirm()`'s done message, and `command_progress`'s reply (see below). Every one of the four command entry points (`command_wiederholen`, `command_progress`, `command_reset`, `command_language`) calls `clear_stale_buttons(message, state)` as its very first action, before anything else. The callback handlers that clear their own button directly and attach nothing new (`_respond_with_next_exercise()`'s exercise-found branch, `handle_recall_request()`, `handle_reset_cancel()`) call `forget_buttoned_message()` right after, so the tracked id doesn't linger stale once its message no longer has a keyboard — `_respond_with_next_exercise()`'s exercise-*not*-found branch and `handle_reset_confirm()` instead call `remember_buttoned_message()`, since each attaches a fresh button of its own (a study-more button, a next-exercise button — see below) that supersedes rather than clears. `handle_reset_confirm()`/`handle_reset_cancel()` also pass `reply_markup=` explicitly to their `edit_text()` calls (`make_next_button(locale)`/`None` respectively) rather than omitting it, since editing a message's text alone doesn't implicitly drop its existing inline keyboard.

`command_progress`'s reply and `handle_reset_confirm()`'s "Прогресс сброшен" reply both carry their own `NEXT_EXERCISE` button (`make_next_button(locale)`, promoted from `wiederholen.py`'s private `_make_next_button` to a plain module-level function once other command modules needed to import it too) — since both already strip or replace whatever button was there before, showing a fresh one lets a learner jump straight back into practicing without a separate `/wiederholen`. `handle_next_exercise()`'s callback handler needs no change to support either: it isn't state- or origin-aware, so a tap works identically regardless of which command's message the button was attached to, and the tap-cleanup/re-remember machinery above already covers it like any other buttoned message.

`message.bot` is typed `Bot | None` by aiogram (bound lazily when a real update is dispatched) — `clear_stale_buttons()` asserts it's set rather than threading an optional through, same as the codebase's other `assert x is not None` narrowing (e.g. `Tutor.request_recall()`'s `last_exercise` check). Tests need a realistic `SendMessage` response to exercise any of this: `tests/plugins/aiogram.py`'s `feed_raw_update` fixture used to mock `session.make_request` to always return bare `True`, which is fine for every method whose result nothing reads, but a message-id-tracking feature needs the actual assigned id — it now returns a synthetic `Message` (an incrementing `message_id` starting at 1000, plus `date`/`chat`) specifically for `SendMessage` calls, and keeps returning `True` for everything else.

## AI-generated exercises

MVP preview step for a possible AI-personalized-exercises freemium feature (GitHub issue #122): an `/ai` toggle, gated behind the `ai_exercises` feature flag (see "Feature flags" above) and invisible to everyone else, switches a chat between the normal exercise flow and one where `question`/`explanation` are generated on the fly by an LLM instead of coming from `exercises.yaml`.

`wiederholen.school.authoring.generate_shadow_exercise(client, exercise, course, *, authoring_guide=None) -> Exercise` takes a real `Exercise` already selected by `Tutor.next_exercise()` and returns a "shadow" copy — same `word`/`topic`/`answer`/`distractors`/`recalls`, AI-written `question`/`explanation` — via `dataclasses.replace(exercise, question=..., explanation=..., ...)` (`Exercise` is a frozen dataclass, so this is the natural way to get a modified copy, and `__post_init__` validates the result for free — e.g. that `explanation` has both `ru`/`en` keys). Keeping everything except the wording untouched means correctness (does the answer fit, are the distractors actually wrong) is guaranteed by construction, not by trusting the model's German grammar. This module is the only place in the codebase that calls out to an LLM, and lives as a flat module, a sibling of `tutoring` under `wiederholen.school` rather than inside `tutoring` specifically so `Tutor`/`StudentRecord` never gain a network dependency (see "Key modules" above) — `session.py`/`student_record.py` don't import it, and nothing about scheduling changes: `check_answer()` only ever reads `word`/`topic`/`answer` off whatever `Exercise` it's given, never `question`, so a shadow exercise flows through `check_answer()`/`request_recall()` identically to a real one once it's in `shown_exercise` state.

`description` (the `preposition_meaning`-style disambiguating translation of the target sentence, shown before answering — see the content repo's own authoring guide) is regenerated too, but only conditionally: it's carried over into `dataclasses.replace()` only when `exercise.description is not None`, and the prompt only asks for a replacement (and the tool schema only requires one) in that case. This isn't optional polish — it was a real bug caught from a live test: `question`/`explanation` used to be the only fields replaced, so a `preposition_meaning` exercise's `description` kept describing the *original* sentence's meaning after the model wrote a brand-new one (observed in production: a new question about apples coming from the garden, paired with a leftover description translating "the table is made of wood") — exactly the mismatch a description exists to prevent in the first place. A topic whose exercises never carry a `description` (the vast majority) is unaffected either way, since `exercise.description is None` for them and the field is never mentioned to the model at all.

The prompt sent to the model (Anthropic Messages API, `AsyncAnthropic`, model pinned to `claude-haiku-4-5-20251001` via the `MODEL` constant) has two parts: an optional cached system block — the full "Exercises" section of the content repo's own `CLAUDE.md` authoring guide, if `authoring_guide` is provided, marked `cache_control: {"type": "ephemeral"}` so repeated calls within a testing session mostly hit Anthropic's prompt cache instead of reprocessing the whole guide each time — and a user message with up to three few-shot examples of real `question`s sharing the target exercise's `topic` (`course.exercises` filtered by topic, excluding the target itself), plus the target's own `word`/`topic`/`answer`/`distractors`. The model is forced to respond via tool use (`tool_choice={"type": "tool", "name": "submit_shadow_exercise"}`) with a `{question: str, explanation: {ru: str, en: str}}` schema, rather than parsing free text — `generate_shadow_exercise()` pulls the `ToolUseBlock` out of the response, validates its `input` shape, and raises `AIGenerationError` (defined alongside it) for anything that goes wrong: the API call itself failing, no tool-use block in the response, missing/wrong-typed fields, or an `explanation` that fails `Exercise.__post_init__`'s own validation. There's no fallback to the real exercise on failure anywhere — `AIGenerationError` always surfaces as `locale.ai_generation_failed` to the learner, deliberately: this is a testing tool for one person, so a silent fallback would risk masking a broken integration behind human-authored questions that look perfectly normal; a visible failure is what lets a tester actually notice and either retry or turn `/ai` back off.

Both the Anthropic client and the guide text are optional, loaded once at startup by `wiederholen.bot.bootstrap.load_anthropic_client()`/`load_authoring_guide()` and threaded through `dispatcher.start_polling()` as `anthropic_client`/`authoring_guide` workflow data, the same mechanism `course`/`feature_flags` already use. Neither is required the way `BOT_TOKEN` is: `ANTHROPIC_API_KEY` unset means `load_anthropic_client()` returns `None` rather than failing startup (only the one flag-gated test chat ever needs it), and `AUTHORING_GUIDE_PATH` unset means `load_authoring_guide()` returns `None` and generation just runs on few-shot examples alone (same "absence means the feature is off" pattern as `topics.yaml`).

`command_ai` (`wiederholen.bot.commands.ai`) is a bare toggle, no arguments, mirroring `/language`'s own shape: reads `ai_mode` out of FSM state as a plain top-level key (like `language`, not nested in `student_record`, so it survives `/reset`), flips it, and replies with `locale.ai_mode_on`/`ai_mode_off`. It no-ops entirely — no reply, no state change — for any chat `has_feature(feature_flags or {}, "ai_exercises", ...)` doesn't cover, the same invisible-unless-flagged shape `command_wiederholen`'s own flag check point uses; like the other four command entry points, it calls `clear_stale_buttons()` first.

`ai_mode` is meant to stay on for a whole session, not just the one exercise it was toggled before — but `handle_answer()`/`handle_recall()` both read `state_data` and immediately call `state.clear()` (wiping the entire FSM data dict, `ai_mode` included) before selectively restoring the handful of keys they still need, and `_start_recall()` does its own separate `state.update_data()` call for the required-recall path. Each of these four `update_data()` call sites (`handle_answer()`'s non-required branch, `handle_recall()`, and both of `_start_recall()`'s callers — `handle_answer()`'s required-recall branch and `handle_recall_request()`) now explicitly re-adds `ai_mode` — read from `state_data` *before* the `clear()` in the first two cases — alongside the keys they already restored; `_start_recall()` itself takes `ai_mode` as a keyword-only parameter for this rather than reaching into `self`/state on its own, matching how it already receives `language`/`student_record` as plain parameters instead of re-reading state. Missing this (caught from a real user report) meant AI mode silently reverted to off after exactly one exercise — since nothing surfaced the flag flipping back, a tester would just see human-authored questions again and have no idea why.

Generation is further scoped **per topic**, not just per chat: `Course.ai_generatable_topics: frozenset[str]` (parsed from `topics.yaml`'s new per-source `ai_generation: true` key, alongside `chains`/`gates`/`chains_by_answer`/`instruction` — same opt-in-by-absence shape, a topic with no entry or `ai_generation` unset/false is simply not eligible) exists because the "swap `question`/`explanation`, leave everything else untouched" correctness argument only holds for topics whose `answer` is grammatically independent of the exact sentence wording. It breaks down for topics where the question's *exact form* encodes part of the answer: `partizip_ii`/`praeteritum`'s `question` is a fixed `"verb → form"` template, not a sentence, so there's nothing meaningful to rewrite; `konjunktion_wortstellung`/`nebensatzkonjunktion_wortstellung`'s `question` embeds a scrambled word bank that `answer` is a specific reordering of — a rewritten sentence with different words would leave the old `answer` matching nothing; `praesens_vokalwechsel`'s `answer` depends on which subject (`du`/`er`-`sie`-`es`) the sentence uses — a model free to pick a different subject while rewriting could produce a sentence whose grammatically correct answer no longer matches the untouched `answer` it's paired with. Both `command_wiederholen` and `_respond_with_next_exercise()` compute this per-exercise, after `next_exercise()` has actually picked one (topic isn't known any earlier): `ai_mode = ai_mode and exercise.topic in course.ai_generatable_topics` — reusing the `ai_mode` name for the narrowed, per-exercise value rather than introducing a second variable, since nothing downstream in either function needs the raw chat-level toggle separately. A topic outside the allowlist behaves exactly as if `ai_mode` were off for that one exercise: the real `question`/`explanation` show through, no `🤖` marker, no API call — not an error, since this is a known, static scope limit rather than a runtime failure.

`_apply_ai_mode()` (`wiederholen.bot.commands.wiederholen`) is the shared decision point both `command_wiederholen` and `_respond_with_next_exercise()` (so both `handle_next_exercise` and `handle_study_more`, which share it) call right after `tutor.next_exercise()` finds a real exercise: if `ai_mode` is off, the exercise passes through untouched; if it's on, it calls `generate_shadow_exercise()` and returns the shadow — or `None`, both when `anthropic_client` is `None` (flag on but not configured) and when generation raises `AIGenerationError`, collapsing both failure modes into one signal the caller reacts to identically (show `locale.ai_generation_failed`, leave FSM state untouched, same as the existing "nothing due" early-return shape). `next_exercise()` itself does no student_record writes (confirmed: no `schedule_pair()`/`_get_or_create_schedule_entry()` calls anywhere in it), so picking an exercise and then bailing out for an AI failure has nothing to roll back.

`_format_question()` takes an `is_ai_generated` keyword-only flag (default `False`) that prefixes the rendered text with `🤖 ` ahead of the `❓` question line — both call sites already have the `ai_mode` boolean in hand (the one `_apply_ai_mode()` was just called with) and pass it straight through, so a shadow exercise is visually distinguishable from a real one at a glance, since nothing else about the message (buttons, reply keyboard, `💭`/`ℹ️` lines) differs between the two.

## Web frontend

`wiederholen.web` (Litestar) is a second delivery mechanism for the same `wiederholen.school` domain — a sibling of `wiederholen.bot`, not a dependency of it or vice versa. Runs as its own `web` service (`python -m wiederholen.web`, `compose.yaml`), separate from `bot`/`reminder`. Two frontends share its one backend: an embeddable widget (a landing page names specific grammar topics for its own page) and a standalone app (no fixed topics of its own — see below for both).

`wiederholen.web.web_student_id.WebStudentID` mirrors `TelegramStudentID`'s shape but not its API: there's no pre-existing identity to encode (no equivalent of `chat_id`), so `WebStudentID.generate() -> StudentID` mints a fresh, unguessable random token (`secrets.token_urlsafe(32)`) tagged with a `web:` prefix, and `WebStudentID.validate(raw) -> StudentID` checks an incoming value actually carries that prefix, raising `NotAWebStudentIdError` for anything that doesn't (a cookie from a different frontend sharing the same `StudentRecordBook`, or a client that sent garbage). A first-time visitor gets a `wiederholen_student_id` cookie set by the server on their first response (`HttpOnly`, `Secure`, `SameSite=Lax`, `Domain` configured via `WEB_COOKIE_DOMAIN`) — deliberately server-chosen and unguessable rather than a client-generated id, so one visitor can't address another's record by picking the same value. `Domain` is expected to be the landing page's own parent domain (e.g. `example.com`, with the widget served from a subdomain like `app.example.com`) — same-site under the modern `SameSite` cookie model, so `Lax` is enough to have the cookie sent on the widget's cross-subdomain fetch calls without needing `SameSite=None` and the third-party-cookie restrictions that comes with.

`wiederholen.web.app` has four endpoints: `POST /api/exercise/next` (body: `{topics: list[str], language?}`), `POST /api/exercise/check` (body: `{answer: str, language?}`), `POST /api/exercise/recall` (body: `{language?}`), and `POST /api/exercise/recall/check` (body: `{answer: str}`) — the last two are the recall equivalents of the first two, see below. `next_exercise()` builds `course.restricted_to(data.topics)` (see "Repetition schedule" above) and calls `Tutor(restricted_course, student_record).next_exercise()` — the topic restriction is per-request, not baked into any stored state, so the same student's `student_record` carries their real progress across every page/widget they've ever used, even though any one request only ever sees the slice of the course its own page is about. An empty `topics` list is a deliberate exception to that: `next_exercise()` uses the whole `course` unrestricted rather than calling `restricted_to([])`, which would otherwise filter every exercise out (an empty `frozenset` matches no topic) — this is what lets the standalone app (below) draw from the entire course without needing to know or send every topic name up front, unlike a landing page's embedded widget, which always names its own specific topics. The response DTO (`ExerciseDTO`) never includes `answer` — multiple-choice `choices` are `distractors + [answer]` shuffled, and a typed-input exercise (empty `distractors`) gets `choices: null`, telling the widget to render a text field instead of buttons.

`request_recall()`/`check_recall()` mirror `Tutor.request_recall()`/`check_recall()` directly, the same pairing `next_exercise()`/`check_answer()` already follow. `request_recall()` reads `shown_exercise` from the session store (409 if none, same shape as `check_answer()`'s own), opens `student_record_book.check_out()`, and calls `Tutor(course, student_record).request_recall(exercise)` — this is where the bot's own recall side effects already live (recording the shown `recall_question` for repeat-avoidance, and halving a pair's repetition interval the first time an *optional* recall is requested for it — see "Repetition schedule" above), so nothing web-specific was needed to get them; the result is stored via `session_store.set_shown_recall()` and returned as `RecallDTO{question, hint}` (`hint` localized to the request's `language`, `null` if the recall has none). Called once per recall step, including retries — each call re-picks via `request_recall()`, which already excludes the immediately-previous `recall_question` when alternatives exist, so a retry naturally varies like it does in the bot. `check_recall()` reads `shown_recall` (409 if none — a *different* 409 from `request_recall()`'s: this one means a recall exists on the exercise but hasn't actually been requested yet for this attempt), opens `check_out()` (`Tutor.check_recall()` is pure — same as the bot's own comment on it — so the checkout's own change-detection just skips the write), and returns `{correct, answer}` — `answer` is `shown_recall.answer[0]`, the same canonical-form index the bot's own `_highlight_diff` call uses, shown on a wrong attempt. No diff-highlighting on the web side (that's Telegram-HTML-specific) — this matches the plain "correct answer: X" line `check_answer()`'s own wrong case already shows.

`wiederholen.web.session.WebSessionStore` is a small Redis-backed store for exactly two things: which `Exercise` was last shown to a student, and (once one's been requested) which `Recall` — one JSON envelope, `{"exercise": {...}, "recall": {...} | absent}`, under one key per student (`web_session:{student_id}`, TTL'd at an hour) — the web equivalent of the Telegram bot's `shown_exercise`/`shown_recall` FSM keys, and deliberately not part of `StudentRecordBook` for the same reason the bot's own UI state isn't (see "Persistence" above): this is session/UI state, not the learning record. `check_answer()` reads `shown_exercise` to know which `Exercise` the submitted answer is actually being checked against — the DTO from `next_exercise()` never carries enough information (no `answer`) for the client to reconstruct that itself, by design; `check_recall()` reads `shown_recall` the same way, for the same reason (a `RecallDTO` never carries `answer` either). `set_shown_exercise()` always writes a fresh envelope with no `recall` key at all — a newly shown exercise means any recall left over from the previous one is no longer relevant, the same way the bot's own `last_exercise` record gets replaced wholesale on every new exercise. `get_shown_recall()`/`set_shown_recall()` are the same fetch/mutate shape as their exercise counterparts; `set_shown_recall()` asserts an exercise is already present in the envelope first, mirroring `Tutor.request_recall()`'s own `assert last_exercise is not None`.

`wiederholen/web/static/widget.js` (served at `/widget/widget.js` via `create_static_files_router()`, no build step, no dependencies) is a vanilla-JS Web Component, `<german-exercise-widget topics="partizip_ii,praeteritum" lang="ru">`, rendering into a Shadow DOM (`attachShadow({mode: "open"})`) so a landing page's own CSS can never leak in or be leaked onto — the whole reason a Web Component was chosen over an iframe: same style isolation, without the fixed-sizing/`postMessage`-resize ceremony an iframe would need. `topics` (comma-separated) is the attribute a landing page author sets per page, mapping directly onto `next_exercise()`'s topic-restricted request; `api-base` defaults to the origin the script itself was loaded from (captured once into a module-level constant while `document.currentScript` is still valid — it stops resolving the moment this file finishes its first synchronous pass, well before any element's `connectedCallback()` runs) so a page only needs to repeat the API domain explicitly if the widget script is served from somewhere other than the API itself. All `fetch()` calls pass `credentials: "include"` so the `wiederholen_student_id` cookie actually travels on the widget's cross-subdomain requests (see above for why `SameSite=Lax` already permits this).

`lang` only reaches the exercise's own content (question/description/instruction/explanation) via the API's `language` request param — the widget's own fixed chrome around it (the "Next"/"Try again" buttons, the "Correct!"/"Correct answer: …" labels, the error and "nothing available" messages) is never sent to the server at all, so it can't be localized that way. A module-level `STRINGS` object (keyed by `Language`, mirroring `wiederholen.school.i18n`'s own `ru`/`en` set) and a `_strings` getter (`STRINGS[this._language] || STRINGS.ru` — the same ru fallback `_language` itself uses, so the two never disagree about what an unset/unsupported attribute means) cover this instead — caught as a real gap, since the exercise content came back properly localized while every button/message around it stayed English regardless of `lang`.

Every color is a `:host`-scoped custom property (`--gew-fg`, `--gew-bg`, `--gew-border`, `--gew-choice-bg`, `--gew-primary`, `--gew-correct`, `--gew-wrong`), redefined wholesale under `@media (prefers-color-scheme: dark)` rather than left to inherit anything from the host page — the Shadow DOM boundary doesn't block `prefers-color-scheme` (an environment feature, not something page CSS could leak through even without encapsulation), but it does mean the widget can't read the host page's own theme variables even if it wanted to, so every one of its colors has to be self-sufficient. `.widget` and the button/input controls get an explicit `background` (`--gew-bg`/`--gew-choice-bg`) for the same reason: an earlier version left them transparent, relying on `--gew-fg`'s text color alone to look right — fine against an assumed-white host background, but on a real page using `prefers-color-scheme: dark` the near-black text rendered on the page's own near-black background, unreadable (caught from a real screenshot). Buttons/inputs also set `color: inherit` explicitly, since form controls don't inherit text color from their container by default the way most other elements do — without it they'd have silently kept light-mode-appropriate black text even once `--gew-fg` switched.

`connectedCallback()` caches the currently-shown exercise in `sessionStorage` (keyed by `topics`+`lang`, so different pages/widgets never collide) and re-renders it directly on a plain page reload instead of always spending a fresh `/api/exercise/next` call — the server's own session (`WebSessionStore`'s `shown_exercise`) hasn't moved on either at that point, since only actually submitting an answer changes it, so reusing the cached DTO client-side stays exactly consistent with what the backend still considers "shown" for this student. `sessionStorage`, not `localStorage`: it survives a reload of the same tab (the actual complaint this caches against) but clears once the tab/session ends, so a genuinely new visit just gets a fresh question with no separate expiry bookkeeping needed — that alone roughly tracks `WebSessionStore`'s own 1h TTL for the common case of reloading soon after the page was first opened; if the two ever drift apart (a tab left open past that hour, then answered), `check_answer` 409s and the learner just sees the existing error+retry path, not a crash. `_loadNext()` writes the cache on every successful fetch (or clears it for the "nothing available" `null` case), and `_submitAnswer()` clears it immediately upon getting a result — *before* rendering that result, not only when the learner later clicks "Next" — since the just-answered exercise is no longer pending, and a reload while the result screen is still showing must not resurrect it from cache and let it be answered a second time.

`_renderQuestion()`'s and `_renderResult()`'s trailing answer control/button is wrapped in a `<div class="toolbar">`, a named region `_setToolbar(html)` can replace on its own — this exists specifically for recall (below), which needs to swap the toolbar repeatedly (offer button → input form → retry-or-next) without touching the rest of the card. `_renderQuestion()`'s typed-input form calls `.focus()` on its `<input>` right after rendering, and `_renderResult()`'s (now factored into a shared `_wireNextButton()`, since a fresh "Next" button appears in several places once recall is involved — see below) does the same for the "Next" button, so Enter activates it via native `<button>` behavior — no custom keyboard handling needed. This matters because `_render()` replaces the whole shadow subtree on every step, dropping whatever had focus before the answer was submitted; without an explicit `.focus()` call, page focus falls back to `<body>`, and a `keydown` there never reaches into this element's shadow tree at all (a listener on the host element only sees events whose focused target is somewhere inside it — a first attempt at this feature used exactly such a listener and silently never fired for that reason). Both calls pass `{preventScroll: true}` — `.focus()`'s default scroll-into-view behavior would otherwise yank the whole page down to the widget the moment a fresh question loads on a page where the widget isn't already at the top (e.g. embedded partway down a landing page), which is exactly what actually happened once the widget was embedded on a real page (caught from a real report, not just a hypothetical).

**Recall** (`result.recall`, mirroring the bot's `RecallMode`: `"none"`/`"optional"`/`"required"`) is handled entirely by `_renderResult()` and two new methods, `_startRecall()`/`_submitRecallAnswer()`. The one design decision that shapes all of it: recall *appends* to the same card rather than replacing it, unlike every other step transition in the widget (`_render()` always wipes the whole shadow subtree). The bot doesn't have this problem — its UI is a persistent chat log, so a learner can always scroll up and see the original question/explanation while working through a recall step — but the widget's single replace-everything card would otherwise make the just-shown correct answer disappear the moment recall starts, with nowhere left to check what it was (confirmed with the user via a mockup, choosing this over a bot-style separate recall screen). `_appendToBody(html)` (`insertAdjacentHTML("beforeend", ...)` into `.body`, then scrolls `.body` to its new bottom so the freshly-appended content is actually visible without the learner scrolling manually) is the one piece of machinery this needs — everything recall-related is *added*, never removed, for as long as the learner stays within one exercise's answer→recall cycle; the next exercise's `_render()` call wipes it all again like normal, so this is a mini-log scoped to one cycle, not a persistent history the way the bot's chat is.

`"none"` behaves exactly as before recall existed: a plain "Next" button via `_wireNextButton()`. `"optional"` (answered correctly, a recall exists but isn't required) shows a two-button `.actions` row — `_setToolbarToActions(this._strings.recallDrill, () => this._startRecall())` — "Закрепить" alongside "Next", mirroring the bot's own `_make_recall_buttons()`, which always pairs a contextual label with "Следующее задание" the same way. `"required"` (answered wrong) calls `_startRecall()` immediately, no offer needed since it isn't optional.

`_startRecall()` (`POST /api/exercise/recall`) appends `<p class="recall-question">❓ …</p>` plus, if present, a hint line reusing `.description`'s own class (💡, muted/smaller — safe to reuse outside `.centered-pair` since that class is now purely typographic, see below) and sets the toolbar to a recall answer form, the same shape as the exercise's own typed-input form. `.recall-question` gets a `border-top` — a divider marking a new step starting, distinct from the result still fully visible above it — sized with only a small `padding-top: 0.5rem` on top of `.body`'s existing `gap: 1rem` (which already provides the space *before* the border), so it reads as a clean divider rather than a doubled gap. The input isn't `focusOnLoad`-gated the way `_renderQuestion()`'s own is (see above) — recall is always the direct result of a deliberate action (submitting the answer that triggered a required recall, or tapping "Закрепить"/"Попробовать ещё раз"), never a cold page load, the one case that gating exists to avoid. Also used for a retry (called again from `_submitRecallAnswer()`'s wrong branch): each call re-fetches via `Tutor.request_recall()`, which already excludes the immediately-previous `recall_question` when alternatives exist (see above), so a retry naturally varies like it does in the bot — and since `_startRecall()` only ever *appends*, a retry's new question/hint lands as a fresh block below the failed attempt rather than overwriting it, which is what makes a wrong-then-retry cycle actually read as a growing log.

`_submitRecallAnswer(answer)` (`POST /api/exercise/recall/check`) appends `.correct`/`.wrong` feedback (both already purely typographic classes — this is exactly why `.description`/`.correct`/`.wrong`'s styling was separated from `.centered-pair`'s positioning in the round of work just before this one, which is what makes reusing them outside a `.centered-pair` context safe here) and sets the toolbar accordingly: correct → a plain "Next" button; wrong → the same two-button `.actions` row as the optional-offer case, with "Попробовать ещё раз" as the trigger. Both `_startRecall()`/`_submitRecallAnswer()` fall back to an appended `.wrong` error line plus a plain "Next" button on a failed fetch (same `_strings.somethingWrong` text `_renderError()` uses) — never leaves the learner stuck, and (being appended, not a full-card replace) never erases the result still shown above it either.

`wiederholen/web/static/app/` (`index.html`/`app.js`, served at the root path `/` via a second `create_static_files_router(path="/", ..., html_mode=True, name="app")` — a distinct `name` from the widget's own router's default `"static"`, since Litestar requires route handler names to be unique within one app) is the standalone app: the same `<german-exercise-widget>` custom element, just as the page's main content rather than embedded partway down someone else's, and with no `topics` attribute at all — drawing from the whole course via the empty-topics handling described above, since this app has no single grammar topic of its own to scope itself to the way a landing page's embed does. It reaches `widget.js` at the plain same-origin path `/widget/widget.js` directly, unlike the content repo's landing pages: those need `widget-loader.js`'s local-vs-production runtime detection because they're served from a completely different site (GitHub Pages) that doesn't know where `wiederholen.web` lives in a given environment, but this page *is* `wiederholen.web`'s own — `widget.js` is always reachable at that fixed path in every environment, local dev included, so there's nothing to detect. `app.js` only handles the language toggle (`localStorage["wiederholen-lang"]`, `ru`/`en`); an inline `<script>` in `index.html`, placed *before* the `<script src="/widget/widget.js">` tag, applies a saved preference to the widget's `lang` attribute first — plain, static `<script>` tags execute synchronously in document order, so the attribute is already set by the time `widget.js` loads and upgrades the element, well before `app.js` (loaded last) even runs. Switching language happens by reloading the page rather than live, since the widget has no `attributeChangedCallback` reacting to a `lang` change after it's already connected, and a reload naturally gets a fresh `/api/exercise/next` call in the new language anyway. The app's own page chrome stays Russian-only for now, matching the site's broader ru-first/en-not-yet-rolled-out state — only the widget's practice content is actually bilingual here. Deliberately no marketing/promotional copy of its own (e.g. a link back to the Telegram bot, or a product/brand name in the header) — that's content, which belongs in the content repo, not this one; `index.html` here is just app shell, and its `<header>` is just the language toggle, right-aligned since it's the only thing left in it.

`german-exercise-widget { --gew-max-width: 36rem; --gew-height: 26rem; }` in `index.html`'s own CSS overrides two of `widget.js`'s `:host` custom properties (`--gew-max-width`/`--gew-height`, both default to the ~28rem/16rem a landing page's embedded widget uses) to give the standalone app a visibly bigger, more prominent practice card — this page's whole purpose is practicing, so the card should read as the focal point rather than a small aside the way it does embedded partway down an article. Custom properties inherit through the Shadow DOM boundary even though ordinary properties don't, so a host page can override just these two without forking the component or reaching inside its shadow tree; nothing else about `<german-exercise-widget>` differs between the two contexts.

The input's own `.focus()` call is additionally gated on a `focusOnLoad` parameter threaded through `_loadNext(focusOnLoad = false)` → `_renderQuestion(exercise, focusOnLoad)`, defaulting to `false` — `connectedCallback()`'s own calls (both the cache-hit `_renderQuestion(cached)` and the cache-miss `_loadNext()`) never pass it, while the Next/Retry button click handlers pass `true`. On mobile, focusing a text input pops the on-screen keyboard open immediately; that's welcome right after the learner taps a button, but not the instant the page itself finishes loading, before they've done anything at all — caught from a real mobile report of the keyboard popping up unprompted on page load. `_renderResult()`'s own Next-button focus isn't gated the same way, since it's never reached from a cold `connectedCallback()` render in the first place — only ever as the result of submitting an answer, itself already a deliberate action.

A deliberate tap on the input is a separate problem from the above: the keyboard opening is expected there, but the widget is often embedded partway down a long page, and the browser's own default scroll-to-input behavior only ever reveals the `<input>` itself — the question above it (`.body`) scrolls out of view behind the keyboard, with nothing bringing it back. `connectedCallback()` adds a `window.visualViewport.resize` listener (`disconnectedCallback()` removes it — bound once in the constructor so add/removeEventListener refer to the same function) that scrolls the whole widget into view (`this.scrollIntoView({behavior: "smooth", block: "center"})`) whenever `this._shadow.activeElement` is the answer `<input>` at the moment the resize fires. `visualViewport.resize`, not the input's own `focus` event: the keyboard's height isn't known yet the instant focus fires, only once it's actually finished opening, which is exactly when `visualViewport` itself resizes. Checking `this._shadow.activeElement` fresh on each resize, rather than a reference captured at render time, matters because `_render()` replaces the whole shadow subtree (the `<input>` included) on every step, while this listener is attached once for the widget's entire lifetime — a stale captured reference would never match a newer `<input>` element. `window.visualViewport?.` throughout, since it isn't universally available; without it this just degrades to the native scroll-to-input behavior the fix improves on, not a crash. `.widget` itself has a fixed `height: 16rem` (not just a floor — an earlier `min-height` attempt still let the box resize between differently-sized questions, just less drastically than before) with `overflow: hidden` — every step renders inside the same-sized box, so nothing about answering or advancing ever resizes the widget and jolts the surrounding page, on top of the loading-state fix above. 16rem, not the bare minimum a desktop-width embed needs: the same German sentence wraps to more lines on a narrow phone screen than on a wide desktop embed, so the box needs more headroom there — caught from a real mobile screenshot where a long `partizip_ii_meaning` question got cut off mid-sentence at 14rem. `_renderLoading()` (shared by `_loadNext()`/`_submitAnswer()`, replacing what used to be the same literal markup string duplicated in both) and the "nothing available"/error states all render with an extra `.centered` class (flex column, centered both axes) — appropriate for a short, single-purpose message inside the fixed-height box, but deliberately not applied to `.widget` generally: a real question or result should start from the top like normal reading order.

`_renderQuestion()`/`_renderResult()` each wrap their variable-length content (`instruction` + a `.centered-pair`, or a `.centered-pair` alone — see below) in a `.body` div, leaving the answer control (`.choices`/the typed-input form) or the "Next" button as a plain sibling after it — a toolbar that's never part of the scrolling region. `.body` takes `flex: 1` (claiming whatever vertical space the toolbar doesn't need, which is also what pins a short toolbar to the bottom without a separate `margin-top: auto` rule) and `overflow-y: auto` of its own; `.widget`'s own flex column also sets `gap: 1rem` between `.body` and the toolbar after it, the same value `.body` itself uses internally between `instruction` and `.centered-pair` (see below) — one shared interval for every boundary between genuinely distinct pieces of the card, not a separately-tuned value for this one specific boundary — `.widget`'s own `overflow: hidden` is deliberately not `auto` here, since scrolling the *whole* box for a too-long question used to take the answer control (and the "Next" button) out of view along with it, a real report from before this split existed. `min-height: 0` on `.body` overrides a flex item's default `min-height: auto`, which would otherwise keep it at its content's full height and defeat `overflow-y: auto` entirely — a well-known flexbox-plus-scrolling gotcha, not a redundant rule. `.body` also gets a `mask-image: linear-gradient(to bottom, black calc(100% - 0.35rem), transparent 100%)` — a soft fade at its bottom edge hinting there's more to scroll to, rather than a hard cutoff; using a mask rather than painting a color over the fade means it works regardless of the page's actual background color, since it fades this element's own content toward transparent rather than overlaying anything. Fixed at `0.35rem`, not a percentage of `.body`'s own height (an earlier version used `92%`): a percentage-based zone scales with `.body`'s own height rather than with the text it's fading — harmless for most content, which (like `.centered-pair` below) has centering slack around it and never touches the fade zone at all, but the standalone app's taller `--gew-height` card could still turn it into most of a line reading visibly faded on whichever content ends up flush against `.body`'s bottom edge (caught from a real screenshot, back when `description` itself sat flush against `.body`'s bottom by design instead of grouped with `question`). A small fixed zone keeps the softening to what it was always meant to be regardless: a few pixels of a line's own bottom edge, not the line itself.

`.centered-pair` groups a card's two central pieces of text into one visual unit that moves and centers together, rather than leaving the second one to drift off on its own — used on both screens `_renderQuestion()`/`_renderResult()` produce, not just one: on the question screen it wraps `question` + `description` (`description` is a translation of `question` into the student's language, not a how-to-answer note the way `instruction` is — the two are the same sentence in two languages); on the result screen it wraps the `.correct`/`.wrong` verdict label (the ✅/❌ line, which also names the correct answer when wrong) + `.explanation` — the label plays `question`'s role (the actual fact worth remembering, so it gets the same `font-size: 1.1em`) and `.explanation` plays `description`'s (the grammar note backing it up, sharing `description`'s own `font-size: 0.9em; color: var(--gew-muted)` rule rather than a separately-declared copy of the same values). `instruction` (question screen only, when present) stays outside the pair, rendered before it — a plain paragraph, not part of this grouping, since it's genuinely a different kind of text (guidance, not a translation or a verdict). `.centered-pair` itself takes `flex: 1` — the only growable item in `.body`'s column, `instruction` stays sized to its own content — so it claims 100% of whatever vertical space `instruction` doesn't need (all of `.body`, on the result screen, which has no `instruction` equivalent), and centers its two children as a group within that claimed space via its own nested `display: flex; flex-direction: column; align-items: center; justify-content: center; text-align: center` — the `text-align` lives here, once, rather than repeated on each child, covering both by inheritance. The `gap` between the two children is a deliberately *tighter* `0.5rem`, distinct from `.body`'s own `gap: 1rem` between `instruction`/`.centered-pair` and `.widget`'s matching `gap: 1rem` between `.body` and the toolbar after it (see above) — the larger interval separates genuinely distinct pieces of the card, while the smaller one is what visually reads as one connected thought (a line and its translation, a verdict and its explanation) rather than two unrelated ones. An earlier version kept each pair's two elements as independent siblings, the second one pinned to the bottom of `.body` on its own (first via `margin-top`/`margin-bottom: auto`, later via `flex: 1` on the first element alone) — mathematically tidy either way, but it left the second element visually stranded far from the first, with no sense the two were related at all, regardless of its own alignment (centering it in that far-away position was tried and reverted for the same reason — caught from real user reports on both the question screen and, once the same imbalance was noticed there too, the result screen). On the rare case long enough to need `.body`'s own scroll, `flex: 1` still can't shrink `.centered-pair` below its content's natural height, so it just packs at the top like a plain paragraph would — no worse than top-alignment already was, unlike plain `justify-content: center` on `.body` itself would have been (that can push a flex group's start past the scrollable area's top edge once content overflows, making the beginning of the text unreachable by scrolling — the same pitfall `.centered` avoids for the same reason elsewhere in this file). Flexbox's `gap` only inserts space *between* items that actually exist, so an exercise missing `instruction` never leaves a phantom gap where it would've been. `p`'s own default margin is plain `margin: 0` (not `0 0 0.75rem`) — every pair gets its spacing from `.centered-pair`'s own `gap` instead of a trailing paragraph margin.

`.choices` is a CSS grid (`grid-template-columns: repeat(2, 1fr)`), not `flex-wrap` — flex-wrap sizes each button to its own text, leaving column edges ragged whenever one choice is longer than a neighbor in the same row (e.g. "mein Wunsch" next to "meines Wunsches", caught from a real screenshot); grid's equal-width columns, combined with a button's default stretch to fill its own cell, keep every button in a row the same width and every column aligned regardless of how uneven the choice text lengths are. A fixed 2 columns, not `auto-fit`: nearly every real exercise has exactly 4 choices (345 of 346 in the actual course data), and `auto-fit` sized to a `minmax(7rem, 1fr)` track sometimes decided 3 columns fit the widget's own width — stranding the 4th choice alone on its own row instead of the clean 2×2 a fixed 2-column grid always gives for the common case (also caught from a real screenshot).

Three env vars, none shared with `wiederholen.bot`: `WEB_SESSION_STORAGE_URL` (own Redis DB — same three-way split reasoning as `BOT_FSM_STORAGE_URL`/`STUDENT_RECORD_STORAGE_URL`, see "Persistence" above), `WEB_ALLOWED_ORIGINS` (comma-separated, `CORSConfig(allow_origins=..., allow_credentials=True)`), `WEB_COOKIE_DOMAIN`. `STUDENT_RECORD_STORAGE_URL` itself is shared with `wiederholen.bot`, unprefixed, same reasoning as always: both frontends address the same physical store.

`create_app()` also registers `litestar.plugins.opentelemetry.OpenTelemetryPlugin(OpenTelemetryConfig())` — real auto-instrumentation (`opentelemetry-instrumentation-asgi` underneath, the same kind of third-party package `instrument_redis()`'s `RedisInstrumentor` is, not a hand-rolled equivalent of `wiederholen.bot.tracing.TracingMiddleware`) that wraps every request in a server span. Without it, every Redis call `next_exercise()`/`check_answer()` makes via `student_record_book`/`session_store` would show up as its own orphan root span instead of grouped under the request that made it — the same problem `TracingMiddleware`/`reminder.py`'s hand-rolled spans solve for their own processes (see "Tracing" above). No explicit `tracer_provider` passed to `OpenTelemetryConfig()`: like `default_tracer` elsewhere, it resolves whatever the current global provider is lazily, so this is a safe no-op until `wiederholen.web.__main__.main()`'s own `configure_tracing()` call actually installs one.

Testing `wiederholen.web` needs `litestar.testing.AsyncTestClient`, not the sync `TestClient`: the sync client serves the ASGI app through an `anyio` portal running in its own thread with its own event loop, and a Redis client whose connection pool already made contact from the outer test's loop can't be reused from a different one (`RuntimeError: ... attached to a different loop`). `tests/web/test_app.py`'s `web_app_factory` fixture depends on the `student_record_book`/`web_session_store` fixtures purely to get their DBs flushed before the test, but deliberately builds *fresh* `RedisStudentRecordBook`/`WebSessionStore` instances pointed at the same URLs for the app's own state, so the app's first real Redis command happens from whichever loop actually serves it, not the outer test's. `AsyncTestClient` also needs `base_url="https://..."` (not the default `http://`): a `Secure` cookie is never attached to a plain-`http` request by httpx's cookie jar, which would otherwise make every cookie silently vanish between requests in a test — same as a real browser would refuse to send it back over plain HTTP.
