# immer-wiederholen

Telegram bot for practicing German with multiple choice questions (aiogram, Python). Exercises and topic relations are loaded at startup from the directory set by `COURSE_PATH` env var (default: `data`) — `{COURSE_PATH}/exercises.yaml` and `{COURSE_PATH}/topics.yaml`. Bot commands: `/start`, `/wiederholen` (show a exercise with answer options), `/progress` (today's remaining/new-today counts plus a learning/mastered breakdown by word), `/language` (toggle ru/en), `/reset` (wipe the repetition schedule after an inline confirm/cancel prompt).

`data/` is gitignored and populated locally with `exercises.yaml` (the exercise database) from outside this repo. Each `Exercise` has a `word` (the specific vocabulary item it drills, e.g. a verb like `sprechen`) and a `topic` (the grammar aspect being drilled, e.g. `partizip_ii`, `preteritum`, `government`) — `topic` is a free-form string (not a fixed enum), so new topics can be introduced without needing a code change in this repo.

## Key modules

- `wiederholen.tutoring` — the tutoring domain, split by concern: `curriculum` (`Exercise`/`Recall`/`Topic`, `Course` — the loaded exercises + `word_chained_topics`/`answer_chained_topics`, see below), `journal` (`Journal` — per-user persisted state), `session` (`Mark`/`Progress`/`RecallMode`, `Tutor` — date-based repetition scheduling for one user's journal, constructed as `Tutor(course, journal)`; also owns the reminder decision, see "Reminders" below); the package's `__init__.py` re-exports all of these, so callers just do `from wiederholen.tutoring import ...`
- `wiederholen.i18n` — supported languages (`Language` type, `LANGUAGES` set)
- `wiederholen.bot` — Telegram bot implementation (aiogram); each command lives in its own module under `wiederholen.bot.commands`

## Repetition schedule

`Tutor` (in `wiederholen.tutoring.session`) tracks review scheduling in `journal["word_schedule"]` — `{"{word}": {"{topic}": {"interval_days": int, "due_date": "YYYY-MM-DD"}}}`. A schedule entry is addressed by `word` *and* `topic` (`Journal.get_schedule_entry(word, topic, ...)`), not `word` alone — so e.g. `sprechen`'s government topic (different prepositions) and its `partizip_ii` topic are scheduled independently, while exercises that intentionally share a `word` within the same topic (different prepositions of the same verb) still share one schedule entry. `next_exercise()` selects in two steps — first a due `(word, topic)` pair, then a random exercise among the (possibly several) YAML entries sharing that pair — so a pair backed by many entries (e.g. several prepositions for one verb) isn't shown more often than a pair with only one entry. The first step isn't a plain uniform pick: when both are non-empty, `next_exercise()` first picks a *category* — due review vs new — at `Tutor.REVIEW_WEIGHT` (currently 8) to 1 odds via `random.choices([due_review, new_eligible], weights=[REVIEW_WEIGHT, 1])`, then picks uniformly at random within whichever category won. This is deliberately category-first rather than a per-pair weight spread across the combined list: `_new_pairs_eligible_today()` (see below) can include every never-touched pair in the whole course whenever the daily cap hasn't been reached, easily outnumbering due reviews by hundreds to one — a per-pair weight would be swamped by sheer pool size no matter how high `REVIEW_WEIGHT` is set, while picking the category first keeps the 8:1 odds independent of how lopsided the two pools are, and the uniform pick within the category preserves random word selection across the whole course. If either category is empty, the other is used directly, no weighting needed. Falls back to a random pair among those tied for the earliest due date if nothing is due yet. `check_answer()` also records `journal["last_exercise"]["question"]`, `word`, and `topic` (alongside `answered_at`/`is_recall_optional` — `record_mark()` replaces the whole `last_exercise` record in one go, see `Journal` docstring-equivalent below; `word`/`topic` are `NotRequired` on `LastExercise` so a record from before they existed stays valid — see below), and `next_exercise()` reads them back for a three-tier repeat-avoidance ladder, via the shared `_prefer(due_review, new_eligible, predicate)` helper (filter both pools by `predicate`, but fall back to the unfiltered pools if that would leave both empty — repeating is then unavoidable, not a bug, same fallback shape at every tier):
1. Prefer a pair whose **word** differs from the last answer's word — even a due topic of the *same* word shouldn't win over an unrelated word (e.g. after answering `sprechen`'s `government`, a due `sprechen`/`partizip_ii` shouldn't be preferred over an eligible `warten` pair just because it's also "not the exact same pair").
2. Failing that (every remaining candidate shares the last word), prefer a pair that at least differs by **topic** — i.e. not the exact same `(word, topic)`.
3. Failing that too (the exact same pair is the only option), fall back to excluding same-pair candidates with a matching **question** text, once a pair is finally chosen — this tier is unchanged from before and lives separately, right where the pair gets turned into a specific `Exercise`.

This ladder exists because the question-level tier alone wasn't enough once a pair's first answer became due again the same day (see below): with `Tutor.REVIEW_WEIGHT` favoring due reviews 8:1, a freshly-answered pair could otherwise dominate the very next pick, and if it only has one YAML entry, the question-level filter has no alternative to fall back to either — so the exact same question could appear twice in a row (observed in production). Excluding by word, then by pair, heads that off before it gets anywhere near the question-level filter, without touching `REVIEW_WEIGHT` itself. This keeps repeat-avoidance entirely inside `Tutor`/`journal` — the bot layer doesn't pass or know anything about it. On a correct answer the interval doubles (capped at `Tutor.MAX_INTERVAL_DAYS`, currently 60 days); on a wrong answer it resets to 1 day (due again immediately). A pair's very first answer is an exception to the "correct → interval days out" half of that rule: `_schedule_next_repetition()` always sets `due_date` to *today*, not `today + interval`, when `is_new` is true — regardless of correctness — so a same-day correct first answer still doubles `interval_days` to 1 (per the normal formula) but doesn't get pushed a full day out; real interval-based spacing only starts from the second answer onward. This exists specifically so a brand-new learner (or one right after `/reset`) doesn't run out of due material partway through their first day just because everything they answered correctly that day — the earlier fix for the same problem (PR #109/#110's borrow-from-future fallback) was reverted for being overcomplicated; this is the simpler replacement, and it composes for free with the rest of the scheduling machinery since a same-day-due pair is `is_new=False` (`interval_days` no longer `0`) the moment it's set, so it's picked up by the ordinary `_due_review_pairs()` path like anything else — no new selection logic needed. The journal's durability depends on the FSM storage backing it — see below.

Each `ScheduleEntry` also carries an optional `introduced_at` (`"YYYY-MM-DD"`, `NotRequired` so pre-existing entries created before this field existed stay valid rather than being treated as malformed) — set once, the first time the pair is actually answered via `check_answer()`, and never overwritten after that. It's tracked independently of `due_date`/`interval_days` so it can double as a per-pair "when did I start learning this" timestamp for future stats (e.g. which words have been in progress longest), not merely as bookkeeping for the cap below.

To keep review frequency from being diluted as the course grows, `next_exercise()` also caps how many distinct never-before-answered **words** it surfaces per calendar day — deliberately per word, not per `(word, topic)` pair: a learner who answers `sprechen`'s `government` and then its `partizip_ii` on the same day has only started one new word, not two, so `Tutor._words_introduced_today()` (scanning `_word_topics`, a pair counts its word if that pair's `introduced_at` equals today) collapses pairs down to their distinct words before comparing against `Tutor.NEW_WORDS_PER_DAY` (currently 7). `Tutor._new_pairs_eligible_today()` is the resulting per-pair filter used by `next_exercise()`: a never-before-answered `(word, topic)` pair from `_available_new_pairs()` stays eligible today if its word is already among today's introduced words (no extra slot needed — this is what lets the rest of an already-started word's topics, including one just unlocked by a chain, keep flowing even once the word cap is otherwise exhausted) or if the word budget isn't exhausted yet (`len(_words_introduced_today()) < NEW_WORDS_PER_DAY`, in which case a genuinely new word may still start). `Tutor._is_new(word, topic)` — `True` when the pair has no schedule entry *or* has one with `interval_days == 0` — backs both `_available_new_pairs()` and `check_answer()`'s decision whether to stamp `introduced_at`. It deliberately checks `interval_days`, not the presence of `introduced_at`: `_schedule_next_repetition()` always sets `interval_days` to at least 1 the moment a pair is genuinely answered (correct or not), so `0` only ever occurs for a pair that's never actually been answered — including a legacy entry that predates the `introduced_at` field entirely (checking for a missing `introduced_at` instead would have wrongly re-classified every such already-in-progress pair as new the next time it's touched, both stealing a slot from the daily cap and risking its exclusion from the due pool once that cap is reached). It also matters because `_expedite_dependent()` (see chaining below) creates a schedule entry with `interval_days=0` to unlock or advance a chained/gated topic before the learner has ever actually seen it — such a pair must still count as new until it's actually answered, or unlocking it would let its word silently bypass the daily cap were it not for the word already being current. `_due_review_pairs()`/`_available_new_pairs()` split `_word_topics` along the same `_is_new()` boundary (both further filtered to `due_date <= today`) and are the shared building block for `next_exercise()`, `_due_topics_count()` (used only by `should_remind()`, see "Reminders" — deliberately not filtered through the word cap, since it only asks whether *anything* is due, not how much of it the cap would currently let through), and `progress()`'s `remaining_today` (see below) — one definition of "due review" vs "available new pair," not three. If the cap excludes every otherwise-due candidate and nothing else is due, `next_exercise()` returns `None` rather than falling back to the earliest-due tie-break (that fallback is unrelated — it's for the case where nothing is due *at all*, e.g. a brand new gated-only course); the bot layer (`command_wiederholen`/`handle_next_exercise` in `wiederholen.bot.commands.wiederholen`) shows `locale.nothing_due_text` in that case and leaves the FSM state untouched, rather than setting `UserState.answering`. `Journal.reset_schedule()` (used by `/reset`) needs no special-casing for this — wiping `word_schedule` already clears every `introduced_at` along with it.

The word cap can be lifted for the rest of the day on request: when `next_exercise()` returns `None` because the cap (not a genuine lack of due material) excluded everything, the bot shows a "study more" button (`STUDY_MORE` callback data, `wiederholen.bot.commands.wiederholen.handle_study_more`) alongside `locale.nothing_due_text`, both from `command_wiederholen`/`handle_next_exercise` and, once granted, from the shared `_respond_with_next_exercise()` helper if the raised cap still isn't enough. Clicking it calls `Tutor.grant_extra_new_words()`, which adds `Tutor.EXTRA_NEW_WORDS_GRANT` (currently 3) to `journal["extra_new_words"]` (`Journal.get_extra_new_words()`/`set_extra_new_words()`, an `{"date": ..., "count": ...}` record) — `Tutor._extra_new_words_today()` reads it back only if its `date` is today (so yesterday's grant, if any, never carries over — no explicit cleanup needed, same self-expiring pattern as `introduced_at`), and `_new_pairs_eligible_today()` adds it straight onto `NEW_WORDS_PER_DAY` when computing the day's effective cap. Grants stack with no limit on how many times a learner can click in one day — deliberately: this is an opt-in escape hatch for a learner who explicitly wants more, not something that needs its own throttle. It's stored outside `word_schedule`, so `Journal.reset_schedule()` (used by `/reset`) doesn't clear it — a leftover same-day grant surviving a same-day `/reset` is harmless (the learner already asked for more today) and it still expires naturally the next day regardless. Telegram keeps a message's inline button clickable indefinitely, so a "study more" button can still be tapped after its message is no longer current — e.g. the next day, once the cap has already reset — and unlike `NEXT_EXERCISE`/`RECALL` (whose handlers have no state that a stale tap could corrupt, they just act on whatever's true *now*), a grant is a stacking mutation, so a stale tap honored blindly would silently raise a day's cap the learner never actually asked to raise that day. `grant_extra_new_words()` guards against this at the source rather than by invalidating the button: it first checks whether today's word count has actually reached the current effective cap (`NEW_WORDS_PER_DAY + _extra_new_words_today()`) and does nothing at all — no journal write — if it hasn't, since that means the cap isn't the thing standing between the learner and more material right now (most likely because a new day reset it). A tap that arrives while the cap is genuinely still binding always goes through, whether that's the button's first day or a later same-day re-tap after actually working through the previous grant.

`request_recall()` follows the same pattern for recall variants: it records `journal["last_exercise"]["recall_question"]` and reads it back next time to exclude a matching candidate, unless that would leave no candidates. Because `record_mark()` replaces the entire `last_exercise` record on every answer, `recall_question` from a prior episode is simply absent from the new one — no explicit reset needed. This too lives entirely inside `Tutor`/`journal` — the bot layer (`_start_recall` in `wiederholen.bot.commands.wiederholen`) just calls `tutor.request_recall(exercise)` and doesn't track which variant was shown last.

`progress()` (shown by `/progress`) reports four numbers, none of them a raw `(word, topic)` pair count — the earlier design exposed `total`/`new`/`due` pair counts directly, but `due` conflated genuine overdue reviews with every never-started pair (always "due" by construction, so the number was dominated by backlog size rather than actual today's-workload) and `total`/`new` meant little to a learner who thinks in words, not word+topic pairs:
- `remaining_today` — `len(_due_review_pairs()) + _new_remaining_today()`, i.e. genuinely overdue reviews plus a *bounded estimate* of new pairs, deliberately **not** `len(_new_pairs_eligible_today())` despite `_new_remaining_today()` being named after it. `_new_pairs_eligible_today()` is `next_exercise()`'s selection pool and can legitimately include every never-touched, non-gated pair in the whole course whenever the daily cap hasn't been reached — exactly right for keeping word choice uniformly random, but wrong for a "how much is left today" number (issue #119: a learner with ~40 words in progress once saw "290 упражнений" because the pool was dominated by hundreds of untouched pairs, not real remaining work). `_new_remaining_today()` instead splits `_available_new_pairs()` by whether each pair's word is already among `_words_introduced_today()`: pairs of an already-started word count in full (uncapped — they cost no additional budget, mirroring `_new_pairs_eligible_today()`'s own "already current word" exception), while pairs of a not-yet-started word are collapsed to **one estimate per remaining budget slot** (`NEW_WORDS_PER_DAY + extra grants - words_introduced_today`, further bounded by how many such words actually exist so a small course isn't inflated up to the raw budget number) — deliberately an estimate, not an exact count, since a not-yet-started word might cascade into more than one pair once actually answered (via chains) and there's no way to predict that in advance without answering it first. This means `remaining_today` is no longer exactly "the count of exercises standing between the learner and `next_exercise()` returning `None` today" the way it once was for due reviews — the new-pair portion is now a deliberately conservative estimate, not a promise.
- `new_today` — `_new_words_introduced_today_count()` (`len(_words_introduced_today())`), how many distinct **words** already got a pair's `introduced_at` stamped today — matching the word cap it mirrors, not a raw pair count; a "progress so far" counter, complementary to `remaining_today` rather than derived from it.
- `learning`/`mastered` — bucketed by distinct **word**, not `(word, topic)` pair, since a learner thinks "I'm learning `sprechen`," not "I'm learning `sprechen`'s `government` and separately its `partizip_ii`." A word needs a rule for combining the states of its (possibly several independently-scheduled) topics: `mastered` only if *every* one of the word's topics has `interval_days >= MAX_INTERVAL_DAYS`; `learning` if the word has any schedule progress at all but isn't fully mastered yet (worst-topic-wins, not best-topic-wins — knowing a verb's `partizip_ii` well doesn't make the word "mastered" while its `government` is still barely started); a word with no schedule entries for any of its topics is counted in neither bucket (it's not being worked on yet, and unlike the old `new` bucket this is no longer surfaced as its own number).

There's no `total` anymore — it wasn't a number a learner could act on. Read-only: `progress()` never creates or mutates schedule entries, unlike `next_exercise()`/`check_answer()`.

`Course` (in `wiederholen.tutoring.curriculum`) bundles `exercises` with `word_chained_topics: dict[str, list[str]]`, `gated_topics: frozenset[str]`, `answer_chained_topics: dict[str, list[str]]`, and `topic_instructions: dict[str, dict[Language, str]]`, all derived from one gitignored file, `topics.yaml` — its absence means all four are empty, the feature is simply off. `Course.load(path)` is the usual construction path: `Course._load_exercises()`/`Course._load_topics()` are both private staticmethods, `Course.load()` is the intended public entry point. `wiederholen.bot.bootstrap.load_bot_course_and_storage()` calls `Course.load()` with the directory from the `COURSE_PATH` env var (see intro). `Tutor(course, journal)` reads the first three (`exercises`, `word_chained_topics`, `gated_topics`, `answer_chained_topics`) off the `Course` it's given — `topic_instructions` is a display-only concern the bot layer reads directly, `Tutor` never touches it (see below).

`topics.yaml` configures, per **source** topic, four independent things: `chains` (topics whose due date this source expedites once answered, keyed by the source exercise's `word`), `gates` (topics that are *also* gated — locked until this source is answered — as well as expedited via `chains`; `gates` is not a subset you repeat in `chains`, `Course._load_topics()` folds it in automatically), `chains_by_answer` (same expediting effect as `chains`, but the dependent's schedule entry is addressed by the source exercise's `answer` instead of its `word` — for a dependent topic that's about *what the source's answer represents*, not about the source's own word; e.g. `government`'s answer is a preposition like `auf`, and that preposition — not the verb being drilled — is what `preposition_meaning`/`preposition_case` are about), and `instruction` (a `{ru: ..., en: ...}` pair shown to the learner alongside exercises of this topic — see below). `Tutor` sees two separate merged results: `Course.word_chained_topics[source]` is `chains + gates` (deduplicated, order preserved, word-keyed), and `Course.answer_chained_topics[source]` is `chains_by_answer` (answer-keyed) — there's no `gates_by_answer`; an answer-chained dependent topic can still be gated, just via a `gates` entry declared under some other (word-keyed) source, since gating only checks the dependent's *topic name*, never how it was reached. `Course.gated_topics` is the flattened set of every topic that appeared in any source's `gates` list. Keeping `chains`/`gates` independent (rather than deriving "gated" from "appears as a dependent," as an earlier design did) matters for pairs like `partizip_ii`/`preteritum`, where either answered first should expedite the other but neither should be locked from the start — making both mutually gated would deadlock them (neither could ever unlock, since each is waiting on the other). The topic names themselves stay opaque to the code — `topics.yaml` is just data, so the content repo can declare new chains/gates/instructions without a code-repo change, same reasoning as `topic` itself being a free-form string (see intro).

`_format_question()` (`wiederholen.bot.commands.wiederholen`) renders two independent optional lines below the question, neither one a fallback for the other: `exercise.description[language]` (per-exercise context, e.g. a sentence the answer is drawn from) prefixed `💭`, and `course.topic_instructions.get(exercise.topic, {}).get(language)` (per-topic guidance on *how* to answer — e.g. `konjunktion_wortstellung`'s answer requires reordering several given words, not just filling in one, so it needs different guidance than a plain fill-in-the-blank topic) prefixed `ℹ️`. Deliberately no hardcoded default instruction text: a topic with nothing in `topics.yaml` simply shows no instruction line, rather than a generic one that could be wrong for its exercise format — this used to be a single locale-templated string (`Locale.description_prompt`, one fixed "enter the missing word" for every topic with a `description`) which broke down once a topic needing different guidance appeared, so it moved to `topics.yaml` for the same free-form-content reason as `chains`/`gates`.

`check_answer()` calls `_expedite_chained_topics()`, which loops `word_chained_topics.get(exercise.topic, [])` (addressing each dependent entry as `exercise.word`, `dependent_topic`) and `answer_chained_topics.get(exercise.topic, [])` (addressing each dependent entry as `exercise.answer`, `dependent_topic`), both routed through the shared `_expedite_dependent(word, topic)`: if that pair has no schedule entry yet, creates one due *today* (`interval_days=0`) — this is what makes a **gated** dependent topic (see below) reachable for the first time, and what gives either side of a *mutual* chain (see below) its one-time initial nudge. If the pair already has an entry, `_expedite_dependent()` now leaves it alone entirely, regardless of its `due_date` or a `(word, topic)` pair with no exercises at all — deliberately: once a dependent has actually been answered (`interval_days >= 1`), its own earned schedule is not something an unrelated chain trigger should override. An earlier version *did* pull an existing future `due_date` forward to today unconditionally; for a one-way chain that just made a dependent show up sooner than its own interval called for, but for a **mutual** chain (two topics each chaining to the other, e.g. `partizip_ii`↔`praeteritum`) it meant every correct answer to either topic immediately erased the other's just-earned interval through this same mechanism — trapping both in a permanent due-today loop, since `interval_days` kept growing but `due_date` never got the chance to hold (caught from a real user report: stuck re-answering the same word's `partizip_ii`/`praeteritum` pair indefinitely). This runs regardless of whether the answer was correct, and only ever affects *when* a never-yet-answered dependent first becomes eligible — once picked, it goes through the exact same `next_exercise()`/`check_answer()` path as anything else, no separate state.

A topic in `gated_topics` (e.g. `partizip_ii_meaning`, gated behind `partizip_ii`) is locked behind its source, not just expedited: `_due_date()` — for a `(word, topic)` pair with **no** schedule entry, instead of the usual `date.min` fallback (always due — the default for any brand-new word), a gated topic's pair returns `date.max` (never due) until `_expedite_chained_topics()` actually creates its entry, which only happens once its source has been answered at least once (for that same word). `next_exercise()` and `_due_topics_count()` needed no changes at all for this — they already just compare `_due_date()` against today, so a `date.max` pair simply never wins either the due-today pool or the earliest-due fallback tie-break. `progress()`'s `learning`/`mastered` buckets are unaffected by lock state (they only look at whether a word's topics have a schedule entry and their `interval_days`, not at `_get_due_date()`); `remaining_today` (via `_due_review_pairs()`/`_available_new_pairs()`, both filtered by `_get_due_date() <= today`) is affected, correctly excluding still-locked pairs.

## Tutoring events

`check_answer()` returns `tuple[Mark, list[TutoringEvent]]`, not just `Mark` — the second element is a list of plain frozen dataclasses (`ExerciseAnswered`, `TopicUnlocked`; the `TutoringEvent` union) describing what happened during the call, for observability. These live in `wiederholen.tutoring.session` alongside everything else and have zero dependency on `opentelemetry` or any other infra package — same as the rest of `wiederholen.tutoring`, which imports nothing outside the standard library and its own sibling modules. This is deliberate: deciding *what counts as a meaningful event and when it fires* is domain knowledge (e.g. `ExerciseAnswered.is_new`/`interval_days_before`/`interval_days_after` mirror exactly what `_schedule_next_repetition()` already computes; `TopicUnlocked.via` — `"chain"` vs `"gate"`, based on whether `dependent_topic in course.gated_topics` — mirrors the gating rule from the previous section), so it belongs next to the rules it's describing, not reconstructed by a caller from before/after state (which would either duplicate that logic or drift from it).

`ExerciseAnswered` always fires once per `check_answer()` call. `TopicUnlocked` fires zero or more times, one per dependent `_expedite_dependent()` actually creates an entry for (see `_topic_unlocked_event()`) — mirroring `_expedite_chained_topics()`'s existing loop exactly, just also collecting an event alongside each successful expedite instead of only mutating the journal.

The bot layer (`wiederholen.bot.tracing.record_tutoring_events()`) is a generic, semantics-free bridge: for each event, it calls `span.add_event(type(event).__name__, attributes=dataclasses.asdict(event))` on `trace.get_current_span()` (the span `TracingMiddleware` already opened for this update) — it has no `if isinstance(event, ExerciseAnswered)` branch or similar, so a new `TutoringEvent` subtype needs no bot-layer change to start showing up as span events. `Enum` fields (e.g. `ExerciseAnswered.recall_mode`) are unwrapped to their `.value` first, since an `Enum` instance isn't a valid span attribute type. `handle_answer()` (`wiederholen.bot.commands.wiederholen`) is currently the only caller — `next_exercise()`/`request_recall()` don't return events (yet); nothing about the design requires them to.

## Persistence

`wiederholen.bot` builds `dispatcher` with aiogram's default in-memory FSM storage (needed so importing the package — e.g. from tests — never depends on an external service or env var). `wiederholen.bot.bootstrap.load_storage()` constructs the real `ScanningRedisStorage` (a `RedisStorage` subclass, see "Reminders" below) from `FSM_STORAGE_URL`, required with no fallback, same as `BOT_TOKEN`. `load_bot_course_and_storage()` calls it alongside loading the bot token and exercises — both `wiederholen.bot.__main__.main()` (polling bot) and `wiederholen.bot.reminder.main()` (reminder worker) call that, so both processes always share the same storage class. Works with Valkey too (wire-compatible). `compose.yaml` (local dev, this repo) and the deployment compose file (outside this repo) both run a `valkey` service and set `FSM_STORAGE_URL` for the `bot` and `reminder` services, backed by a named volume for durability across container recreation.

Tests run against a real Redis/Valkey too, not an in-memory fake — `tests/plugins/aiogram.py::pytest_configure` pins `FSM_STORAGE_URL` to a dedicated DB number for the whole test session, before any test code runs, so the suite can never touch a DB a real dev/prod bot might be using regardless of what's set in the environment. The DB number comes from the `--fsm-storage-db-override` pytest option, defaulting to `15` (separate from dev/prod's DB 0) via `pyproject.toml`'s `addopts`; passing `--fsm-storage-db-override=""` disables the pin entirely, which the CI workflow does since its `valkey` service container is already ephemeral and tests-only, so there's no dev/prod DB to protect there. The `redis_storage` fixture (same module) calls `load_storage()` and flushes the DB before every test; the autouse `_reset_storage` fixture wires it into `dispatcher.fsm.storage`. This is deliberately fidelity-over-speed: it's still fast (no measurable slowdown at this suite's size) and catches real Redis/`KeyBuilder` behavior that an in-memory double can't (see "Reminders" below — this is exactly how a key-format bug was caught). The `redis_storage` fixture is function-scoped, not session-scoped: pytest-asyncio gives each test its own event loop by default, and a Redis connection can't outlive the loop it was created in.

## Tracing

`wiederholen.bot.tracing.TracingMiddleware` wraps every incoming Telegram update in one OpenTelemetry span — registered as `outer_middleware` on `dispatcher.update` (not `.message`/`.callback_query`) in `wiederholen/bot/__init__.py`, deliberately at the top-level "update" observer rather than the per-event-type ones. This matters because aiogram's own `Dispatcher.__init__` registers several of its own outer middlewares on `dispatcher.update` — `ErrorsMiddleware`, `UserContextMiddleware`, and `FSMContextMiddleware` (`dispatcher.fsm`) — and `FSMContextMiddleware` reads the current FSM state from storage (a Redis `GET` via `RedisStorage`) *before* routing even resolves message vs callback_query vs anything else. Outer middlewares wrap in registration order (first-registered = outermost — verified via aiogram's `MiddlewareManager.wrap_middlewares`), so registering `TracingMiddleware` on `dispatcher.message`/`.callback_query` (an earlier version of this) meant that Redis `GET` always ran *before* our span existed, showing up as an orphan root span in the backend instead of a child of the update's span — caught by directly inspecting real trace data. The fix: construct `Dispatcher(disable_fsm=True)` (which still creates `dispatcher.fsm` but skips aiogram's own auto-registration of it as outer middleware) and register `TracingMiddleware` on `dispatcher.update` first, then `dispatcher.fsm` second — so our span now wraps the FSM state lookup too. Confirmed empirically both ways: pointed a live dispatcher at real Redis with an in-memory span exporter and checked parent/child span IDs directly, rather than trusting the theory. `dispatcher.fsm.storage = storage` (set later in `main()`, see "Persistence") still works exactly as before — `disable_fsm` only skips the auto-registration, not the middleware's existence.

The module-level `_describe()` function unwraps `update.event` (aiogram's own property for "whichever event type is actually set on this Update") and builds the span name/attributes from it: `"telegram.message"` with `telegram.chat_id` and, only if the text is a bot command (starts with `/`), `telegram.command` — deliberately never the raw free-text an exercise answer might contain; `"telegram.callback_query"` with `telegram.chat_id` (from `event.message`, guarded by `isinstance(..., Message)` since Telegram can hand back an `InaccessibleMessage` for an old message) and `telegram.callback_data` (always one of this codebase's own fixed constants — `NEXT_EXERCISE`/`RECALL`/`STUDY_MORE`/etc. — never free text, so safe to record outright). Any other update type (this bot doesn't handle any, but Telegram can still deliver e.g. `poll_answer`/`my_chat_member`) falls back to a generic `"telegram.update"` span with no attributes, rather than the middleware raising for a type it doesn't special-case.

The SDK wiring is separate from the middleware itself: `TracingMiddleware` takes an injectable `tracer` (defaulting to `tracing.default_tracer`, a module-level `trace.get_tracer(__name__)` obtained *before* any provider is configured) — this is the standard OTel pattern, since `get_tracer()` returns a proxy that starts delegating to a real provider the moment one is registered, so it's safe to grab at import time. `configure_tracing()` (which builds the real `TracerProvider` + `BatchSpanProcessor(OTLPSpanExporter())` and calls `trace.set_tracer_provider()`) is called only from `wiederholen.bot.__main__.main()` and `wiederholen.bot.reminder.main()`, never at import time — so importing `wiederholen.bot` (e.g. from tests) still has no external dependency (same reasoning as the in-memory FSM storage default, see "Persistence" above): without a configured provider, spans are inert no-ops. `configure_tracing()` itself is a no-op (`_otlp_endpoint_configured()` returns `False`, checked before touching anything else) unless `OTEL_EXPORTER_OTLP_ENDPOINT` or `OTEL_EXPORTER_OTLP_TRACES_ENDPOINT` is actually set — deliberately: `OTLPSpanExporter()` on its own defaults to `http://localhost:4318` (the standard convention for a local collector sidecar), which this project's plain docker-compose deployment never has, so without an explicit endpoint that default is never valid; without this check, `configure_tracing()` would still build a real `TracerProvider`/`BatchSpanProcessor` that spends its life retrying a doomed export in the background (confirmed: `BatchSpanProcessor` logs `Transient error ... Connection refused` repeatedly and `Failed to export span batch` on shutdown) purely as log noise, never actually breaking anything since it fails closed rather than raising. `configure_tracing()` passes `Resource.create()` no explicit attributes at all — deliberately: every other piece of this config (endpoint, headers, protocol) is 100% env-var-driven with no code-level default, so `service.name`/`service.namespace`/etc. follow the same rule via `OTEL_SERVICE_NAME`/`OTEL_RESOURCE_ATTRIBUTES`, falling back to the OTel SDK's own generic `"unknown_service"` if genuinely unset. A hardcoded fallback name was tried and dropped: it actively hid a real misconfiguration (the `reminder` service briefly missing its `OTEL_*` env vars in `compose.override.yaml` — see below) by making its spans look identically labeled to the bot's instead of standing out as unconfigured. Tests exercise `TracingMiddleware` by constructing it directly with a throwaway `TracerProvider`/`InMemorySpanExporter` (`tests/bot/test_tracing.py`) rather than touching the process-global provider, since `trace.set_tracer_provider()` can only ever succeed once per process — a second call is a silent no-op, which would make per-test isolation impossible if tests relied on the global registration instead.

`tests/plugins/tracing.py::pytest_configure` forces `OTEL_SDK_DISABLED=true` for the whole test session, before any test code runs — same rationale and shape as `tests/plugins/aiogram.py::pytest_configure` pinning `FSM_STORAGE_URL` to a dedicated DB (see "Persistence" above): `docker compose run bot pytest` shares the `bot` service's config with the real bot, so without this, a real `OTEL_EXPORTER_OTLP_ENDPOINT`/`HEADERS` set for local dev (e.g. real Honeycomb credentials via `compose.override.yaml`, see below) would mean every test run actually exports real spans to that backend — confirmed by temporarily pointing the endpoint at an unreachable address and watching `BatchSpanProcessor` retry and fail to export at process exit (`TracerProvider` registers an `atexit` handler that flushes on shutdown by default). `OTEL_SDK_DISABLED` is read by `TracerProvider.__init__` itself — regardless of whether it's the global provider or a one-off instance a test constructs directly — so it also disables the throwaway `TracerProvider`/`InMemorySpanExporter` `tests/bot/test_tracing.py`'s `middleware` fixture builds to verify span content; that fixture explicitly opts back in with `monkeypatch.delenv("OTEL_SDK_DISABLED", raising=False)` before constructing its own provider, scoped to just those tests via `monkeypatch`'s automatic teardown.

`compose.override.yaml` (gitignored, local-only, also used to bind-mount the private content repo's `data/`) sets `OTEL_SERVICE_NAME`/`OTEL_RESOURCE_ATTRIBUTES`/`OTEL_EXPORTER_OTLP_*` per service (`bot`/`reminder` each get their own `OTEL_SERVICE_NAME` so their spans are distinguishable in the backend) — this needs its own `environment:` block under *each* service key, since Compose merges `environment` per-service, not globally; a service with no block simply gets none of these vars and `OTLPSpanExporter()` silently falls back to `http://localhost:4318`, which just fails every export in a container with no local collector. A stray `=` inside a YAML mapping *key* (e.g. `OTEL_RESOURCE_ATTRIBUTES=:` instead of `OTEL_RESOURCE_ATTRIBUTES:`) is a related trap worth knowing about: Compose doesn't error on it, it silently becomes part of the *value* instead (`docker compose config` is the way to check what actually gets resolved) — which for `OTEL_RESOURCE_ATTRIBUTES` manifests as a leading `=` that makes the first `key=value` pair parse with an empty key, logged by `opentelemetry/attributes` as `invalid key `` `.

`instrument_redis()` wraps `opentelemetry.instrumentation.redis.RedisInstrumentor().instrument()` — third-party auto-instrumentation that monkeypatches `redis`'s command execution (both the sync client and the `redis.asyncio.Redis` aiogram's `RedisStorage` actually uses, see "Persistence" above) to emit a span per Redis call, with no code changes needed at any call site. It's idempotent (a repeat call just logs a warning and no-ops) like `set_tracer_provider()`, which matters because both it and `configure_tracing()` get called on every `main()` invocation, including the repeated ones in `tests/bot/test_main.py`/`tests/bot/test_reminder.py` within a single test session. Both `wiederholen.bot.__main__.main()` and `wiederholen.bot.reminder.main()` call `configure_tracing()` and `instrument_redis()`, since both processes talk to Redis through `ScanningRedisStorage`. The `TracingMiddleware`-per-update span coverage above is bot-only (the reminder worker has no aiogram routers to wrap) — but `wiederholen.bot.reminder` gets its own hand-rolled equivalent instead of going without: `tick()` wraps its whole sweep in a `"reminder.tick"` span (via the same `tracing.default_tracer` `TracingMiddleware` uses) and `_remind_chat()` wraps each chat's check in a nested `"reminder.check_chat"` span (`telegram.chat_id` attribute, plus `reminder.sent` — `False` by default, flipped to `True` only once `bot.send_message()` actually succeeds) — without this, every Redis call `iter_fsm_data()`/`_remind_chat()` makes would otherwise show up as an orphan root span per call, one per sweep-chat, with no way to see which chat or sweep it belonged to. A chat whose processing raises still gets its exception recorded on `reminder.check_chat` automatically (the exception propagates out through the `with` block before `tick()`'s own `except Exception` catches it and logs), same mechanism as `TracingMiddleware`.

## Reminders

A separate worker process (`python -m wiederholen.bot.reminder`, its own `reminder` service in this repo's `compose.yaml` and in the deployment compose file) nudges users who've gone quiet with material due — not an in-process `asyncio` task in the polling bot, specifically to avoid leaking an uncancelled background task across `tests/bot/test_main.py`'s repeated `main()` calls.

`Tutor` owns the decision, journal-backed like the rest of its scheduling state: `check_answer()` records `journal["last_exercise"]["answered_at"]` (a timestamp, part of the same `last_exercise` record as `question`) — "activity" means answering the main exercise specifically, not any interaction with the bot (recall answers don't count). `Tutor.should_remind()` is a pure query — no side effects — returning `True` only if `_due_topics_count() > 0`, `last_answered_at` is ≥`Tutor.REMIND_AFTER` (24h) old, and there hasn't already been a reminder since that last answer (`last_reminded_at is None or last_reminded_at < last_answered_at`) — this last condition means exactly one reminder per period of inactivity, not a repeating nag. `Tutor.record_reminder_sent()` is a separate method, called by the bot layer only *after* a Telegram send actually succeeds — `should_remind()` itself never mutates the journal, so a failed send never gets wrongly marked as delivered.

The worker has no separate registry of known chats — `wiederholen.bot.redis_storage.ScanningRedisStorage` (a `RedisStorage` subclass) adds `iter_fsm_data(bot_id)`, which enumerates every chat with FSM data via a real Redis `SCAN` and returns each chat's data alongside its id. It doesn't assume any particular `KeyBuilder` format: it builds a marker `StorageKey` (`chat_id`/`user_id` set to sentinel strings — `KeyBuilder.build()` only ever does `str(key.chat_id)`, so this works despite the declared `int` type) and derives both the SCAN glob pattern and a parsing regex from whatever comes back, rather than hardcoding `DefaultKeyBuilder`'s shape. `wiederholen.bot.reminder.tick()` calls this once per sweep, then for each chat with `Tutor.should_remind()` true sends `locale.reminder_text` and calls `record_reminder_sent()`; one chat raising (e.g. malformed journal data) is caught and logged, not fatal to the sweep. `run()` loops `tick()` every `POLL_INTERVAL_SECONDS` (15 min).

## Commands

All commands run inside the Docker container:

```bash
docker compose run --rm bot <command>
```

Examples:
- `docker compose run --rm bot ruff check . --fix`
- `docker compose run --rm bot ty check .`
- `docker compose run --rm bot uv add <package>`
- `docker compose run --rm bot pytest`
