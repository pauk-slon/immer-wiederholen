# immer-wiederholen

Telegram bot for practicing German with multiple choice questions (aiogram, Python). Exercises and topic relations are loaded at startup from the directory set by `COURSE_PATH` env var (default: `data`) — `{COURSE_PATH}/exercises.yaml` and `{COURSE_PATH}/topics.yaml`. Bot commands: `/start`, `/wiederholen` (show a exercise with answer options), `/progress` (today's remaining/new-today/answered-today counts plus a learning/mastered breakdown by word), `/language` (toggle ru/en), `/reminders` (how long after the last session to send a reminder, or turn reminders off — see `docs/bot.md`), `/topics` (choose which topic groups exercises come from, see `docs/bot.md`), `/reset` (wipe the repetition schedule and today's answer stats after an inline confirm/cancel prompt).

The course format (`exercises.yaml`, `topics.yaml`, `bot.yaml`, every exercise field and topic setting) is documented for course authors in `docs/course-format.md` — read it before changing `wiederholen.school.curriculum`'s fields or loading, and update it (plus `demo/`, which `tests/school/test_demo_course.py` checks still uses every field and setting) along with any format change. `demo/` is the default local course (`compose.yaml` sets `COURSE_PATH: ${COURSE_PATH:-demo}`); the real content lives in a separate private repo, bind-mounted to the gitignored `data/` with `COURSE_PATH: data` in `compose.override.yaml`. The code's own default stays `data`, which is what production relies on.

Every environment variable, the processes, and the optional integrations (Anthropic, R2/Workers AI, OpenTelemetry, feature flags) are documented for operators in `docs/configuration.md` — update it along with any new or renamed env var.

## Key modules

The package map, the dependency rules between `wiederholen.school`, `wiederholen.bot`, `wiederholen.web` and `wiederholen.tracing`, the processes, and where each piece of state lives are in `docs/architecture.md` — read it before adding a module or making one package import another. The rules that matter most: `school` never imports a frontend or reads env vars (the cue generator's `__main__` excepted); `tutoring` does no I/O; `bot` and `web` never import each other. Every `wiederholen.bot` handler resolves the `StudentID` it addresses `StudentRecordBook` with via `StudentIdentityStore` (see `docs/storage.md`), never from the chat directly.

## Persistence and student identity

`StudentRecordBook` (the per-student record `Tutor` works on), aiogram's FSM storage (everything else per Telegram chat), and `StudentIdentityStore` (login → `StudentID`) are documented in `docs/storage.md`, including the test setup against real Redis — read it before touching any store or adding per-chat or per-student state. The invariants that matter most:

- Every handler opens exactly one `async with student_record_book.check_out(student_id) as student_record:` per request and does its replies inside it; `check_out()` saves only if the record changed, in a `finally`, so there's no explicit save anywhere.
- Every bot handler gets its `student_id` from `student_identity_store.resolve_or_create_student_id("telegram", str(chat_id))` (callback handlers: `str(callback.from_user.id)`, the same value in a private chat).
- The student record holds only learning state; chat settings and conversation state stay in FSM data. A new chat-level setting belongs in `_CHAT_SETTINGS_KEYS`.
- `Tutor` never touches a store — it gets a plain `dict`.
- `check_out()` isn't atomic across concurrent updates for the same student: last write wins (#249). Don't rely on two handlers for one student seeing each other's changes.

## Tracing and tutoring events

What's traced (span names and attributes per process, `Tutor`'s span events), how it's wired, and how tests check span content are in `docs/tracing.md` — read it before adding a span, an attribute or a tutoring event. The rules that matter most:

- `TracingMiddleware` is registered on `dispatcher.update` *before* `dispatcher.fsm` (the dispatcher is built with `disable_fsm=True` for this); swapping them makes the FSM's Redis read an orphan root span.
- Never record free text a learner typed — only commands and the bot's own callback-data constants.
- `Tutor` reports events by calling `wiederholen.school.tutoring.events.emit()` with a frozen dataclass at the point they happen; they're not returned to callers. `tutoring` may use the OpenTelemetry *API* only, never the SDK.
- New spans come from `wiederholen.tracing.default_tracer`, named `area.action`, with namespaced attributes (`telegram.*`, `reminder.*`, `client.error.*`); outgoing HTTP calls (Telegram, Anthropic, R2, Workers AI) aren't instrumented.
- `configure_tracing()`/`instrument_redis()` are called only from the three `main()`s, never at import time. Tests must not use the global provider: use the `tracer`/`exporter` fixtures from `tests/plugins/tracing.py`.

## Telegram bot

Commands, how a question is rendered, chat settings (`/topics`, `/reminders`, `/language`, `/ai`), the reminder worker, blocked chats, pending inline buttons, feature flags and grammar-class hints are documented in `docs/bot.md` — read it before touching `wiederholen.bot`. The rules that matter most:

- Every message sent with an inline keyboard is followed by `remember_buttoned_message()`; a callback handler that removes its own buttons and attaches none calls `forget_buttoned_message()`; every typed command calls `clear_stale_buttons()` first. When editing a message's text, pass `reply_markup=` explicitly.
- `_format_question()` sends HTML: every piece of authored text goes through `html.escape()`.
- The reminder decision stays in `Tutor.should_remind()` (pure); `record_reminder_sent()` only after Telegram accepted the message.
- Topic selection narrows what's *shown* (`/wiederholen`, next/study-more buttons, reminders), never `/progress` or answer checking.
- `bot_blocked` is set from both `my_chat_member` and a 403 on send; the reminder skips such chats before touching the record.
- Feature flags stay in the bot layer; `wiederholen.school` never sees a chat id or flag name.

## AI-generated exercises

MVP preview step for a possible AI-personalized-exercises freemium feature (GitHub issue #122): an `/ai` toggle, gated behind the `ai_exercises` feature flag (see `docs/bot.md`) and invisible to everyone else, switches a chat between the normal exercise flow and one where `question`/`explanation` are generated on the fly by an LLM instead of coming from `exercises.yaml`.

`wiederholen.school.authoring.generate_shadow_exercise(client, exercise, course, *, authoring_guide=None) -> Exercise` takes a real `Exercise` already selected by `Tutor.next_exercise()` and returns a "shadow" copy — same `word`/`topic`/`answer`/`distractors`/`recalls`, AI-written `question`/`explanation` — via `dataclasses.replace(exercise, question=..., explanation=..., ...)` (`Exercise` is a frozen dataclass, so this is the natural way to get a modified copy, and `__post_init__` validates the result for free — e.g. that `explanation` has both `ru`/`en` keys). Keeping everything except the wording untouched means correctness (does the answer fit, are the distractors actually wrong) is guaranteed by construction, not by trusting the model's German grammar. `wiederholen.school.authoring` is a package (`shadow_exercises.py` for this function, `cues.py` for its sibling — see "Visual cues for exercises" below), a sibling of `tutoring` under `wiederholen.school` rather than inside it specifically so `Tutor`/`StudentRecord` never gain a network dependency (see "Key modules" above) — `session.py`/`student_record.py` don't import either submodule, and nothing about scheduling changes: `check_answer()` only ever reads `word`/`topic`/`answer` off whatever `Exercise` it's given, never `question`, so a shadow exercise flows through `check_answer()`/`request_recall()` identically to a real one once it's in `shown_exercise` state.

`description` (the `preposition_meaning`-style disambiguating translation of the target sentence, shown before answering — see the content repo's own authoring guide) is regenerated too, but only conditionally: it's carried over into `dataclasses.replace()` only when `exercise.description is not None`, and the prompt only asks for a replacement (and the tool schema only requires one) in that case. This isn't optional polish — it was a real bug caught from a live test: `question`/`explanation` used to be the only fields replaced, so a `preposition_meaning` exercise's `description` kept describing the *original* sentence's meaning after the model wrote a brand-new one (observed in production: a new question about apples coming from the garden, paired with a leftover description translating "the table is made of wood") — exactly the mismatch a description exists to prevent in the first place. A topic whose exercises never carry a `description` (the vast majority) is unaffected either way, since `exercise.description is None` for them and the field is never mentioned to the model at all.

The prompt sent to the model (Anthropic Messages API, `AsyncAnthropic`, model pinned to `claude-haiku-4-5-20251001` via the `MODEL` constant) has two parts: an optional cached system block — the full "Exercises" section of the content repo's own `CLAUDE.md` authoring guide, if `authoring_guide` is provided, marked `cache_control: {"type": "ephemeral"}` so repeated calls within a testing session mostly hit Anthropic's prompt cache instead of reprocessing the whole guide each time — and a user message with up to three few-shot examples of real `question`s sharing the target exercise's `topic` (`course.exercises` filtered by topic, excluding the target itself), plus the target's own `word`/`topic`/`answer`/`distractors`. The model is forced to respond via tool use (`tool_choice={"type": "tool", "name": "submit_shadow_exercise"}`) with a `{question: str, explanation: {ru: str, en: str}}` schema, rather than parsing free text — `generate_shadow_exercise()` pulls the `ToolUseBlock` out of the response, validates its `input` shape, and raises `AIGenerationError` (defined alongside it) for anything that goes wrong: the API call itself failing, no tool-use block in the response, missing/wrong-typed fields, or an `explanation` that fails `Exercise.__post_init__`'s own validation. There's no fallback to the real exercise on failure anywhere — `AIGenerationError` always surfaces as `locale.ai_generation_failed` to the learner, deliberately: this is a testing tool for one person, so a silent fallback would risk masking a broken integration behind human-authored questions that look perfectly normal; a visible failure is what lets a tester actually notice and either retry or turn `/ai` back off.

Both the Anthropic client and the guide text are optional, loaded once at startup by `wiederholen.bot.bootstrap.load_anthropic_client()`/`load_authoring_guide()` and threaded through `dispatcher.start_polling()` as `anthropic_client`/`authoring_guide` workflow data, the same mechanism `course`/`feature_flags` already use. Neither is required the way `BOT_TOKEN` is: `ANTHROPIC_API_KEY` unset means `load_anthropic_client()` returns `None` rather than failing startup (only the one flag-gated test chat ever needs it), and `AUTHORING_GUIDE_PATH` unset means `load_authoring_guide()` returns `None` and generation just runs on few-shot examples alone (same "absence means the feature is off" pattern as `topics.yaml`).

`command_ai` (`wiederholen.bot.commands.ai`) is a bare toggle, no arguments, mirroring `/language`'s own shape: reads `ai_mode` out of FSM state as a plain top-level key (like `language`, not nested in `student_record`, so it survives `/reset`), flips it, and replies with `locale.ai_mode_on`/`ai_mode_off`. It no-ops entirely — no reply, no state change — for any chat `has_feature(feature_flags or {}, "ai_exercises", ...)` doesn't cover, the same invisible-unless-flagged shape `command_wiederholen`'s own flag check point uses; like the other four command entry points, it calls `clear_stale_buttons()` first.

`ai_mode` is meant to stay on for a whole session, not just the one exercise it was toggled before — but `handle_answer()`/`handle_recall()` both end an exercise's conversation state with `state.clear()`, which wipes the entire FSM data dict. Both go through `_clear_keeping_chat_settings(state, state_data)` instead of a bare `clear()`: it clears, then restores every key in `_CHAT_SETTINGS_KEYS` (`language`, `ai_mode`, `topic_groups` — chat-level settings, as opposed to per-exercise conversation state like `shown_exercise`/`shown_recall`) from the `state_data` read beforehand. An earlier version re-added `ai_mode` by hand at each of four separate `update_data()` call sites (and threaded it through `_start_recall()` as a parameter); missing one of them (caught from a real user report) meant AI mode silently reverted to off after exactly one exercise — a tester would just see human-authored questions again and have no idea why. Centralizing it was prompted by `topic_groups` becoming a third such setting with exactly the same failure mode. A new chat-level FSM setting belongs in `_CHAT_SETTINGS_KEYS`.

Generation is further scoped **per topic**, not just per chat: `Course.ai_generatable_topics: frozenset[str]` (parsed from `topics.yaml`'s new per-source `ai_generation: true` key, alongside `chains`/`gates`/`chains_by_answer`/`instruction` — same opt-in-by-absence shape, a topic with no entry or `ai_generation` unset/false is simply not eligible) exists because the "swap `question`/`explanation`, leave everything else untouched" correctness argument only holds for topics whose `answer` is grammatically independent of the exact sentence wording. It breaks down for topics where the question's *exact form* encodes part of the answer: `partizip_ii`/`praeteritum`'s `question` is a fixed `"verb → form"` template, not a sentence, so there's nothing meaningful to rewrite; `konjunktion_wortstellung`/`nebensatzkonjunktion_wortstellung` has an `Exercise.word_bank` that `answer` is a specific reordering of (see below) — a rewritten sentence with different words would leave the old `word_bank`/`answer` matching nothing; `praesens_vokalwechsel`'s `answer` depends on which subject (`du`/`er`-`sie`-`es`) the sentence uses — a model free to pick a different subject while rewriting could produce a sentence whose grammatically correct answer no longer matches the untouched `answer` it's paired with. Both `command_wiederholen` and `_respond_with_next_exercise()` compute this per-exercise, after `next_exercise()` has actually picked one (topic isn't known any earlier): `ai_mode = ai_mode and exercise.topic in course.ai_generatable_topics` — reusing the `ai_mode` name for the narrowed, per-exercise value rather than introducing a second variable, since nothing downstream in either function needs the raw chat-level toggle separately. A topic outside the allowlist behaves exactly as if `ai_mode` were off for that one exercise: the real `question`/`explanation` show through, no `🤖` marker, no API call — not an error, since this is a known, static scope limit rather than a runtime failure.

`_apply_ai_mode()` (`wiederholen.bot.commands.wiederholen`) is the shared decision point both `command_wiederholen` and `_respond_with_next_exercise()` (so both `handle_next_exercise` and `handle_study_more`, which share it) call right after `tutor.next_exercise()` finds a real exercise: if `ai_mode` is off, the exercise passes through untouched; if it's on, it calls `generate_shadow_exercise()` and returns the shadow — or `None`, both when `anthropic_client` is `None` (flag on but not configured) and when generation raises `AIGenerationError`, collapsing both failure modes into one signal the caller reacts to identically (show `locale.ai_generation_failed`, leave FSM state untouched, same as the existing "nothing due" early-return shape). `next_exercise()` itself does no student_record writes (confirmed: no `schedule_pair()`/`_get_or_create_schedule_entry()` calls anywhere in it), so picking an exercise and then bailing out for an AI failure has nothing to roll back.

`_format_question()` takes an `is_ai_generated` keyword-only flag (default `False`) that prefixes the rendered text with `🤖 ` ahead of the `❓` question line — both call sites already have the `ai_mode` boolean in hand (the one `_apply_ai_mode()` was just called with) and pass it straight through, so a shadow exercise is visually distinguishable from a real one at a glance, since nothing else about the message (buttons, reply keyboard, `💭`/`ℹ️` lines) differs between the two.

`Exercise.word_bank: list[str] | None` (`wiederholen.school.curriculum`) is the structured word-order data for `konjunktion_wortstellung`/`nebensatzkonjunktion_wortstellung` exercises: `answer`'s own words, grouped into meaningful phrase chunks (e.g. `"in Hamburg"` stays one chunk, not two — confirmed against the real content data, true for the large majority of these exercises) in the *correct*, unscrambled order. `__post_init__` validates `" ".join(word_bank) == answer` when set, the same kind of authoring-drift check `answer`-in-`distractors`/`explanation`/`description` keys already get. This replaced an earlier design (issue #191) where the scrambled hint was hand-authored prose baked directly into `question` (`'...sondern ___. (in Hamburg / wohnt / sie)'`) — no single source of truth, kept in sync with `answer` by hand, with nothing to validate it. `question` no longer carries this parenthetical at all once an exercise has `word_bank`; both frontends reconstruct it fresh instead: `curriculum.shuffle_word_bank(word_bank) -> list[str]` is one shared shuffle-with-reshuffle-if-unchanged implementation (reshuffles if `shuffle()` happens to land back on the original order — real for a short sentence, and the learner should never be handed an already-solved bank; a single-chunk `word_bank` has no other permutation to land on, so it's returned as-is instead of looping forever) that both `wiederholen.bot` (re-inserts the shuffled chunks as a `" (a / b / c)"` parenthetical after the question, in `_format_question()` — reproducing exactly the old visual shape, just computed fresh on every render instead of frozen at authoring time) and `wiederholen.web` (renders them as tap-to-arrange tiles, see below) call rather than each keeping its own copy. `word_bank` truthiness is the only signal either frontend needs — no separate `topics.yaml` flag exists for this (an earlier draft had one, `Course.word_order_topics`; dropped once `word_bank` itself became the self-describing signal, the same convention `choices: null` already uses for a typed-input exercise). `Tutor` never touches this field — deciding *how to render* an exercise stays a frontend concern, not a scheduling one.

## Visual cues for exercises

`_meaning`-topic exercises (`preposition_meaning`/`partizip_ii_meaning`/`praeteritum_meaning`) test understanding of a concrete sentence — a manually-piloted illustration (picked by hand via an external image generator, before any of this existed) suggested a relevant image plausibly helps recall for exactly this kind of exercise, via dual coding: a picture and the sentence it depicts reinforce each other, unlike a purely decorative image would. Named "cue" throughout, not "image": the point is a *retrieval cue* for the sentence, not a generic visual asset. Pure-grammar-form topics (`verb_case`, `partizip_ii`, word-order topics, ...) are deliberately excluded — there's no scene to illustrate for "which case does this verb govern".

`Course.cue_generatable_topics: frozenset[str]` (`wiederholen.school.curriculum`, parsed from `topics.yaml`'s per-source `cue_generation: true` key) gates eligibility per topic, the same opt-in-by-absence shape as `ai_generatable_topics` right above — a deliberately *separate* decision from whether a given exercise happens to carry a `description`, even though today the two coincide for every eligible topic: `description` exists for an unrelated reason (the disambiguating translation shown before answering), and conflating "has a description" with "should get a cue" would silently turn cues on for any future topic that grows a `description` for some other reason.

`Exercise.cue_key: str` (a computed property, not a stored field) is `hashlib.sha256(question.encode()).hexdigest()` — the single place this derivation lives, so `wiederholen.school.authoring.cues.__main__` (the worker, which uploads under this key) and `wiederholen.school.cue_store` (which looks it up at render time) can never disagree about what an exercise's key is. Keyed by `question`, not `word`+`topic`: several exercises in one `_meaning` topic can share a word while each describing a distinct, separately-illustrated sentence. A consequence accepted rather than worked around: editing `question` later (as the `word_bank` migration did, for unrelated topics) changes this hash, silently orphaning whatever cue was generated for the old wording — safe (never a mismatched cue shown against a different sentence), just means the worker needs a re-run after a content edit that touches wording.

`wiederholen.school.authoring.cues` (a sibling of `authoring.shadow_exercises`, see "AI-generated exercises" above) generates the actual image: `build_cue_prompt(exercise) -> str | None` returns `None` when `exercise.description` is absent (nothing to build a prompt from — the real gate is `cue_generatable_topics`, but a topic could in principle have an eligible exercise without one) and otherwise `exercise.description["en"]` plus a fixed style suffix (`", simple clear illustration, single scene, no text or letters in the image"` — appended to every prompt for visual consistency across the set, and specifically to stop the model from rendering in-image text at all, which image models frequently garble and which would otherwise risk baking incorrect German into the picture itself). `generate_exercise_cue(client, exercise, *, account_id, api_token) -> bytes | None` calls `build_cue_prompt()` and, if it got a real prompt, POSTs to Cloudflare Workers AI's REST API for `@cf/black-forest-labs/flux-1-schnell` (chosen for cost: 10,000 free Neurons/day — in practice about 90 images/day at 1024×1024, so a full run over the `_meaning` corpus takes a few days, each run picking up where the quota cut the last one off) and returns the decoded image bytes, raising `httpx.HTTPError` on a failed call or an unrecognized response shape. Cloudflare's response wraps the base64-encoded image as `{"result": {"image": ...}}` per its usual envelope, but this specific model's docs only ever show the bare `{"image": ...}` shape — `result = data.get("result", data)` checks both rather than assuming one. No Anthropic client involved here at all: Anthropic doesn't do image generation, so this is a wholly separate provider/credential from the shadow-exercise generation above, despite living in the same package.

`wiederholen.school.cue_store` holds the storage side — interface and implementation together in one module, the same shape `student_record_book.py` already uses for `StudentRecordBook`/`RedisStudentRecordBook`, since there's only one real backend and no reason to force an interface/implementation split before a second one exists. `CueStore` (ABC) declares `get_cue_url(exercise) -> str | None` and `upload_cue(exercise, image_bytes) -> None`. `R2CueStore` implements it against Cloudflare R2 (an S3-compatible bucket, chosen over a self-hosted alternative since the project's own Cloudflare account already covers domain/Zero Trust, and R2's free tier/no-egress-fees pricing covers this data volume for free either way) via `aioboto3` (an async S3 client, matching the rest of the codebase's async style — plain `boto3` is sync-only): `get_cue_url()` does a `head_object` and returns `f"{public_url_base}/{exercise.cue_key}"` if found, `None` on a 404 (identified by the response's own status code — `head_object`'s 404 comes back as a generic `ClientError`, not a dedicated exception class the way `get_object`'s does); `upload_cue()` does a plain `put_object`. `CachedCueStore` wraps another `CueStore` with a 12-hour in-process TTL cache (`dict[str, tuple[str | None, datetime]]`, keyed by `cue_key`) — chosen over checking R2 on every render specifically to keep that off the bot's hot path; a *negative* result (no cue yet) is cached exactly like a real URL, which means a newly-uploaded cue can take up to the TTL to actually start appearing for a question rendered just before the upload — an accepted tradeoff, not a bug, for never hitting R2 per-render. A plain dict needs no external storage: `wiederholen.bot` runs as a single polling process, unlike `StudentRecordBook`/`WebSessionStore`, which are per-student data that must survive a restart.

The worker is `wiederholen.school.authoring.cues.__main__` (`python -m wiederholen.school.authoring.cues`) — the `cues` package's own entry point, not a top-level sibling of `bot`/`web` (where it first lived, as `wiederholen.cues`): it isn't another frontend for the same learning logic, just a content-authoring tool, so it belongs next to the generation code it drives. It's the one place under `wiederholen.school` that reads `os.environ` itself — everything else there gets its dependencies passed in — accepted since nothing imports a `__main__`, so the rest of `school` stays as it was. `cues` is a package rather than a single `cues.py` with an `if __name__ == "__main__"` block because `wiederholen.school.authoring.__init__` imports from it: `python -m` on a module its parent package has already imported runs the file a second time as a separate copy (runpy's "found in sys.modules" `RuntimeWarning`), whereas a package's `__init__` never imports its `__main__`. It's a one-shot CLI run on demand whenever content changes, not a standing service like `wiederholen.bot.reminder` — new exercises are added rarely, at content-authoring time, so there's nothing here worth polling for the way reminders are time-sensitive. `run()` loads the `Course`, filters to `exercise.topic in course.cue_generatable_topics`, and for each: checks `get_cue_url()` first (a single cheap `head_object`, before spending a Workers AI call) and skips if already present; else calls `generate_exercise_cue()` and uploads the result if non-`None`. One combined summary line (generated/already-had-one/no-description/failed counts) is logged at the end — there's no automated approval gate on what gets uploaded, so this summary is what the person who just ran it actually reads afterward to spot-check the result themselves, consistent with this being a small personal-project pipeline rather than a reviewed content pipeline.

`wiederholen.bot`'s rendering side: `bootstrap.load_cue_store() -> CueStore | None` builds a `CachedCueStore(R2CueStore(...))` from `R2_ACCOUNT_ID`/`R2_ACCESS_KEY_ID`/`R2_SECRET_ACCESS_KEY`/`R2_BUCKET`/`R2_PUBLIC_URL_BASE`, `None` if `R2_ACCOUNT_ID` is unset — same "absence means off" shape as `load_anthropic_client()`, threaded through `dispatcher.start_polling()` as `cue_store` workflow data the same way. `commands/wiederholen.py`'s `_answer_with_optional_cue(target, text, exercise, course, cue_store, **kwargs)` replaces the plain `target.answer(text, **kwargs)` call at both places a question gets sent (`command_wiederholen`, `_respond_with_next_exercise` — shared by `handle_next_exercise`/`handle_study_more`): if `cue_store` is set, `exercise.topic` is in `course.cue_generatable_topics`, and `text` fits Telegram's 1024-character photo caption limit (well below the 4096 a plain message gets — `_format_question()`'s word_bank parenthetical/description/instruction lines can in principle push a question past it), it looks up `get_cue_url()` and sends `answer_photo(url, caption=text, **kwargs)` instead of plain text when found. The lookup is wrapped in a bare `try`/`except Exception`, logged and swallowed — the same best-effort shape as `clear_stale_buttons()`'s own `TelegramBadRequest` swallowing — so an R2 hiccup degrades to the plain-text question rather than ever blocking a learner from practicing.

## Telegram login

`wiederholen.web`'s one shared cookie slot (`_student_id_from_request()`/`_remember_student_id()`/`_remember_browser_login()` in `app.py`) carries two different kinds of value, disambiguated by a prefix check: an anonymous `WebStudentID`'s own `web:` token (see above), or a `browser:{token}` value minted by `telegram_login_callback()` below. Deliberately not `student:{student_id}` (an earlier version of this): a logged-in cookie never carries the real `student_id` at all, only an opaque per-browser credential resolved through `StudentIdentityStore` the same way a Telegram `chat_id` is — `"browser"` is a second `AuthProvider` alongside `"telegram"`, added for exactly this, and `StudentIdentityStore.resolve_student_id(provider, identifier) -> StudentID | None` is a resolve-*only* sibling to `resolve_or_create_student_id()` (same `_get()` primitive underneath, just never falling through to `_create_if_absent()`) added alongside it — a `browser:` token existing at all already implies a real login happened somewhere to link it, so minting a fresh student on a miss would be wrong the way it isn't for `"telegram"`. This is the same account/credential split `docs/storage.md` draws for every other provider: the cookie in the browser is a credential, never the account id itself, so a compromised or leaked cookie value doesn't hand over the permanent `student_id` directly, and a future "log out this browser" flow would just be `link_identity`'s row for `("browser", token)` going away, no `student_id` rotation needed. `telegram_login_callback()`/`_remember_browser_login()` always mints a brand-new `secrets.token_urlsafe(32)` and `link_identity()`s it to the resolved `student_id` — never reuses whatever `browser:` token the incoming request already carried, since that token might already be linked to a *different* student (a previous login, on a shared or reused browser) and `link_identity()` raises `IdentityAlreadyLinkedError` rather than silently reassigning it. `_student_id_from_request()` checks for the `browser:` prefix *before* falling through to `WebStudentID.validate()`, and resolves the token via `resolve_student_id()` — a miss (stale store, tampered value) falls through to a fresh anonymous `WebStudentID` exactly like a foreign/garbage `web:`-shaped cookie already does, rather than either trusting it as a literal id or, worse, minting a phantom new account for it. This tagging is deliberately not "anything that isn't `web:`-prefixed is a real login" — that was tried first and reverted (`test_next_exercise_treats_a_foreign_cookie_as_a_new_visitor` catches exactly this): it would blindly trust *any* foreign or garbage cookie value as a legitimate `StudentID`, not just genuine ones this module minted itself.

`GET /api/auth/telegram/callback` is a sixth endpoint, the target of a [Telegram Login Widget](https://core.telegram.org/widgets/login) button (see `widget.js` below) — deliberately not OIDC/OAuth: Telegram has no real standards-based identity provider, just this one bespoke, redirect-based HMAC scheme (`wiederholen/web/telegram_login.py`'s `validate_telegram_login()`), itself a different scheme again from a Mini App's own `initData`, which this codebase doesn't implement. `hash = HMAC-SHA256(data_check_string, SHA256(BOT_TOKEN))`, `data_check_string` being every other field sorted and joined `key=value` with `\n` — `validate_telegram_login()` raises `InvalidTelegramLoginError` for a bad signature *or* an `auth_date` older than a day (stale/replayed callback URLs, e.g. one saved in browser history). `BOT_TOKEN` is why `wiederholen.web` needs it at all now (`load_bot_token()`, required, no fallback, same as `wiederholen.bot`'s own) — not to call the Bot API, just to check this one signature.

On success, `telegram_login_callback()` calls the exact same `StudentIdentityStore.resolve_or_create_student_id("telegram", str(telegram_user_id))` `wiederholen.bot` calls for every message — this is the entire point: a learner who's chatted with the bot and then logs into the web app with the same Telegram account lands on the same `student_id`, same progress, no separate account. `return_to` (a query param the widget adds itself, *not* one of Telegram's own signed fields — popped off the payload before `validate_telegram_login()` ever sees it, or its mere presence would change the `data_check_string` Telegram itself never signed over) lets the redirect land back on whichever page the login button was actually clicked from, not always the API's own root — `_safe_redirect_target()` only honors it if it's a same-origin relative path (`/...`, explicitly rejecting the `//host/...` protocol-relative form, a real open-redirect vector that passes a naive `startswith("/")` check) or an absolute URL whose origin is already in `WEB_ALLOWED_ORIGINS`; anything else falls back to `/` rather than sending a visitor to an attacker-chosen destination reflected straight off their own request.

`wiederholen/web/static/widget.js`'s `<german-exercise-widget>` gains two attributes for this, off by default like `recall`: a bare `login`, plus `telegram-bot="BotUsername"` naming which bot (the component has no single bot baked in). `_renderLoginButton()` constructs Telegram's own `<script data-telegram-login=... data-auth-url=...>` via `createElement()`/`setAttribute()`, not an HTML string — a `<script>` tag inserted via `innerHTML`/`insertAdjacentHTML` never executes, by design, in every browser. This is also why `_render()` — previously the single "wipe the whole shadow root and rebuild" entry point — now only replaces `.deck`'s own contents: `_render()` runs on *every* exercise (a fresh question, a result, an error), and re-running `_renderLoginButton()` that often would re-fetch Telegram's widget script and flicker the button on every single interaction. `connectedCallback()` now builds a small persistent shell once (`<style>` + an empty `[data-login-container]`) before ever calling `_render()`, and `_renderLoginButton()` renders into that container exactly once per connection — `_render()` only ever touches its own `.deck` sibling from then on. No client-side "am I already logged in" check gates the button itself: clicking it while already logged in just re-resolves the same `student_id`, which is harmless, so simplicity won over hiding a button that's still safe to click.

The standalone app (`index.html`) is the one place actually setting `login`+`telegram-bot="ImmerWiederholenBot"` today, same bot-parity reasoning as its own `recall` attribute — a landing page's embedded widget could opt in too, but only on a domain actually registered for this bot via BotFather's `/setdomain` (Telegram ties the whole widget to one specific domain; there's no way to register several).

`create_app()` also registers `litestar.plugins.opentelemetry.OpenTelemetryPlugin(OpenTelemetryConfig())` — real auto-instrumentation (`opentelemetry-instrumentation-asgi` underneath, the same kind of third-party package `instrument_redis()`'s `RedisInstrumentor` is, not a hand-rolled equivalent of `wiederholen.bot.tracing.TracingMiddleware`) that wraps every request in a server span. Without it, every Redis call `next_exercise()`/`check_answer()` makes via `student_record_book`/`session_store` would show up as its own orphan root span instead of grouped under the request that made it — the same problem `TracingMiddleware`/`reminder.py`'s hand-rolled spans solve for their own processes (see `docs/tracing.md`). No explicit `tracer_provider` passed to `OpenTelemetryConfig()`: like `default_tracer` elsewhere, it resolves whatever the current global provider is lazily, so this is a safe no-op until `wiederholen.web.__main__.main()`'s own `configure_tracing()` call actually installs one.

Testing `wiederholen.web` needs `litestar.testing.AsyncTestClient`, not the sync `TestClient`: the sync client serves the ASGI app through an `anyio` portal running in its own thread with its own event loop, and a Redis client whose connection pool already made contact from the outer test's loop can't be reused from a different one (`RuntimeError: ... attached to a different loop`). `tests/web/test_app.py`'s `web_app_factory` fixture depends on the `student_record_book`/`web_session_store`/`student_identity_store` fixtures purely to get their DBs flushed before the test, but deliberately builds *fresh* `RedisStudentRecordBook`/`WebSessionStore`/`RedisStudentIdentityStore` instances pointed at the same URLs for the app's own state, so the app's first real Redis command happens from whichever loop actually serves it, not the outer test's. `AsyncTestClient` also needs `base_url="https://..."` (not the default `http://`): a `Secure` cookie is never attached to a plain-`http` request by httpx's cookie jar, which would otherwise make every cookie silently vanish between requests in a test — same as a real browser would refuse to send it back over plain HTTP.

All commands run inside the Docker container — `docker compose run --rm bot <command>` (`pytest`, `ruff format .`, `ruff check . --fix`, `ty check .`, `uv add <package>`). Testing and pull request conventions are in `CONTRIBUTING.md`.
