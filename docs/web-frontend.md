# Web frontend

`wiederholen.web` (Litestar) is a second delivery mechanism for the same `wiederholen.school` domain — a sibling of `wiederholen.bot`, not a dependency of it or vice versa. Runs as its own `web` service (`python -m wiederholen.web`, `compose.yaml`), separate from `bot`/`reminder`. Two frontends share its one backend: an embeddable widget (a landing page names specific grammar topics for its own page) and a standalone app (no fixed topics of its own — see below for both).

`wiederholen.web.web_student_id.WebStudentID` is the anonymous half of `_student_id_from_request()`'s two-way cookie (see "Telegram login" in `CLAUDE.md` for the other): no login of any kind, so there's no provider/identifier pair to resolve. `WebStudentID.generate() -> StudentID` mints a fresh, unguessable random token (`secrets.token_urlsafe(32)`) tagged with its own `web:` prefix, and `WebStudentID.validate(raw) -> StudentID` checks an incoming value actually carries that prefix, raising `NotAWebStudentIdError` for anything that doesn't (a cookie from a different frontend sharing the same `StudentRecordBook`, a stale/foreign value, or a client that sent garbage — all of which fall through to minting a fresh anonymous id, same as never having a cookie at all). A first-time visitor gets a `wiederholen_student_id` cookie set by the server on their first response (`HttpOnly`, `Secure`, `SameSite=Lax`, `Domain` configured via `WEB_COOKIE_DOMAIN`) — deliberately server-chosen and unguessable rather than a client-generated id, so one visitor can't address another's record by picking the same value. `Domain` is expected to be the landing page's own parent domain (e.g. `example.com`, with the widget served from a subdomain like `app.example.com`) — same-site under the modern `SameSite` cookie model, so `Lax` is enough to have the cookie sent on the widget's cross-subdomain fetch calls without needing `SameSite=None` and the third-party-cookie restrictions that comes with.

`wiederholen.web.app` has four endpoints: `POST /api/exercise/next` (body: `{topics: list[str], language?}`), `POST /api/exercise/check` (body: `{answer: str, language?}`), `POST /api/exercise/recall` (body: `{language?}`), and `POST /api/exercise/recall/check` (body: `{answer: str}`) — the last two are the recall equivalents of the first two, see below. `next_exercise()` builds `course.restricted_to(data.topics)` (see `docs/repetition-schedule.md`) and calls `Tutor(restricted_course, student_record).next_exercise()` — the topic restriction is per-request, not baked into any stored state, so the same student's `student_record` carries their real progress across every page/widget they've ever used, even though any one request only ever sees the slice of the course its own page is about. An empty `topics` list is a deliberate exception to that: `next_exercise()` uses the whole `course` unrestricted rather than calling `restricted_to([])`, which would otherwise filter every exercise out (an empty `frozenset` matches no topic) — this is what lets the standalone app (below) draw from the entire course without needing to know or send every topic name up front, unlike a landing page's embedded widget, which always names its own specific topics. The response DTO (`ExerciseDTO`) never includes `answer` — multiple-choice `choices` are `distractors + [answer]` shuffled, and a typed-input exercise (empty `distractors`) gets `choices: null`, telling the widget to render a text field instead of buttons.

`ExerciseDTO.word_bank: list[str] | None` is set only when `exercise.word_bank` itself is (see "AI-generated exercises" in `CLAUDE.md` for where that field comes from and why there's no separate `topics.yaml` flag) — `shuffle_word_bank(exercise.word_bank)` shuffles a fresh copy for this response. This needed no change to `check_answer()`/`Tutor.check_answer()` at all: reassembling the tiles in the correct order and joining with `" "` reconstructs `answer` exactly (`Exercise.__post_init__` already guarantees `" ".join(word_bank) == answer`), so the widget just submits that joined string through the existing `/api/exercise/check` the same as any typed answer — the whole feature is a rendering choice, not a new answer-checking path. Left `None` for every other exercise, same convention `choices` already uses for a typed-input one.

`request_recall()`/`check_recall()` mirror `Tutor.request_recall()`/`check_recall()` directly, the same pairing `next_exercise()`/`check_answer()` already follow. `request_recall()` reads `shown_exercise` from the session store (409 if none, same shape as `check_answer()`'s own), opens `student_record_book.check_out()`, and calls `Tutor(course, student_record).request_recall(exercise)` — this is where the bot's own recall side effects already live (recording the shown `recall_question` for repeat-avoidance, and halving a pair's repetition interval the first time an *optional* recall is requested for it — see `docs/repetition-schedule.md`), so nothing web-specific was needed to get them; the result is stored via `session_store.set_shown_recall()` and returned as `RecallDTO{question, hint}` (`hint` localized to the request's `language`, `null` if the recall has none). Called once per recall step, including retries — each call re-picks via `request_recall()`, which already excludes the immediately-previous `recall_question` when alternatives exist, so a retry naturally varies like it does in the bot. `check_recall()` reads `shown_recall` (409 if none — a *different* 409 from `request_recall()`'s: this one means a recall exists on the exercise but hasn't actually been requested yet for this attempt), opens `check_out()` (`Tutor.check_recall()` is pure — same as the bot's own comment on it — so the checkout's own change-detection just skips the write), and returns `{correct, answer}` — `answer` is `shown_recall.answer[0]`, the same canonical-form index the bot's own `_highlight_diff` call uses, shown on a wrong attempt. No diff-highlighting on the web side (that's Telegram-HTML-specific) — this matches the plain "correct answer: X" line `check_answer()`'s own wrong case already shows.

`POST /api/client-error` (body: `{step: str, status: int | None}`) is a fifth endpoint, deliberately unlike the other four: it's not part of the exercise flow, just a fire-and-forget diagnostic beacon `widget.js`'s own `_reportClientError(step, error)` calls from every one of its four `catch` blocks (`_loadNext`/`_submitAnswer`/`_startRecall`/`_submitRecallAnswer` — `step` is one of those exact names, a fixed set the client itself chooses from, never free text) whenever a fetch fails, with `status` carrying the failed request's own HTTP status when there was a response at all (`null` for a fetch that never got one — offline, DNS, timeout). Before this, a real client-side failure was visible only as a raw access-log line (the failed request's own status) with no way to tell what the learner's browser actually did next short of manually reproducing it — this happened for real (a `409` on `/api/exercise/check`, the stale-session case `_submitAnswer()`'s own catch above already handles, see its comment) and took a manual Playwright repro to diagnose. The handler itself does two things with the report: `logger.warning(...)` (mirrors the bot/reminder's own `logging.warning()` convention, for the same signal without needing Honeycomb access) and `trace.get_current_span().set_attribute(...)` — no manual span creation needed, since this request already gets its own auto-instrumented span via `OpenTelemetryPlugin` (see below) the same as every other route, so the attributes just need attaching to it. This reuses the project's existing OTel/Honeycomb pipeline rather than adding a second, disconnected tool (e.g. Sentry) for frontend errors specifically — one place to look for a problem that can span both sides, not two. `_post()`'s own thrown `Error` carries `status` as a real property (`Object.assign(new Error(...), { status: response.status })`), not just interpolated into the message string, so `_reportClientError()` can report it as an actual number the server can query on. `_reportClientError()` itself is `.catch(() => {})`-guarded — a failure to *report* an error must never itself become a new user-facing error, so its own result is never awaited or otherwise allowed to affect what the caller does next.

`wiederholen.web.session.WebSessionStore` is a small Redis-backed store for exactly two things: which `Exercise` was last shown to a student, and (once one's been requested) which `Recall` — one JSON envelope, `{"exercise": {...}, "recall": {...} | absent}`, under one key per **(student, topics)** pair (`web_session:{student_id}:{sorted-joined-topics}`, TTL'd at an hour) — the web equivalent of the Telegram bot's `shown_exercise`/`shown_recall` FSM keys, and deliberately not part of `StudentRecordBook` for the same reason the bot's own UI state isn't (see "Persistence" in `CLAUDE.md`): this is session/UI state, not the learning record. Every public method (`get_shown_exercise`/`set_shown_exercise`/`get_shown_recall`/`set_shown_recall`) takes `topics: Sequence[str]` alongside `student_id`, sorted before joining into the key so ordering never matters. This *isn't* keyed by `student_id` alone (an earlier version was): the `wiederholen_student_id` cookie is shared across every page on a domain, so a student browsing two different landing pages (different `topics`, each with its own embedded widget) in the same sitting would otherwise share one slot between them — visiting page B between loading page A's question and answering it would silently overwrite what `check_answer()` compares page A's answer against, reporting "incorrect" and citing page B's answer as correct even for a genuinely correct answer (caught from a real user report, and exactly reproduced by `test_check_answer_is_scoped_to_its_own_topics`). The topics segment mirrors `widget.js`'s own client-side `sessionStorage` cache key (`topics`+`lang`, see below) — two pages with the *same* topics still share a slot, which is fine, since they're the same widget in every way that matters; `language` itself isn't part of the server-side scope, since it only affects which translation of an already-decided `Exercise` is returned, never which `Exercise` is picked. `check_answer()` reads `shown_exercise` (now via its own `topics` field, see below) to know which `Exercise` the submitted answer is actually being checked against — the DTO from `next_exercise()` never carries enough information (no `answer`) for the client to reconstruct that itself, by design; `check_recall()` reads `shown_recall` the same way, for the same reason (a `RecallDTO` never carries `answer` either). `set_shown_exercise()` always writes a fresh envelope with no `recall` key at all — a newly shown exercise means any recall left over from the previous one is no longer relevant, the same way the bot's own `last_exercise` record gets replaced wholesale on every new exercise. `get_shown_recall()`/`set_shown_recall()` are the same fetch/mutate shape as their exercise counterparts; `set_shown_recall()` asserts an exercise is already present in the envelope first, mirroring `Tutor.request_recall()`'s own `assert last_exercise is not None`.

`CheckAnswerRequest`, `RecallRequest`, and `CheckRecallRequest` each gained their own `topics: list[str]` field (defaulting to `[]`, mirroring `NextExerciseRequest.topics`'s own shape) purely to identify *which* `WebSessionStore` slot a given call means — unlike `NextExerciseRequest.topics`, this one is never used to restrict a `Course` (these three endpoints never call `next_exercise()`), only forwarded straight into the matching `session_store` call. `widget.js` sends its own `this._topics` on every one of these calls now, not just `/api/exercise/next`'s — the same value on every request from one widget instance, which is exactly what keeps its calls addressing one consistent slot throughout an exercise's lifecycle.

`wiederholen/web/static/widget.js` (served at `/widget/widget.js` via `create_static_files_router()`, no build step, no dependencies) is a vanilla-JS Web Component, `<german-exercise-widget topics="partizip_ii,praeteritum" lang="ru">`, rendering into a Shadow DOM (`attachShadow({mode: "open"})`) so a landing page's own CSS can never leak in or be leaked onto — the whole reason a Web Component was chosen over an iframe: same style isolation, without the fixed-sizing/`postMessage`-resize ceremony an iframe would need. `topics` (comma-separated) is the attribute a landing page author sets per page, mapping directly onto `next_exercise()`'s topic-restricted request; `api-base` defaults to the origin the script itself was loaded from (captured once into a module-level constant while `document.currentScript` is still valid — it stops resolving the moment this file finishes its first synchronous pass, well before any element's `connectedCallback()` runs) so a page only needs to repeat the API domain explicitly if the widget script is served from somewhere other than the API itself. All `fetch()` calls pass `credentials: "include"` so the `wiederholen_student_id` cookie actually travels on the widget's cross-subdomain requests (see above for why `SameSite=Lax` already permits this).

`lang` only reaches the exercise's own content (question/description/instruction/explanation) via the API's `language` request param — the widget's own fixed chrome around it (the "Next"/"Try again" buttons, the "Correct!"/"Correct answer: …" labels, the error and "nothing available" messages) is never sent to the server at all, so it can't be localized that way. A module-level `STRINGS` object (keyed by `Language`, mirroring `wiederholen.school.i18n`'s own `ru`/`en` set) and a `_strings` getter (`STRINGS[this._language] || STRINGS.ru` — the same ru fallback `_language` itself uses, so the two never disagree about what an unset/unsupported attribute means) cover this instead — caught as a real gap, since the exercise content came back properly localized while every button/message around it stayed English regardless of `lang`.

Every color is a `:host`-scoped custom property (`--gew-fg`, `--gew-bg`, `--gew-border`, `--gew-choice-bg`, `--gew-primary`, `--gew-correct`, `--gew-wrong`), redefined wholesale under `@media (prefers-color-scheme: dark)` rather than left to inherit anything from the host page — the Shadow DOM boundary doesn't block `prefers-color-scheme` (an environment feature, not something page CSS could leak through even without encapsulation), but it does mean the widget can't read the host page's own theme variables even if it wanted to, so every one of its colors has to be self-sufficient. `.card` and the button/input controls get an explicit `background` (`--gew-bg`/`--gew-choice-bg`) for the same reason: an earlier version left them transparent, relying on `--gew-fg`'s text color alone to look right — fine against an assumed-white host background, but on a real page using `prefers-color-scheme: dark` the near-black text rendered on the page's own near-black background, unreadable (caught from a real screenshot). Buttons/inputs also set `color: inherit` explicitly, since form controls don't inherit text color from their container by default the way most other elements do — without it they'd have silently kept light-mode-appropriate black text even once `--gew-fg` switched.

`connectedCallback()` caches the currently-shown exercise in `sessionStorage` (keyed by `topics`+`lang`, so different pages/widgets never collide) and re-renders it directly on a plain page reload instead of always spending a fresh `/api/exercise/next` call — the server's own session (`WebSessionStore`'s `shown_exercise`) hasn't moved on either at that point, since only actually submitting an answer changes it, so reusing the cached DTO client-side stays exactly consistent with what the backend still considers "shown" for this student. `sessionStorage`, not `localStorage`: it survives a reload of the same tab (the actual complaint this caches against) but clears once the tab/session ends, so a genuinely new visit just gets a fresh question with no separate expiry bookkeeping needed — that alone roughly tracks `WebSessionStore`'s own 1h TTL for the common case of reloading soon after the page was first opened; if the two ever drift apart (a tab left open past that hour, then answered), `check_answer` 409s and the learner just sees the existing error+retry path, not a crash. `_loadNext()` writes the cache on every successful fetch (or clears it for the "nothing available" `null` case), and `_submitAnswer()` clears it immediately upon getting a result — *before* rendering that result, not only when the learner later clicks "Next" — since the just-answered exercise is no longer pending, and a reload while the result screen is still showing must not resurrect it from cache and let it be answered a second time.

`_renderQuestion()`'s and `_renderResult()`'s trailing answer control/button is wrapped in a `<div class="toolbar">`, a named region `_setToolbar(html, card = this._currentCard)` can replace on its own — this exists so a step's toolbar can change (offer button → input form → retry-or-next) without touching the rest of that card, and so recall's own cards (below) can each get their own toolbar independently. `_renderQuestion()`'s typed-input form calls `.focus()` on its `<input>` right after rendering, and `_wireNextButton()` (a fresh "Next" button appears in several places once recall is involved — see below) does the same for whichever "Next" button it just wired, so Enter activates it via native `<button>` behavior — no custom keyboard handling needed. This matters because both `_render()` (a fresh deck) and `_addCard()` (a fresh card within the existing deck — see below) drop whatever had focus before; without an explicit `.focus()` call, page focus falls back to `<body>`, and a `keydown` there never reaches into this element's shadow tree at all (a listener on the host element only sees events whose focused target is somewhere inside it — a first attempt at this feature used exactly such a listener and silently never fired for that reason). Both calls pass `{preventScroll: true}` — `.focus()`'s default scroll-into-view behavior would otherwise yank the whole page down to the widget the moment a fresh question loads on a page where the widget isn't already at the top (e.g. embedded partway down a landing page), which is exactly what actually happened once the widget was embedded on a real page (caught from a real report, not just a hypothetical).

**The deck.** Every step of one exercise's cycle — the question, the result, a recall question, a recall result — is its own separate `.card`, laid out side by side in a horizontally-scrollable `.track` and clipped to one card's width by the outer `.deck` (`height: var(--gew-height)`, `overflow: hidden`). `.card` is exactly what the whole widget used to be (border, radius, padding, background, the `.body`+`.toolbar` flex column, `overflow: hidden`) — a rename, not a redesign, of the pre-deck `.widget`. `.track` uses native CSS `scroll-snap-type: x mandatory` (each `.card` gets `scroll-snap-align: start`) so swiping or trackpad-scrolling always lands cleanly on a card boundary with no JS-driven carousel logic at all; its own scrollbar is hidden (`scrollbar-width: none` plus the WebKit pseudo-element), since two small circular `.deck-nav` arrow buttons — absolutely positioned at `.deck`'s left/right edges, styled from the same `--gew-*` tokens as everything else — are the intended visible control instead, alongside the swipe/scroll gesture itself.

This replaced an earlier design where a recall step *appended* into the same card that showed the result, separated by a divider — the user didn't like the look (a chat-transcript-in-a-box feel) and asked for each step to read as its own card instead, with some intuitive way to move between them; a swipeable deck with arrows, confirmed via discussion and an `AskUserQuestion` choice between swipe-only/dots/arrows, is what replaced it. The underlying problem that design was solving is still solved here, just differently: the bot's UI is a persistent chat log, so a learner can always scroll up to see the original question/explanation while working through a recall step, and the widget's own single-card-at-a-time model would otherwise make that content disappear the moment a new step starts — now it doesn't disappear, it's just one swipe/arrow-click away instead of always on screen at once.

`_addCard(html)` is the step-transition primitive `_appendToBody()` used to be: `insertAdjacentHTML("beforeend", ...)` onto `.track` (not `.body`), then `track.scrollTo({ left: newCard.offsetLeft, behavior: "smooth" })` to bring the new card into view, then `_updateDeckNav()`. Before inserting, it also **freezes** the *previous* current card's toolbar — clears it outright (`toolbar.innerHTML = ""`), not just disables it — so a step that's been superseded can never have its controls triggered a second time. This isn't just tidiness: `check_answer()` isn't idempotent, so a learner swiping back to the original question and tapping a choice button again would record a real second mark against the same pair in `student_record`; a stale "Закрепить"/retry button would similarly kick off a redundant recall. A frozen card still shows its full content, just with nothing left to click — read-only history, not a second live control surface. `_render(cardHtml)` is the complementary, everything-wiping entry point (a fresh `.deck`/`.track` holding just one card, plus both `.deck-nav` buttons, wired via `_wireDeckNav()`) — still correct, and still used, wherever there's a genuinely *new* exercise starting and nothing from before is worth keeping: `_loadNext()`'s loading/error/nothing-available states and its first successful `_renderQuestion()` call. `get _currentCard()` (`.track`'s `lastElementChild`) is what `_setToolbar()`/`_wireNextButton()`/`_setToolbarToActions()` all default to now that a deck can hold several `.toolbar`s at once — a bare, unscoped `this._shadow.querySelector(".toolbar")` would otherwise match the *first* one in document order, not necessarily the current step.

`_wireDeckNav()` (called once per `_render()`, not per card) attaches the two arrows' click handlers — each just `track.scrollBy({ left: ±track.clientWidth, behavior: "smooth" })` — and a `scroll` listener on `.track` that calls `_updateDeckNav()` on every scroll position change, whether it came from a click, a swipe, or a trackpad gesture; none of the latter two go through `_addCard()` at all, so this is the only way the arrows' own state stays in sync with those. `_updateDeckNav()` hides both arrows outright (the plain `hidden` attribute, not just a visual/disabled state) whenever `track.scrollWidth <= track.clientWidth` — no overflow, nothing to page through — which is true for two states, not just one: a freshly loaded, not-yet-answered question, and the result card right after answering (`_renderResult()` itself `_render()`s a fresh single-card deck for the result — see below), since neither has any sibling card yet. Only once a recall step actually starts (`_addCard()`-ing onto that result card) does the deck grow past one card, and each arrow hides itself specifically at its own end (`prev` at `scrollLeft <= 0`, `next` at the opposite edge) from then on, with a ±1px slack absorbing sub-pixel scroll-position rounding. `.deck-nav`'s own `display: flex` has the same specificity as the browser's built-in `[hidden] { display: none }` rule, and author styles beat the user-agent stylesheet regardless of selector order — an explicit `.deck-nav[hidden] { display: none; }` is needed to make the `hidden` attribute actually take effect (caught from a real screenshot: a "next" arrow rendering always-visible, including on the deck's own last card, right where there's nothing to go next to).

`_renderResult()` itself calls `_render()`, not `_addCard()` — the one place besides a genuinely new exercise that resets the deck rather than adding to it. The question card is no longer useful once answered (its fill-in-the-blank prompt is superseded by the actual answer sitting right there in the result), and its choice buttons/typed-input form being frozen (per `_addCard()`'s own freezing, which no longer applies here since there's no *previous* card at all now) would make swiping back to it show dead controls for no benefit — caught from a direct user report. Recall cards still `_addCard()` onto *this* result card once one exists, so the deck still grows from here on — only the *question* is dropped, not the reviewability recall itself needs.

`"none"` behaves exactly as before recall existed: a plain "Next" button via `_wireNextButton()` on the result card. `"optional"` (answered correctly, a recall exists but isn't required) shows a two-button `.actions` row on that same result card — `_setToolbarToActions(this._strings.recallDrill, () => this._startRecall())` — "Закрепить" alongside "Next", mirroring the bot's own `_make_recall_buttons()`, which always pairs a contextual label with "Следующее задание" the same way. `"required"` (answered wrong) shows a *single* "Закрепить" button that calls `_startRecall()` on click — deliberately not an immediate call the way an earlier version did: triggering it right as the result card was still finishing its own scroll-into-view meant the ❌ and its explanation flashed by almost too quickly to actually read before the deck auto-advanced a second time, and that explanation is exactly what the upcoming recall step needs (caught from a direct user report). Reusing `recallDrill`'s exact label rather than a separate string for this single-button case is deliberate too — it's already the same action ("move into the recall step") the optional-offer button uses, and the surrounding wrong-answer context already supplies whatever "you need to do this" framing the bare label doesn't carry on its own; alternatives ("Далее", too close to the existing but differently-acting "Дальше"; a brand new word) were considered and dropped for exactly that reason.

Every button-only toolbar state — not just the two-button recall-offer/retry case `.actions` was first built for — goes through the *same* `.actions` grid now, via `_primarySlot(buttonHtml)` (`` `<div class="actions">${buttonHtml}</div>` ``): a bare "Дальше" (the `"none"` case above, and every error fallback below), and the required-recall case's single "Закрепить", all wrap their one button this way instead of rendering it bare directly into `.toolbar`. `.actions`'s own `display: grid; grid-template-columns: 1fr 1fr;` combined with `.actions > button:only-child { grid-column: 1 / -1; }` is what spans a lone button across both columns (full width) rather than leaving it sized and positioned by plain block flow, which used to put it flush against `.toolbar`'s left edge. That read fine for a bare "Дальше" on its own, but "Закрепить" is used to sitting *left of* "Дальше" in the paired `.actions` row — alone, keeping that same left-aligned, content-sized position read as one half of a pair missing its other half, not a deliberate single action (caught from a direct user report, in two rounds: first about the position alone — a `.toolbar > button:only-child { width: 100% }` rule, now superseded, was tried as a narrower fix — then about generalizing it into one shared slot system every button-only state goes through, rather than patching each mismatch as it's separately noticed). Primary/blue styling is positional for the same reason, not tied to any one button's own attribute: `.actions > button:last-child` (a lone button is trivially both first and last child of `.actions`) covers "Дальше" whether paired or alone and "Закрепить" whether secondary (paired) or the sole forward action (required-recall case) — `button[type="submit"]` is the one remaining attribute-based case, since the recall answer form's own ✓ button is never inside `.actions` at all. `.toolbar` itself is `display: flex; flex-direction: column; gap: 0.5rem;` so an error message and its `.actions` row below it get the same consistent spacing every other boundary in the card uses, rather than whatever a paragraph's own margin happened to leave.

Gated behind a `recall` boolean attribute (`_recallEnabled`, `this.hasAttribute("recall")`) — off by default, the same convention `disabled`/`required` use natively — rather than shipping unconditionally to every embed: a landing page's embedded widget is meant to stay a light, low-commitment sample of practicing, while the standalone app (`wiederholen/web/static/app/index.html`, the one place actually opting in, via the bare `recall` attribute on `<german-exercise-widget>`) is the surface meant to grow toward full bot-parity functionality. `_renderResult()` computes `recallMode` as `this._recallEnabled ? result.recall : "none"` once, at the top, rather than a separate branch duplicating `"none"`'s own body — an embed that never opted in takes exactly the same path as an exercise with no recalls at all, regardless of what `check_answer()`'s `recall` field actually says. This is a single shared component with one behavior gated by attribute, deliberately not a second forked file for the app: the two contexts already share everything else this file does (layout, `--gew-*` sizing, i18n, focus handling), and forking would mean applying every future fix to both.

`_startRecall()` (`POST /api/exercise/recall`) shows a transient `"…"` in the *current* card's own toolbar while the fetch is in flight (there's nothing to show yet), then on success calls `_addCard()` with a *complete* new card: an `.instruction` line (`recallInstruction` in `STRINGS`, mirroring the bot's own `recall_prompt` wording, "Восстановите фразу"/"Reconstruct the phrase" — without it a learner had no explanation of what a recall step even was or how it differs from the main exercise, caught from a direct user report), a `.centered-pair` wrapping `<p class="question">❓ …</p>` plus, if present, a hint line reusing `.description`'s own class (💡, muted/smaller), and a recall answer form (the same shape as the exercise's own typed-input form) for its toolbar. The recall question is still a question — it reuses `.question`/`.description` directly, the exact same classes the question card itself uses, rather than a bespoke style of its own; that's only possible because a recall step now gets its own dedicated card with its own dedicated `.centered-pair` claimed space, the same as the question card gets. (An earlier version, before the deck existed, squeezed a recall question into the *existing* result card via `insertAdjacentHTML`, which meant it had no claimed vertical space of its own to center within, and needed a bespoke `.recall`/`.recall-question` class pair with only partial centered-pair behavior as a result — both classes are gone now, no longer needed once recall got a real card.) The input isn't `focusOnLoad`-gated the way `_renderQuestion()`'s own is (see below), recall is always the direct result of a deliberate action (submitting the answer that triggered a required recall, or tapping "Закрепить"/"Попробовать ещё раз"), never a cold page load, the one case that gating exists to avoid. Also used for a retry (called again from `_submitRecallAnswer()`'s wrong branch): each call re-fetches via `Tutor.request_recall()`, which already excludes the immediately-previous `recall_question` when alternatives exist (see `docs/repetition-schedule.md`), so a retry naturally varies like it does in the bot.

`_startRecall()`/`_submitRecallAnswer()` both call `_dropRecallCards()` right before their own `_addCard()` — a *second* trim, on top of `_renderResult()`'s own question-card-dropping `_render()` (above): it removes every card after the explanation card (always index 0 by the time recall starts), so the deck only ever holds the explanation plus *one* current recall step, never a growing trail of every attempt. An earlier version let each attempt keep its own card (a retry's new question landing as a fresh card rather than overwriting the failed one, so swiping back showed every attempt in turn) — dropped per a direct user report: unlike the explanation (the actual grammar note recall exists to reinforce), a superseded attempt's own question or feedback stops being useful the moment a new one replaces it, and accumulating them read as clutter rather than history worth reviewing. Both call sites set their loading `"…"` state *before* calling `_dropRecallCards()`, not after — so whatever was showing (the explanation, or a previous attempt's feedback/question) stays in place while the fetch is in flight, and only actually disappears once there's a real new card ready to replace it, not a beat early.

`_submitRecallAnswer(answer)` (`POST /api/exercise/recall/check`) similarly calls `_addCard()` on success — a new card holding just a single-child `.centered-pair` (`.correct`/`.wrong` feedback alone; a `.centered-pair` with one child centers exactly the same way it does with two, `align-items`/`justify-content` don't care how many children there are) — then sets *that* new card's toolbar: correct → a plain "Next" button; wrong → the same two-button `.actions` row as the optional-offer case, with "Попробовать ещё раз" as the trigger. `.correct`/`.wrong` are safe to reuse here outside `.centered-pair`'s original question-card context because both were already purely typographic classes (no positioning baked in) from the round of work that first introduced `.centered-pair`. Both `_startRecall()`/`_submitRecallAnswer()` restore the *current* card's own toolbar to an error + a plain "Next" button on a failed fetch (same `_strings.somethingWrong` text `_renderError()` uses) rather than adding a new card for a step that never actually arrived — never leaves the learner stuck, and never erases whatever's already shown either. `_submitAnswer()`'s own failure handling follows the same shape now, for the same reason: restores the *question* card's own toolbar to an error + "Next", clearing the sessionStorage cache too, rather than routing through the shared, full-reset `_renderError()` — that would `_render()` a brand new single-card deck, wiping the very card the error needs to stay attached to. Deliberately *not* a retry of the same `check_answer()` call, even though the already-chosen answer is right there in the closure: a real-world failure here is far more often a `409` (`WebSessionStore`'s server-side session for this exercise expired — a 1h TTL — while `sessionStorage`'s own cached copy, which carries none, kept letting the learner answer a question the backend no longer has any record of showing) than a transient network blip, and retrying the identical request would just `409` again forever, since nothing about that mismatch changes between attempts — caught from a real `409` in production logs after an earlier version of this tried exactly that "genuine retry" instead. Fetching a fresh exercise is what actually recovers either way.

`wiederholen/web/static/app/` (`index.html`/`app.js`, served at the root path `/` via a second `create_static_files_router(path="/", ..., html_mode=True, name="app")` — a distinct `name` from the widget's own router's default `"static"`, since Litestar requires route handler names to be unique within one app) is the standalone app: the same `<german-exercise-widget>` custom element, just as the page's main content rather than embedded partway down someone else's, and with no `topics` attribute at all — drawing from the whole course via the empty-topics handling described above, since this app has no single grammar topic of its own to scope itself to the way a landing page's embed does. It reaches `widget.js` at the plain same-origin path `/widget/widget.js` directly, unlike the content repo's landing pages: those need `widget-loader.js`'s local-vs-production runtime detection because they're served from a completely different site (GitHub Pages) that doesn't know where `wiederholen.web` lives in a given environment, but this page *is* `wiederholen.web`'s own — `widget.js` is always reachable at that fixed path in every environment, local dev included, so there's nothing to detect. `app.js` only handles the language toggle (`localStorage["wiederholen-lang"]`, `ru`/`en`); an inline `<script>` in `index.html`, placed *before* the `<script src="/widget/widget.js">` tag, applies a saved preference to the widget's `lang` attribute first — plain, static `<script>` tags execute synchronously in document order, so the attribute is already set by the time `widget.js` loads and upgrades the element, well before `app.js` (loaded last) even runs. Switching language happens by reloading the page rather than live, since the widget has no `attributeChangedCallback` reacting to a `lang` change after it's already connected, and a reload naturally gets a fresh `/api/exercise/next` call in the new language anyway. The app's own page chrome stays Russian-only for now, matching the site's broader ru-first/en-not-yet-rolled-out state — only the widget's practice content is actually bilingual here. Deliberately no marketing/promotional copy of its own (e.g. a link back to the Telegram bot, or a product/brand name in the header) — that's content, which belongs in the content repo, not this one; `index.html` here is just app shell, and its `<header>` is just the language toggle, right-aligned since it's the only thing left in it.

`german-exercise-widget { --gew-max-width: 36rem; --gew-height: 26rem; }` in `index.html`'s own CSS overrides two of `widget.js`'s `:host` custom properties (`--gew-max-width`/`--gew-height`, both default to the ~28rem/16rem a landing page's embedded widget uses) to give the standalone app a visibly bigger, more prominent practice card — this page's whole purpose is practicing, so the card should read as the focal point rather than a small aside the way it does embedded partway down an article. Custom properties inherit through the Shadow DOM boundary even though ordinary properties don't, so a host page can override just these two without forking the component or reaching inside its shadow tree; nothing else about `<german-exercise-widget>` differs between the two contexts.

The input's own `.focus()` call is additionally gated on a `focusOnLoad` parameter threaded through `_loadNext(focusOnLoad = false)` → `_renderQuestion(exercise, focusOnLoad)`, defaulting to `false` — `connectedCallback()`'s own calls (both the cache-hit `_renderQuestion(cached)` and the cache-miss `_loadNext()`) never pass it, while the Next/Retry button click handlers pass `true`. On mobile, focusing a text input pops the on-screen keyboard open immediately; that's welcome right after the learner taps a button, but not the instant the page itself finishes loading, before they've done anything at all — caught from a real mobile report of the keyboard popping up unprompted on page load. `_renderResult()`'s own Next-button focus isn't gated the same way, since it's never reached from a cold `connectedCallback()` render in the first place — only ever as the result of submitting an answer, itself already a deliberate action.

A deliberate tap on the input is a separate problem from the above: the keyboard opening is expected there, but the widget is often embedded partway down a long page, and the browser's own default scroll-to-input behavior only ever reveals the `<input>` itself — the question above it (`.body`) scrolls out of view behind the keyboard, with nothing bringing it back. `connectedCallback()` adds a `window.visualViewport.resize` listener (`disconnectedCallback()` removes it — bound once in the constructor so add/removeEventListener refer to the same function) that scrolls the whole widget into view (`this.scrollIntoView({behavior: "smooth", block: "center"})`) whenever `this._shadow.activeElement` is the answer `<input>` at the moment the resize fires. `visualViewport.resize`, not the input's own `focus` event: the keyboard's height isn't known yet the instant focus fires, only once it's actually finished opening, which is exactly when `visualViewport` itself resizes. Checking `this._shadow.activeElement` fresh on each resize, rather than a reference captured at render time, matters because both `_render()` (the whole shadow subtree) and `_addCard()` (just a new card) can replace the `<input>` on any given step, while this listener is attached once for the widget's entire lifetime — a stale captured reference would never match a newer `<input>` element. `window.visualViewport?.` throughout, since it isn't universally available; without it this just degrades to the native scroll-to-input behavior the fix improves on, not a crash. `.deck` itself has a fixed `height: var(--gew-height)` (16rem by default — not just a floor, an earlier `min-height` attempt still let the box resize between differently-sized questions, just less drastically than before) with `overflow: hidden`, and every `.card` inside it stretches to fill that same fixed height (flex's own default `align-items: stretch` in `.track`'s row) — every step, on every card, renders inside the same-sized box, so nothing about answering, advancing, or paging through the deck ever resizes the widget and jolts the surrounding page, on top of the loading-state fix above. 16rem, not the bare minimum a desktop-width embed needs: the same German sentence wraps to more lines on a narrow phone screen than on a wide desktop embed, so the box needs more headroom there — caught from a real mobile screenshot where a long `partizip_ii_meaning` question got cut off mid-sentence at 14rem. `_renderLoading()` (shared by `_loadNext()`/`_submitAnswer()`, replacing what used to be the same literal markup string duplicated in both) and the "nothing available"/error states all render with an extra `.centered` class on their card (flex column, centered both axes) — appropriate for a short, single-purpose message inside the fixed-height box, but deliberately not applied to `.card` generally: a real question or result should start from the top like normal reading order.

`_renderQuestion()`/`_renderResult()` each wrap their variable-length content (`instruction` + a `.centered-pair`, or a `.centered-pair` alone — see below) in a `.body` div, leaving the answer control (`.choices`/the typed-input form) or the "Next" button as a plain sibling after it — a toolbar that's never part of the scrolling region. `.body` takes `flex: 1` (claiming whatever vertical space the toolbar doesn't need, which is also what pins a short toolbar to the bottom without a separate `margin-top: auto` rule) and `overflow-y: auto` of its own; `.card`'s own flex column also sets `gap: 1rem` between `.body` and the toolbar after it, the same value `.body` itself uses internally between `instruction` and `.centered-pair` (see below) — one shared interval for every boundary between genuinely distinct pieces of the card, not a separately-tuned value for this one specific boundary — `.card`'s own `overflow: hidden` is deliberately not `auto` here, since scrolling the *whole* box for a too-long question used to take the answer control (and the "Next" button) out of view along with it, a real report from before this split existed. `min-height: 0` on `.body` overrides a flex item's default `min-height: auto`, which would otherwise keep it at its content's full height and defeat `overflow-y: auto` entirely — a well-known flexbox-plus-scrolling gotcha, not a redundant rule. `.body` also gets a `mask-image: linear-gradient(to bottom, black calc(100% - 0.35rem), transparent 100%)` — a soft fade at its bottom edge hinting there's more to scroll to, rather than a hard cutoff; using a mask rather than painting a color over the fade means it works regardless of the page's actual background color, since it fades this element's own content toward transparent rather than overlaying anything. Fixed at `0.35rem`, not a percentage of `.body`'s own height (an earlier version used `92%`): a percentage-based zone scales with `.body`'s own height rather than with the text it's fading — harmless for most content, which (like `.centered-pair` below) has centering slack around it and never touches the fade zone at all, but the standalone app's taller `--gew-height` card could still turn it into most of a line reading visibly faded on whichever content ends up flush against `.body`'s bottom edge (caught from a real screenshot, back when `description` itself sat flush against `.body`'s bottom by design instead of grouped with `question`). A small fixed zone keeps the softening to what it was always meant to be regardless: a few pixels of a line's own bottom edge, not the line itself.

`.centered-pair` groups a card's two central pieces of text into one visual unit that moves and centers together, rather than leaving the second one to drift off on its own — used on three of the four kinds of card in the deck, not just one: on the question card it wraps `question` + `description` (`description` is a translation of `question` into the student's language, not a how-to-answer note the way `instruction` is — the two are the same sentence in two languages); on the result card it wraps the `.correct`/`.wrong` verdict label (the ✅/❌ line, which also names the correct answer when wrong) + `.explanation` — the label plays `question`'s role (the actual fact worth remembering, so it gets the same `font-size: 1.1em`) and `.explanation` plays `description`'s (the grammar note backing it up, sharing `description`'s own `font-size: 0.9em; color: var(--gew-muted)` rule rather than a separately-declared copy of the same values); a recall question card reuses `question`/`description` directly for its own question/hint, exactly like the original question card — the fourth kind, a recall result card, holds only a single-child `.centered-pair` (see above). `instruction` (question card only, when present) stays outside the pair, rendered before it — a plain paragraph, not part of this grouping, since it's genuinely a different kind of text (guidance, not a translation or a verdict). `.centered-pair` itself takes `flex: 1` — the only growable item in `.body`'s column, `instruction` stays sized to its own content — so it claims 100% of whatever vertical space `instruction` doesn't need (all of `.body`, on every card besides the question one, none of which have an `instruction` equivalent), and centers its children as a group within that claimed space via its own nested `display: flex; flex-direction: column; align-items: center; justify-content: center; text-align: center` — the `text-align` lives here, once, rather than repeated on each child, covering all of them by inheritance. The `gap` between children is a deliberately *tighter* `0.5rem`, distinct from `.body`'s own `gap: 1rem` between `instruction`/`.centered-pair` and `.card`'s matching `gap: 1rem` between `.body` and the toolbar after it (see above) — the larger interval separates genuinely distinct pieces of the card, while the smaller one is what visually reads as one connected thought (a line and its translation, a verdict and its explanation) rather than two unrelated ones. An earlier version kept each pair's two elements as independent siblings, the second one pinned to the bottom of `.body` on its own (first via `margin-top`/`margin-bottom: auto`, later via `flex: 1` on the first element alone) — mathematically tidy either way, but it left the second element visually stranded far from the first, with no sense the two were related at all, regardless of its own alignment (centering it in that far-away position was tried and reverted for the same reason — caught from real user reports on both the question card and, once the same imbalance was noticed there too, the result card). On the rare case long enough to need `.body`'s own scroll, `flex: 1` still can't shrink `.centered-pair` below its content's natural height, so it just packs at the top like a plain paragraph would — no worse than top-alignment already was, unlike plain `justify-content: center` on `.body` itself would have been (that can push a flex group's start past the scrollable area's top edge once content overflows, making the beginning of the text unreachable by scrolling — the same pitfall `.centered` avoids for the same reason elsewhere in this file). Flexbox's `gap` only inserts space *between* items that actually exist, so an exercise missing `instruction` never leaves a phantom gap where it would've been. `p`'s own default margin is plain `margin: 0` (not `0 0 0.75rem`) — every pair gets its spacing from `.centered-pair`'s own `gap` instead of a trailing paragraph margin.

`.choices` is a CSS grid (`grid-template-columns: repeat(2, 1fr)`), not `flex-wrap` — flex-wrap sizes each button to its own text, leaving column edges ragged whenever one choice is longer than a neighbor in the same row (e.g. "mein Wunsch" next to "meines Wunsches", caught from a real screenshot); grid's equal-width columns, combined with a button's default stretch to fill its own cell, keep every button in a row the same width and every column aligned regardless of how uneven the choice text lengths are. A fixed 2 columns, not `auto-fit`: nearly every real exercise has exactly 4 choices (345 of 346 in the actual course data), and `auto-fit` sized to a `minmax(7rem, 1fr)` track sometimes decided 3 columns fit the card's own width — stranding the 4th choice alone on its own row instead of the clean 2×2 a fixed 2-column grid always gives for the common case (also caught from a real screenshot).

`_renderQuestion()` branches to `_renderWordOrderQuestion()` entirely (returning immediately) when `exercise.word_bank` is set, rather than adding a third `answerArea` case alongside `.choices`/the typed-input form: a `word_bank` exercise (`konjunktion_wortstellung`/`nebensatzkonjunktion_wortstellung` — see `Exercise.word_bank` in `CLAUDE.md`) needed genuinely different body content, not just a different answer control — typing the whole reconstructed sentence by hand was a real, direct complaint once the widget was no longer constrained to a chat's text input the way the Telegram bot still is. Its body skips `.centered-pair` altogether: `instruction`, then a plain `<p class="question">`, then `description`, then the tile UI, all as ordinary top-down siblings in `.body`'s own flex column — this content needs the card's height for the tiles themselves, not flashcard centering. Two `flex-wrap` rows, `.word-order-bank` (the shuffled tiles, one `<button type="button" data-tile>` per `word_bank` chunk — a chunk may be more than one word, e.g. `"in Hamburg"`, rendered as a single tile) and `.word-order-assembled` (starts genuinely empty — no placeholder text; an earlier version showed a muted `…` there, dropped per a direct user report since it read as a loading indicator rather than "drop words here" — `.word-order-assembled`'s own `min-height` plus its dashed bottom border already mark it as a real, bounded drop zone on their own, and the instruction line above already says what to do), share one click handler per tile: tapping a tile appends it to whichever row it *isn't* currently in (`tile.parentElement === bank ? assembled : bank`). Tracking tiles as the actual DOM elements moved between the two containers, rather than by their text, means two identical chunks (e.g. two `der` tiles) are each independently clickable with no special-casing at all. `flex-wrap`, not `.choices`'s own fixed 2-column grid: a sentence's word count varies far more than "almost always 4" multiple-choice options. No submit button — once `.word-order-bank` empties, the assembled tiles' text joins with `" "` and goes straight to the existing `_submitAnswer()`, and every assembled tile is `disabled` first (same non-idempotent-`check_answer()` reasoning as `_addCard()`'s own toolbar-freezing) so a tap mid-submission can't send one back to the bank.

Env vars: `WEB_SESSION_STORAGE_URL` (own Redis DB — same one-store-one-DB reasoning as `BOT_FSM_STORAGE_URL`/`STUDENT_RECORD_STORAGE_URL`, see "Persistence" in `CLAUDE.md`), `WEB_ALLOWED_ORIGINS` (comma-separated, doing double duty — `CORSConfig(allow_origins=..., allow_credentials=True)` *and* the trusted-origin list `_safe_redirect_target()` checks, see "Telegram login" in `CLAUDE.md`), `WEB_COOKIE_DOMAIN`. `STUDENT_RECORD_STORAGE_URL` and `STUDENT_IDENTITY_STORAGE_URL` are both shared with `wiederholen.bot` outright, unprefixed, same reasoning as always: every frontend addressing the same physical store needs the same URL, not a `wiederholen.web`-specific copy. `BOT_TOKEN` is shared too, but for a different reason than the two stores — see "Telegram login" in `CLAUDE.md`.

`create_app()` also registers `litestar.plugins.opentelemetry.OpenTelemetryPlugin(OpenTelemetryConfig())` — real auto-instrumentation (`opentelemetry-instrumentation-asgi` underneath, the same kind of third-party package `instrument_redis()`'s `RedisInstrumentor` is, not a hand-rolled equivalent of `wiederholen.bot.tracing.TracingMiddleware`) that wraps every request in a server span. Without it, every Redis call `next_exercise()`/`check_answer()` makes via `student_record_book`/`session_store` would show up as its own orphan root span instead of grouped under the request that made it — the same problem `TracingMiddleware`/`reminder.py`'s hand-rolled spans solve for their own processes (see "Tracing" in `CLAUDE.md`). No explicit `tracer_provider` passed to `OpenTelemetryConfig()`: like `default_tracer` elsewhere, it resolves whatever the current global provider is lazily, so this is a safe no-op until `wiederholen.web.__main__.main()`'s own `configure_tracing()` call actually installs one.

Testing `wiederholen.web` needs `litestar.testing.AsyncTestClient`, not the sync `TestClient`: the sync client serves the ASGI app through an `anyio` portal running in its own thread with its own event loop, and a Redis client whose connection pool already made contact from the outer test's loop can't be reused from a different one (`RuntimeError: ... attached to a different loop`). `tests/web/test_app.py`'s `web_app_factory` fixture depends on the `student_record_book`/`web_session_store`/`student_identity_store` fixtures purely to get their DBs flushed before the test, but deliberately builds *fresh* `RedisStudentRecordBook`/`WebSessionStore`/`RedisStudentIdentityStore` instances pointed at the same URLs for the app's own state, so the app's first real Redis command happens from whichever loop actually serves it, not the outer test's. `AsyncTestClient` also needs `base_url="https://..."` (not the default `http://`): a `Secure` cookie is never attached to a plain-`http` request by httpx's cookie jar, which would otherwise make every cookie silently vanish between requests in a test — same as a real browser would refuse to send it back over plain HTTP.
